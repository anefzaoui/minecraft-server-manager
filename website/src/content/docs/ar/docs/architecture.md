مدير خوادم Minecraft هو تطبيق Node.js أحادي العملية، يعرض الصفحات من جانب الخادم. يدير هذا التطبيق خوادم Minecraft التي تعمل كحاويات Docker باستخدام صورة [itzg/docker-minecraft-server](https://github.com/itzg/docker-minecraft-server)، ويتواصل مع Docker daemon عبر واجهة برمجة التطبيقات الخاصة به (وليس عن طريق استدعاء `docker` CLI).

## شكل وقت التشغيل

- يقوم **Express + Handlebars** بعرض الصفحات من جانب الخادم. لا يوجد تطبيق أحادي الصفحة (SPA)؛ JavaScript في المتصفح الموجود في `public/js/` هو تحسين تدريجي مكتوب يدويًا. تقوم خطوة esbuild (`pnpm run build:js`) بتجميع وتصغيره إلى `public/dist/js/`؛ ويقدم التطبيق هذه الحزمة عندما تكون موجودة، وإلا فإنه يقدم المصدر الخام، لذا فإن تشغيل التطوير بدون بناء لا يزال يعمل.
- **`node:sqlite`** (مدمج في Node؛ تتطلب اللوحة Node ≥ 24) هو قاعدة البيانات - متزامنة، بدون وحدات أصلية، وضع WAL. يقوم مشغل ترحيل صغير ذو إصدارات بتطبيق `src/db/migrations/*` عند التشغيل. يتم تخزين العبارات المُجهزة مؤقتًا في `src/db/index.js` مفتاحها هو نص SQL.
- يحمل **`ws`** تدفقات وحدة التحكم والإحصائيات المباشرة. كلاهما **وسيط**: `docker logs --follow` واحد (أو `docker stats`) لكل خادم، يتم فك تعدد الإرسال مرة واحدة وتوزيعه على كل علامة تبويب متصلة، بدلاً من تدفق واحد لكل مشاهد. يحتفظ وسيط وحدة التحكم بمخزن مؤقت صغير لإعادة التشغيل لعلامات التبويب التي تنضم متأخرًا ويسقط المشترك الذي يتأخر مقبس الاتصال الخاص به كثيرًا بدلاً من تعطيل التدفق المشترك.
- **dockerode** هي الطريقة الوحيدة التي يتحدث بها التطبيق إلى Docker. يتم الكشف عن نقطة النهاية تلقائيًا لكل منصة (أنبوب Windows المسمى مقابل مقبس يونكس).
- **جميع الحالات المستمرة تعيش تحت دليل واحد** (`$DATA_DIR`، الافتراضي `./data`). يؤدي نسخ هذا الدليل إلى ترحيل اللوحة بأكملها.

## الطبقات

تتدفق التبعيات في اتجاه واحد:

```
                 ┌─────────────────────────────┐
   HTTP  ───────▶│  web/routes/*  (+ middleware)│   parse & validate input, shape responses
                 └──────────────┬──────────────┘
                                │
                 ┌──────────────▼──────────────┐
                 │         services/*          │   domain logic (the actual features)
                 └───┬─────────┬─────────┬─────┘
                     │         │         │
        ┌────────────▼──┐ ┌────▼────┐ ┌──▼──────────┐
        │   docker/*    │ │  db/*   │ │  storage/*  │   infrastructure
        └───────────────┘ └─────────┘ └─────────────┘
```

- **`web/routes/`** - موجه واحد لكل نطاق (`servers`, `players`, `worlds`, `crashes`, `blueprints`, `files`, …)، مثبت في `web/app.js`. تقوم الموجهات بالتحقق باستخدام zod، وتستدعي خدمة، وتعيد JSON أو تعرض عرضًا. لا ينتمي منطق العمل إلى هنا. يتم تثبيت موجهين في **المنطقة العامة**، قبل `requireAuth`: `routes/status.js` (صفحات حالة HTML اختيارية لكل خادم) و`routes/apiV1.js` (`/api/v1`، واجهة برمجة تطبيقات JSON للقراءة فقط مصادق عليها بواسطة رمز Bearer مميز من قبل المسؤول من `services/apiTokens.js`، معطلة ما لم يتم تمكينها في الإعدادات؛ انظر `docs/public-api.md`).
- **`services/`** - قلب التطبيق. تمتلك كل خدمة نطاقًا واحدًا وقد تعتمد على البنية التحتية وعلى خدمات أخرى.
- **`docker/`** - أغلفة dockerode: `connect` (الكشف عن نقطة النهاية + صحة daemon)، `containers` (إنشاء/بدء/إيقاف/إعادة إنشاء مع ربط وحدات التخزين، حدود الذاكرة/وحدة المعالجة المركزية، والتسميات)، `logs`، `stats`، `images`، و`watcher` يحول أحداث Docker إلى سجل + الكشف عن الأعطال.
- **`db/`** - غلاف SQLite ومشغل الترحيل.
- **`storage/`** - تمهيد `./data`، و**حارس المسار** (`safeJoin`، العمود الفقري لسلامة الملفات)، ومفهرس الحجم في الخلفية + تطبيق الحصص.

عبر القطاعات:

- **`config/`** - تكوين البيئة بالإضافة إلى **كتالوج الحقول**: المصدر الوحيد للحقيقة لإعدادات الخادم. يتم فهرسة كل متغير بيئة itzg (التسمية، المساعدة، النوع، الوحدة، الافتراضي، التحقق، القسم، علامات الخطر). يتم اشتقاق المعالج، ونماذج الإعدادات، والتحقق من zod كلها منه، لذا فإن كشف إعداد جديد هو تغيير في البيانات، وليس سباكة واجهة مستخدم جديدة.
- **`events/`** - `recordEvent()` هي نقطة الدخول الوحيدة لسجل التاريخ؛ تلتقط أحداث دورة الحياة أيضًا مقتطفات سجل الحاوية إلى `data/logs/<id>/events/`.
- **`ws/`** - WebSockets لوحدة التحكم والإحصائيات المصادق عليها (يتم التحقق من ملف تعريف الارتباط الخاص بالجلسة عند الترقية، ويتم فحص `Origin` لمنع اختطاف المواقع)، يتم توسطها لكل خادم (انظر "شكل وقت التشغيل").
- **`logger.js` + `instrument.js`** - `require('./logger')(label)` يعيد مسجل [Pino](https://getpino.io) لكل وحدة؛ المستوى من `LOG_LEVEL`، `makeFailureThrottle()` يحافظ على حلقة خلفية فاشلة باستمرار لسطر سجل واحد بالإضافة إلى سطر "تم الاسترداد". يقوم `src/utils/logSanitize.js` بحذف المفاتيح التي تشبه بيانات الاعتماد ورموز webhook من البيانات الوصفية المهيكلة؛ `src/config/logLevel.js` هو قائمة السماح المشتركة للمستوى (يتم الاحتفاظ بها منفصلة لتجنب دورة `require` مع `config`). `src/instrument.js` هو درز Sentry خامد، يتم تحميله أولاً في `src/server.js`. `src/web/middleware/requestLog.js` يكتب سطر سجل وصول واحد لكل طلب (يتخطى `/healthz` والأصول الثابتة). يفرض ESLint `no-console` تحت `src/**`، مع إعفاء `preflight.js` و`instrument.js` و`config/index.js` (يتم تشغيلها قبل وجود المسجل).
- **تحديد المعدل** - `src/web/middleware/rateLimit.js` يضع `express-rate-limit` أمام `/api` (`RATE_LIMIT_API_PER_MIN`، الافتراضي 1200) وتسجيل الدخول / المصادقة الثنائية / إرسالات الإعدادات (`RATE_LIMIT_AUTH_PER_15MIN`، الافتراضي 100)؛ `0` يعطل المحدد. يعتمد على `req.ip`، لذا فإن `TRUST_PROXY` مهم خلف وكيل. يحتوي `/api/v1` على محدد خاص به لكل رمز مميز (`RATE_LIMIT_PUBLIC_API_PER_MIN`، الافتراضي 120)، يعتمد على تجزئة رمز Bearer مع احتياطي IP. يتعامل عداد ناعم منفصل لكل حساب في `src/web/middleware/auth.js` مع قفل تسجيل الدخول (لكل IP وعلى مستوى الحساب، يتلاشى).

## سلوكيات النطاق الرئيسية

- **حزم التعديلات مثبتة دائمًا.** تقوم الصورة بالترقية التلقائية للحزم غير المثبتة في كل إعادة تشغيل، لذا تقوم اللوحة بحل "الأحدث" إلى معرف إصدار محدد في وقت التثبيت وتثبيته. الترقيات هي تدفق منسق صريح (`updates/`): معاينة ← نسخ احتياطي قبل التحديث ← إيقاف تشغيل سلس ← إعادة تثبيت ← إعادة إنشاء ← مراقبة الصحة ← استعادة بنقرة واحدة.
- **تراكب التعديلات المخصصة** تتم إدارته بواسطة اللوحة: تصل التعديلات التي يضيفها المستخدم إلى المكتبة المكررة ويتم ربطها بقوة بالخادم بحيث تبقى على قيد الحياة بعد تحديثات الحزمة. التعطيل يراعي الفئة.
- يتم تخصيص **المنافذ** من مخطط أساسي (اللعبة من `PORT_GAME_START` فصاعدًا، RCON = اللعبة + `PORT_RCON_OFFSET`، Bedrock من `PORT_BEDROCK_START`)، ويتم فحصها للتأكد من توفرها، وحجزها في قاعدة البيانات.
- يتم فرض **حصص القرص** بواسطة اللوحة لأن Docker لا يمكنه تحديد استخدام وحدات التخزين المربوطة: يقوم المفهرس بتخزين أحجام كل دليل ويتم التحكم في عمليات زيادة القرص بناءً عليها.
- يتم تشفير **الأسرار** (كلمات مرور RCON، مفاتيح API، أسرار TOTP، عنوان URL لـ Discord webhook) في حالة السكون باستخدام AES-256-GCM باستخدام مفتاح عشوائي مخصص في `$DATA_DIR/.secret-key` (الوضع `0600`، يتم إنشاؤه تلقائيًا). وهو مستقل عن `SESSION_SECRET`؛ يتم الاحتفاظ بمفتاح مشتق من `SESSION_SECRET` كاحتياطي لفك التشفير فقط للقيم المكتوبة قبل وجود المفتاح المخصص، ويقوم `src/services/secretsMigration.js` بإعادة تشفير تلك القيم تحت المفتاح المخصص مرة واحدة عند التشغيل. يعتبر `.secret-key` الموجود ولكن لا يمكن تحليله خطأ تشغيل صارم (لا يتم إعادة إنشائه بصمت أبدًا). تقوم المخططات بإزالة جميع الأسرار عند التصدير.

## تنسيقات البيانات والأسلاك

- **`data/panel.db`** - قاعدة بيانات SQLite. يتم أخذ لقطات يوميًا عبر `VACUUM INTO` إلى `data/backups/_panel/` (يتم الاحتفاظ بأحدث 14 لقطة)؛ يتم تشغيل `PRAGMA integrity_check` عند التشغيل.
- **`data/.session-secret`** - سر توقيع ملف تعريف الارتباط الذي يتم إنشاؤه تلقائيًا، يتم إنشاؤه عند التشغيل الأول إذا لم يتم تعيين `SESSION_SECRET`. يؤدي حذفه إلى تدوير السر (مما يبطل الجلسات).
- **`data/.secret-key`** - مفتاح التشفير المخصص في حالة السكون بحجم 32 بايت (الوضع `0600`)، يتم إنشاؤه تلقائيًا عند التشغيل الأول. مستقل عن `SESSION_SECRET`؛ يؤدي حذفه إلى جعل كل بيانات الاعتماد المخزنة غير قابلة للفك، لذا فهو ينتمي إلى نسخك الاحتياطية.
- **المخططات (`.mcserver.zip`)** - ملف مضغوط يحتوي على `manifest.json` يصف التكوين والموارد ومرجع الحزمة المثبتة وبيان التراكب (عناوين URL المصدر + sha256) وملفات التكوين المختارة، واختياريًا عالم. إعادة التنزيل والتحقق من التجزئة لكل تعديل وتعيين منافذ جديدة.
- يتم تسمية وتصنيف **حاويات Docker** التي أنشأتها اللوحة بحيث يمكن للمراقب العثور عليها؛ تمتلك اللوحة دورة حياتها الكاملة.

## تسلسل التشغيل

1. `require('./instrument')` (درز Sentry) قبل أي شيء آخر، ثم `require('./preflight')` للفشل بوضوح في إصدار Node غير مدعوم.
2. تحميل التكوين؛ التأكد من/إنشاء `.session-secret` **و** `.secret-key`.
3. `ensureDataRoot()` - إنشاء تخطيط `./data`، مسح `tmp/`.
4. تشغيل ترحيلات قاعدة البيانات، ثم `PRAGMA integrity_check` (يسجل بصوت عالٍ، ويشير إلى `data/backups/_panel` عند الفشل).
5. إعادة تشفير أي أسرار قديمة مفتاحها `SESSION_SECRET` تحت `.secret-key` (`secretsMigration`).
6. بذور المخططات الأولية (محمية).
7. بدء خادم HTTP + WS. عند الربط المكشوف، اطبع رقم التعريف الشخصي (PIN) الخاص بـ `/setup` للتشغيل الأول.
8. تثبيت حارس وقت التشغيل بعد التشغيل (يلتقط الأخطاء غير المعالجة؛ `MSM_EXIT_ON_FATAL=1` يجعله يخرج بقوة للنشر تحت الإشراف).
9. بدء خدمات الخلفية: وسيط WS، مفهرس التخزين، مراقبي الأعطال والمخزون، المجدول، جسر أحداث Discord، و**مؤقت الصيانة اليومي** (تقليم صفوف التحليلات القديمة + لقطة `panel.db`).
10. تهيئة Docker **في الخلفية**. واجهة المستخدم قابلة للاستخدام بالكامل بينما يكون daemon معطلاً؛ تضيء ميزات Docker عندما يصبح قابلاً للوصول. بمجرد الاتصال، تقوم `refreshStatuses({ boot })` بتسوية الحالات المخزنة مؤقتًا، وتصدر حدث `offline-after-restart` لمرة واحدة لخادم كان يعمل قبل إعادة تشغيل اللوحة ولن يتم إعادته، وتبدأ حلقة التشغيل خوادم `auto_start` بالإضافة إلى استعادة خوادم `auto_restart` التي تم العثور عليها معطلة أثناء الانقطاع (مع مراعاة التراجع عن حلقة الأعطال).

> ترتيب "instrument-before-preflight" هو مقايضة متعمدة: فهو يسمح لربط Sentry المستقبلي بتصحيح وقت التشغيل أولاً، على حساب رسالة أقل ودية قليلاً على Node قديم حقًا.

## خط أنابيب البناء

`pnpm run build` = `build:css` (Tailwind → `public/css/app.css`) + `build:js` (esbuild → `public/dist/js/`، ESM مع تقسيم الكود). `postinstall` يشغل **CSS فقط**. `public/css/app.css` و`public/dist/` هي عناصر بناء يتم تجاهلها بواسطة git؛ تشغل مرحلة بناء Dockerfile `pnpm run build` بالكامل وتنسخ `public/` إلى صورة وقت التشغيل. يتم تقديم الأصول الثابتة `immutable`/long-cache للملفات ذات البصمة، وshort-cache لـ CSS/JS، و`no-cache` لـ HTML و`/api`.
