مدير خوادم Minecraft هو تطبيق Node.js أحادي العملية، يعرض الصفحات من جانب الخادم. يدير خوادم Minecraft التي تعمل كحاويات Docker باستخدام صورة [itzg/docker-minecraft-server](https://github.com/itzg/docker-minecraft-server)، ويتواصل مع Docker daemon عبر واجهة برمجة التطبيقات الخاصة به (لا يتم استخدام سطر أوامر `docker` أبدًا).

## شكل وقت التشغيل

- يقوم **Express + Handlebars** بعرض الصفحات من جانب الخادم. لا يوجد تطبيق صفحة واحدة (SPA)؛ JavaScript الخاص بالمتصفح في `public/js/` مكتوب يدويًا لتحسين الأداء التدريجي. تقوم خطوة esbuild (`pnpm run build:js`) بتجميع وتصغيره في `public/dist/js/`؛ ويقدم التطبيق هذه الحزمة عندما تكون موجودة، وإلا فإنه يقدم المصدر الأصلي، لذا فإن تشغيل التطوير بدون بناء لا يزال يعمل.
- **`node:sqlite`** (مدمج في Node؛ تتطلب اللوحة Node ≥ 24) هو قاعدة البيانات - متزامنة، بدون وحدات أصلية، وضع WAL. يقوم مشغل ترحيل صغير ذو إصدارات بتطبيق `src/db/migrations/*` عند التشغيل. يتم تخزين العبارات المُعدة مؤقتًا في `src/db/index.js` مفتاحها هو نص SQL.
- يحمل **`ws`** تدفقات وحدة التحكم والإحصائيات المباشرة. كلاهما **وسيط**: تدفق `docker logs --follow` واحد (أو `docker stats`) لكل خادم، يتم فك تجميعه مرة واحدة وتوزيعه على كل علامة تبويب متصلة، بدلاً من تدفق واحد لكل عارض. يحتفظ وسيط وحدة التحكم بمخزن مؤقت صغير لإعادة التشغيل لعلامات التبويب التي تنضم متأخرًا ويسقط المشترك الذي يتأخر مقبس الاتصال الخاص به كثيرًا بدلاً من تعطيل التدفق المشترك.
- **dockerode** هي الطريقة الوحيدة التي يتحدث بها التطبيق إلى Docker. يتم الكشف عن نقطة النهاية تلقائيًا لكل منصة (أنبوب Windows المسمى مقابل مقبس Unix).
- **جميع الحالات المستمرة تعيش تحت دليل واحد** (`$DATA_DIR`، الافتراضي `./data`). يؤدي نسخ هذا الدليل إلى ترحيل اللوحة بأكملها.

## الطبقات

تتدفق التبعيات في اتجاه واحد:

```
                 ┌─────────────────────────────┐
   HTTP  ───────▶│  web/routes/*  (+ middleware)│   parse & validate input, shape responses
                 └──────────────┬──────────────┘
                                │
                 ┌──────────────▼──────────────┐
                 │         services/*          │   domain logic (the actual features)
                 └───┬─────────┬─────────┬─────┘
                     │         │         │
        ┌────────────▼──┐ ┌────▼────┐ ┌──▼──────────┐
        │   docker/*    │ │  db/*   │ │  storage/*  │   infrastructure
        └───────────────┘ └─────────┘ └─────────────┘
```

- **`web/routes/`** - موجه واحد لكل مجال (`players`, `worlds`, `crashes`, `blueprints`, `files`, …). يقوم `web/app.js` بتثبيت الموجهات ذات المستوى الأعلى (`api.js`، واجهة برمجة تطبيقات JSON للجلسة التي تحتوي أيضًا على مسارات الخادم الأساسية وتثبت موجهات المجال لكل خادم؛ `index.js`، الصفحات؛ `auth`، `account`، `tasks`، …). تقوم الموجهات بالتحقق من الصحة باستخدام zod، وتستدعي خدمة، وتعيد JSON أو تعرض عرضًا. لا ينتمي منطق العمل هنا. يتم تثبيت موجهين في **المنطقة العامة**، قبل `requireAuth`: `routes/status.js` (صفحات حالة HTML اختيارية لكل خادم) و`routes/apiV1.js` (`/api/v1`، واجهة برمجة تطبيقات JSON للقراءة فقط مصادقة بواسطة رمز مميز Bearer صادر عن المسؤول من `services/apiTokens.js`، معطلة ما لم يتم تمكينها في الإعدادات؛ انظر `docs/public-api.md`).
- **`services/`** - قلب التطبيق. تمتلك كل خدمة مجالًا واحدًا وقد تعتمد على البنية التحتية وعلى خدمات أخرى.
- **`docker/`** - أغلفة dockerode: `connect` (الكشف عن نقطة النهاية + صحة daemon)، `containers` (إنشاء/بدء/إيقاف/إعادة إنشاء مع ربط المجلدات، وحدود الذاكرة/وحدة المعالجة المركزية، والتسميات)، `logs`، `stats`، `images`، `networks` (اكتشاف شبكة المضيف)، `hostPath` (إعادة توجيه مسارات الربط تحت `DATA_DIR_HOST`)، و`watcher` يحول أحداث Docker إلى سجل + اكتشاف الأعطال.
- **`db/`** - غلاف SQLite ومشغل الترحيل.
- **`storage/`** - تهيئة `./data`، و**حارس المسار** (`safeJoin`، العمود الفقري لسلامة الملفات)، ومؤشر الحجم في الخلفية + تطبيق الحصص.

عبر القطاعات:

- **`config/`** - تكوين البيئة بالإضافة إلى **كتالوج الحقول**: المصدر الوحيد للحقيقة لإعدادات الخادم. يتم فهرسة كل متغير بيئة itzg (التسمية، المساعدة، النوع، الوحدة، الافتراضي، التحقق من الصحة، القسم، علامات الخطر). يتم اشتقاق المعالج ونماذج الإعدادات والتحقق من صحة zod منه، لذا فإن كشف إعداد جديد هو تغيير بيانات، وليس سباكة واجهة مستخدم جديدة.
- **`events/`** - `recordEvent()` هي نقطة الدخول الوحيدة لسجل التاريخ؛ تلتقط أحداث دورة الحياة أيضًا مقتطفات سجل الحاوية إلى `data/logs/<id>/events/`.
- **`ws/`** - WebSockets لوحدة التحكم والإحصائيات المصادق عليها (يتم التحقق من ملف تعريف الارتباط الخاص بالجلسة عند الترقية، ويتم فحص `Origin` لمنع اختطاف المواقع المشتركة)، يتم وسيطتها لكل خادم (انظر "شكل وقت التشغيل").
- **`logger.js` + `instrument.js`** - `require('./logger')(label)` يعيد مسجل [Pino](https://getpino.io) لكل وحدة؛ المستوى من `LOG_LEVEL`، `makeFailureThrottle()` يحافظ على حلقة خلفية فاشلة باستمرار لسطر سجل واحد بالإضافة إلى سطر "تم الاسترداد". يقوم `src/utils/logSanitize.js` بحذف المفاتيح التي تشبه بيانات الاعتماد ورموز webhook من البيانات الوصفية المهيكلة؛ `src/config/logLevel.js` هي قائمة السماح المشتركة للمستوى (مفصولة لتجنب دورة التطلب مع `config`). `src/instrument.js` هو وصلة Sentry خاملة، يتم تحميلها أولاً في `src/server.js`. `src/web/middleware/requestLog.js` يكتب سطر سجل وصول واحد لكل طلب (يتخطى `/healthz` والأصول الثابتة). يفرض ESLint `no-console` تحت `src/**`، مع استثناء `preflight.js` و`instrument.js` و`config/index.js` (يتم تشغيلها قبل وجود المسجل).
- **تحديد المعدل** - `src/web/middleware/rateLimit.js` يضع `express-rate-limit` أمام `/api` (`RATE_LIMIT_API_PER_MIN`، الافتراضي 1200) وطلبات POST لتسجيل الدخول / المصادقة الثنائية / الإعداد (`RATE_LIMIT_AUTH_PER_15MIN`، الافتراضي 100)؛ `0` يعطل المحدد. يعتمد على `req.ip`، لذا فإن `TRUST_PROXY` مهم خلف وكيل. يحتوي `/api/v1` على محددات خاصة به: حد لكل عنوان IP للعميل (خمسة أضعاف ميزانية الرمز المميز) يعمل قبل التحقق من الرمز المميز، ثم ميزانية لكل رمز مميز (`RATE_LIMIT_PUBLIC_API_PER_MIN`، الافتراضي 120) مفتاحها هو معرف الرمز المميز الذي تم التحقق منه. يتعامل عداد ناعم منفصل لكل حساب في `src/web/middleware/auth.js` مع قفل تسجيل الدخول (لكل IP وعام للحساب، يتلاشى).
- **الترخيص**: طبقتان. الدور العام (`requireAuth` → `requireRole` / `requireWrite` في `src/web/middleware/auth.js`) يحمي الإجراءات على مستوى اللوحة وهو الافتراضي على كل خادم. أذونات لكل خادم (`src/services/permissions.js`، تسع قدرات مخزنة كقائمة JSON لكل `(user, server)` في `user_server_permissions`) تنقح هذا الافتراضي لخادم واحد؛ كل مسار `/api/servers/:id`، وتثبيت موجه فرعي، وصفحة، وWebSocket، وقائمة على مستوى الأسطول تمر عبر `src/web/middleware/serverAccess.js` (`serverScope`، مثبت على بادئة `/servers/:id` لكل من واجهة برمجة التطبيقات وموجه الصفحة، يخفي الخادم بدون `view` كخطأ 404؛ `requireCap(cap)` يسمي القدرة التي يحتاجها المسار). الكتابات التي تسمي خادمها في النص (الجداول الزمنية، استخراج وتثبيت العالم، تصدير المخطط) مفتوحة للمشاهدين بواسطة `requireWrite` فقط لهذا الخادم، ويتحقق كل مسار من هذه القدرة بنفسه. `test/permissions-routes.test.js` يتتبع مكدسات الموجه المباشر ويفشل إذا كان مسار الكتابة أو التثبيت أو الصفحة ذات النطاق الخادم لا يحتوي على بوابة.

## سلوكيات المجال الرئيسية

- **حزم التعديل مثبتة دائمًا.** تقوم الصورة بترقية الحزم غير المثبتة تلقائيًا عند كل إعادة تشغيل، لذا تقوم اللوحة بحل "الأحدث" إلى معرف إصدار محدد وقت التثبيت وتثبيته. الترقيات هي تدفق منسق صريح (`updates/`): معاينة ← نسخ احتياطي قبل التحديث ← إيقاف تشغيل سلس ← إعادة تثبيت ← إعادة إنشاء ← مراقبة الصحة ← استعادة بنقرة واحدة.
- **تراكب التعديلات المخصصة** تتم إدارته بواسطة اللوحة: التعديلات التي يضيفها المستخدم تهبط في المكتبة المزالة التكرار ويتم ربطها بقوة بالخادم بحيث تبقى على قيد الحياة بعد تحديثات الحزمة. يتم تعطيلها مع مراعاة الفئة. نظرًا لأن المكتبة تحتفظ بكل بناء تم تنزيله، فإن التحديث يسجل البناء الذي استبدله (`server_content.previous_*`) ويمكن التراجع عنه من الملفات المحلية وحدها. يؤدي تعطيل تعديل الحزمة إلى كتابة متغير بيئة استبعاد الحزمة بدلاً من ذلك؛ يحمل `packs.applyPack` ذلك وبقية ضبط الحزمة (`PACK_TUNING_KEYS`) عبر تغيير إصدار نفس الحزمة، ويسقطها عند تغيير الحزمة.
- **يجب كسب ترقية إصدار Minecraft.** يقوم `services/compat.js` بمسح تعديلات الخادم - التي يتم حلها من الصفوف المثبتة باللوحة، ثم بيان حزمة CurseForge، ثم عن طريق تجزئة المحتوى مقابل Modrinth/CurseForge - ويبني مصفوفة دعم (المحمل، إصدار Minecraft) لكل مشروع من `latestFilesIndexes` في CurseForge (200 مشروعًا لكل طلب) وقائمة إصدارات Modrinth لكل مشروع (طلب واحد لكل مشروع، وهو ما يحافظ على اقتران المحمل والإصدار). يقدم مدقق التحديث أحدث إصدار يدعمه كل تعديل فقط، ولا يقدم أي شيء على الإطلاق عندما لا يمكن تحديد الإجابة: لا يوجد مسح، أو مسح لإصدار أو محمل مختلف، أو مسح لم ينتهِ أبدًا، أو ملف jar لا يتعرف عليه أي سجل. عمليات المسح يدوية فقط، وتعيش تقدمها ونتائجها الجزئية في `version_compat` (وليس في `services/tasks.js` في الذاكرة)، لذا فإن التحديث أو إعادة تشغيل اللوحة يستأنف بدلاً من التعليق على مؤشر الدوران؛ يقوم `reconcileScans()` بتمييز عمليات المسح التي تم إيقافها بسبب إيقاف التشغيل عند التمهيد التالي.
- **إصدار محمل التعديل هو تثبيت، مثل أي شيء آخر.** يقرأ `services/loaderPin.js` البناء المثبت من بيان تثبيت الصورة الخاص بها (`.forge-manifest.json` والأصدقاء) ويكتب التثبيت: متغير itzg للمحمل على خادم عادي (`FORGE_VERSION`، …)، أو `CF_MOD_LOADER_VERSION` على حزمة Forge أو Fabric CurseForge، والذي يتجاوز الإصدار الذي تعلنه الحزمة. يتجاهل مثبت CurseForge الخاص بالصورة هذا التجاوز لـ NeoForge، ولا تحتوي حزم Modrinth وFTB على أي تجاوز، لذا يتبع محملها الحزمة. يقوم `packs.applyPack` بتجريد كل متغير `CF_` عند تحديث الحزمة أو التراجع عنها، مما يسقط التجاوز مع البقية. يتم فحص بناء مكتوب مقابل القائمة الكاملة للسجل أولاً (`services/loaderVersions.js`؛ يأتي Forge من بياناته الوصفية maven، والتي تتخطى الأرقام؛ يتم إعادة فحص الفشل مرة واحدة مقابل السجل نفسه)، ثم يتم إجراء التغيير نسخ احتياطي ← تثبيت (فوق البيئة كما هي بعد النسخ الاحتياطي) ← إعادة بناء.
- **المنافذ** يتم تخصيصها من مخطط أساسي (اللعبة من `PORT_GAME_START` صعودًا، RCON = اللعبة + `PORT_RCON_OFFSET`، Bedrock من `PORT_BEDROCK_START`)، ويتم فحصها للتأكد من توفرها، وحجزها في قاعدة البيانات. "المأخوذ" هو اتحاد مطالبات كل خادم (المنافذ المباشرة، بالإضافة إلى زوج معلق أدناه)، وكل منفذ مضيف تنشره أي حاوية Docker (`containers.publishedHostPorts`: ارتباطات الحاويات قيد التشغيل المباشرة بالإضافة إلى المنافذ المكونة لكل حاوية متوقفة، لأن فحص ربط نظام التشغيل من داخل حاوية اللوحة الخاصة بها يرى فقط مساحة اسم شبكة تلك الحاوية)، وفحص نظام التشغيل. يتم تخزين جزء Docker مؤقتًا لمدة 3 ثوانٍ ومحدود: قائمة لا تستجيب في 2.5 ثانية تسقط جزء Docker فقط، ويكلف الفحص البطيء منافذ تلك الحاوية فقط. يقوم إنشاء الخادم و`servers.changeGamePort` باختيار المنافذ من خلال سلسلة تسلسل واحدة تغطي فقط الاختيار والمطالبة به (كتابة الصف لإنشاء، الحجز في الذاكرة لتغيير المنفذ)؛ لا يوجد منتقي منفذ BlueMap وتجاوزات المنافذ الإضافية فيه ولا يستشيران Docker. يتم تطبيق تغيير المنفذ على خادم موجود (`servers.changeGamePort`، تحت قفل عملية الخادم) على الفور، لأن Docker يثبت ارتباطات المنفذ عند إنشاء الحاوية: يتم فحص الزوج الجديد (RCON دائمًا اللعبة + `PORT_RCON_OFFSET`) وحجزه في الذاكرة (`ports.reserve`، كل من الزوج القديم والجديد، يتم احترامهما بواسطة كل اختيار آخر) تحت قفل المنفذ. يتم رفضه (409 `PENDING_CHANGES`) بينما تنتظر الإعدادات الأخرى إعادة البناء، لذا فإنه يعيد بناء حاوية كانت تعمل بالفعل، على منفذ جديد؛ ولا يتم تغيير خادم قيد التشغيل إلا عندما يطلب الطلب `restart: true` (وإلا 409 `NEEDS_CONFIRM`). يتم سحب الصورة ويتم فحص اسم حاوية مخصص قبل لمس أي شيء. يتم إيقاف خادم قيد التشغيل؛ ثم يتم كتابة الزوج الجديد مع `pending_recreate = 1` (لذا فإن تعطل اللوحة من هناك يترك "إعادة بناء معلقة" صادقة)، تتم إزالة الحاوية، وإعادة بنائها على الزوج الجديد وبدء تشغيلها. إذا فشلت أي خطوة بعد الإيقاف، يقوم `putBackOnOldPort` بإعادة كتابة الزوج القديم، وإعادة البناء (وإعادة التشغيل، إذا كانت تعمل) عليه ويسجل الخطوة التي فشلت؛ يخبر التاريخ والتنبيهات إذا فشل ذلك أيضًا، مما يترك الخادم متوقفًا حتى يقوم شخص ما ببدء تشغيله. قدرة `settings` كافية، بما في ذلك الخادم قيد التشغيل. يمكن لغير المسؤولين اختيار فقط من `PORT_GAME_START` صعودًا. (أعمدة `port_*_pending` من الترحيل 029 تنتمي إلى تصميم سابق غير منشور وغير مستخدمة؛ 031 يمسحها.) يجيب تصادم القفل 409 مع `code: 'BUSY'`، والذي يتحقق منه المتصلون الذين يعيدون المحاولة أدناه بدلاً من الصياغة. إعادة التشغيل التلقائي بعد التعطل (`watcher.restartAfterCrash`) والنسخ الاحتياطي المجدول أو البدء (`scheduler.runTaskWithRetry`) التي تجد الخادم مشغولًا بإجراء آخر تحاول مرة أخرى كل 20 ثانية / 60 ثانية لمدة تصل إلى 30 دقيقة، وتحديث الحزمة أو التراجع يعيد محاولة خطواته المقفلة بنفس الطريقة (`opLock.retryWhileBusy`)؛ إعادة تشغيل بعد التعطل أو بدء مجدول ينتظر يتوقف بمجرد أن يقوم شخص ما بإيقاف أو قتل أو بدء تشغيل الخادم منذ ذلك الحين (`events.lifecycleActionSince`)، وإعادة تشغيل بعد التعطل أيضًا عندما يكون إعادة التشغيل التلقائي معطلًا أو الخادم غير موجود. لا يتم إعادة محاولة عمليات إعادة التشغيل والإيقاف والأوامر المجدولة، ويتخطى الجدول الزمني الذي لا يزال تشغيله الأخير ينتظر تشغيله التالي.
- **حصص القرص** يتم فرضها بواسطة اللوحة لأن Docker لا يمكنه تحديد استخدام ربط المجلدات: يقوم الفهرس بتخزين أحجام كل دليل مؤقتًا ويتم حماية عمليات نمو القرص بناءً عليها.
- **الأسرار** (كلمات مرور RCON، مفاتيح API، أسرار TOTP، عنوان URL لـ Discord webhook) يتم تشفيرها في وضع السكون باستخدام AES-256-GCM باستخدام مفتاح عشوائي مخصص في `$DATA_DIR/.secret-key` (الوضع `0600`، يتم إنشاؤه تلقائيًا). إنه مستقل عن `SESSION_SECRET`؛ يتم الاحتفاظ بمفتاح مشتق من `SESSION_SECRET` كخيار احتياطي لفك التشفير فقط للقيم المكتوبة قبل وجود المفتاح المخصص، ويقوم `src/services/secretsMigration.js` بإعادة تشفير تلك القيم تحت المفتاح المخصص مرة واحدة عند التمهيد. `.secret-key` موجود ولكنه لا يمكن تحليله هو خطأ تمهيد صعب (لا يتم إعادة إنشائه بصمت أبدًا). تقوم المخططات بتجريد جميع الأسرار عند التصدير.
- **`server.properties` مملوكة للوحة ولكنها مظللة بالبيئة.** تقوم صورة itzg بإعادة تأكيد كل خاصية مدعومة بالبيئة عند كل بدء تشغيل (`OVERRIDE_SERVER_PROPERTIES` افتراضيًا صحيح)، لذا فإن القيمة التي تعدلها اللوحة مباشرة - PvP/صعوبة World Controls، تبديل القائمة البيضاء، محرر الملفات - سيتم إعادتها بصمت عند البدء التالي ما لم يتم إزالة متغير البيئة المطابق وإعادة إنشاء الحاوية. تمر كل كتابة مباشرة للخاصية عبر `writeServerProperties()` (الملف بأكمله) أو `setServerProperty()` (مفتاح واحد) في `src/services/servers.js`، والتي تعيد كتابة الملف بشكل ذري، وتلغي تعيين متغير البيئة خلف كل مفتاح متغير (عبر السمة `prop:` في حقول الكتالوج، يتم فحصها في الاختبارات مقابل تعريفات خصائص الصورة الخاصة بها)، وتضع علامة `pending_recreate`. يتم كتابة الصعوبة في الملف وكذلك إرسالها عبر RCON، لأن الخادم المخصص يعيد تطبيق خاصية `difficulty` عند كل تمهيد. يقوم Minecraft نفسه بإعادة حفظ server.properties من قيمه وقت التمهيد عند `whitelist on/off`، مما سيلغي التعديلات التي تم إجراؤها أثناء تشغيل الخادم، لذا فإن تبديل القائمة البيضاء قيد التشغيل يلتقط الملف أولاً ويعيد كتابته مع تغيير `white-list` فقط. تظل متغيرات البيئة قابلة للتكوين بالكامل عند الإنشاء (يعرضها المعالج ويتم تطبيقها مرة واحدة)؛ يتم إلغاء تثبيتها فقط في المرة الأولى التي تعدل فيها اللوحة الخاصية الأساسية. MOTD هو نفس العقد: يؤدي التعديل المباشر لملف `motd` إلى إلغاء تعيينه، لذا فإن آخر كتابة تفوز.

## تنسيقات البيانات والأسلاك

- **`data/panel.db`** - قاعدة بيانات SQLite. يتم أخذ لقطة يوميًا عبر `VACUUM INTO` إلى `data/backups/_panel/` (يتم الاحتفاظ بأحدث 14 لقطة)؛ يتم تشغيل `PRAGMA integrity_check` عند التمهيد.
- **`data/.session-secret`** - سر توقيع ملف تعريف الارتباط الذي يتم إنشاؤه تلقائيًا، يتم إنشاؤه عند التشغيل الأول إذا لم يتم تعيين `SESSION_SECRET`. يؤدي حذفه إلى تدوير السر (مما يبطل الجلسات).
- **`data/.secret-key`** - مفتاح التشفير المخصص 32 بايت في وضع السكون (الوضع `0600`)، يتم إنشاؤه تلقائيًا عند التشغيل الأول. مستقل عن `SESSION_SECRET`؛ يؤدي حذفه إلى جعل كل بيانات اعتماد مخزنة غير قابلة للفك، لذا فهو ينتمي إلى نسخك الاحتياطية.
- **المخططات (`.mcserver.zip`)** - ملف مضغوط يحتوي على `manifest.json` يصف التكوين والموارد ومرجع الحزمة المثبتة وبيان التراكب (عناوين URL المصدر + sha256) وملفات التكوين المختارة، واختياريًا عالم. يقوم الاستيراد بإعادة تنزيل كل تعديل والتحقق من تجزئته وتعيين منافذ جديدة.
- **حاويات Docker** التي تم إنشاؤها بواسطة اللوحة يتم تسميتها وتصنيفها بحيث يمكن للمراقب العثور عليها؛ تمتلك اللوحة دورة حياتها الكاملة.

## تسلسل التمهيد

1. `require('./instrument')` (وصلة Sentry) قبل أي شيء آخر، ثم `require('./preflight')` للفشل بوضوح عند إصدار Node غير مدعوم.
2. تحميل التكوين؛ التأكد من/إنشاء `.session-secret` **و** `.secret-key`.
3. `ensureDataRoot()` - إنشاء تخطيط `./data`، مسح `tmp/`.
4. تشغيل ترحيلات قاعدة البيانات، ثم `PRAGMA integrity_check` (يسجل بصوت عالٍ، ويشير إلى `data/backups/_panel` عند الفشل).
5. إعادة تشفير أي أسرار قديمة مفتاحها `SESSION_SECRET` تحت `.secret-key` (`secretsMigration`).
6. استيراد مفاتيح API من البيئة مرة واحدة (`apiKeys.importFromEnvOnce()`)، تثبيت أي خادم لا يزال يحمل محدد حزمة تعديل غير مثبت (`packPins.pinUnpinnedServers()`)، وضع علامة على عمليات مسح توافق الإصدار التي تركت قيد التشغيل بواسطة عملية سابقة على أنها مقاطعة (`compat.reconcileScans()`)، ثم بذر المخططات الأولية (محمية).
7. بدء تشغيل خادم HTTP + WS. عند ربط مكشوف، اطبع رقم التعريف الشخصي `/setup` للتشغيل الأول.
8. تثبيت حارس وقت التشغيل بعد التمهيد (يلتقط الأخطاء غير المعالجة؛ `MSM_EXIT_ON_FATAL=1` يجعله يخرج بقوة للنشر تحت الإشراف).
9. بدء تشغيل الخدمات الخلفية: وسيط WS، مفهرس التخزين، مراقبو الأعطال والمخزون، المجدول، جسر أحداث Discord، مراقب التواصل مع الروبوتات، و**مؤقت الصيانة اليومي** (تقليم صفوف التحليلات القديمة، نصوص الروبوتات، سجل الأحداث (365 يومًا) وصفوف ذاكرة التخزين المؤقت لواجهة برمجة التطبيقات، ثم أخذ لقطة لـ `panel.db`).
10. تهيئة Docker **في الخلفية**. واجهة المستخدم قابلة للاستخدام بالكامل بينما يكون daemon معطلاً؛ تضيء ميزات Docker عندما يصبح قابلاً للوصول. بمجرد الاتصال، يقوم `refreshStatuses({ boot })` بتسوية الحالات المخزنة مؤقتًا، ويصدر حدث `offline-after-restart` لمرة واحدة لخادم كان يعمل قبل إعادة تشغيل اللوحة ولن يتم إعادته، وتبدأ حلقة التمهيد خوادم `auto_start` بالإضافة إلى استعادة خوادم `auto_restart` التي تم العثور عليها معطلة أثناء الانقطاع (مع احترام التراجع عن حلقة التعطل).

> ترتيب instrument-before-preflight هو مقايضة متعمدة: يسمح لربط Sentry المستقبلي بتصحيح وقت التشغيل أولاً، على حساب رسالة أقل ودية قليلاً على Node قديم حقًا.

## خط أنابيب البناء

`pnpm run build` = `build:css` (Tailwind → `public/css/app.css`) + `build:js` (esbuild → `public/dist/js/`، ESM مع تقسيم التعليمات البرمجية). `postinstall` يشغل **CSS فقط**. `public/css/app.css` و`public/dist/` هي عناصر بناء يتم تجاهلها بواسطة Git؛ تقوم مرحلة بناء Dockerfile بتشغيل `pnpm run build` بالكامل وتنسخ `public/` إلى صورة وقت التشغيل. يتم تقديم الأصول الثابتة `immutable`/ذاكرة تخزين مؤقت طويلة للملفات ذات البصمة، وذاكرة تخزين مؤقت قصيرة لـ CSS/JS، و`no-cache` لـ HTML و`/api`.
