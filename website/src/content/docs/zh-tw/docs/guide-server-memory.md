簡短回答，對於實際遊玩的伺服器：

| 您正在執行的伺服器類型               | Java 堆積記憶體 | 分配給機器的記憶體 |
| ------------------------------------ | --------------- | ------------------ |
| Vanilla 或 Paper，最多 10 位玩家     | 2 GB            | 4 GB               |
| 裝有插件的 Paper，10 至 30 位玩家    | 4 GB            | 6 GB               |
| 輕量級模組包，40 至 80 個模組        | 4 GB            | 6 GB               |
| 大型綜合模組包，150 至 300 個模組    | 6 至 8 GB       | 10 GB              |
| GregTech New Horizons 及類似的怪物包 | 8 至 12 GB      | 16 GB              |

兩個數字，不是一個。這是大多數指南都會跳過的部分，也是人們購買 4 GB
伺服器，分配 4 GB 給 Java，然後看著它崩潰的原因。

## 堆積記憶體與機器記憶體是不同的數字

Java 堆積記憶體 (`-Xmx`) 是遊戲本身可供世界、實體和模組資料使用的記憶體量。機器或容器必須容納該堆積記憶體**加上** Java 所需的所有其他內容：類別元資料、執行緒堆疊、垃圾回收器記錄、網路緩衝區以及 JVM 本身。對於裝有模組的伺服器，這些額外開銷大約是 0.5 至 1.5 GB。

如果堆積記憶體等於機器的記憶體，當 Java 嘗試使用這些額外開銷時，核心就會終止伺服器。在 Docker 中，這會顯示為退出代碼 137，在日誌中則完全沒有記錄：該程序會在句子中間消失。人們通常會歸咎於某個模組。

一個安全的規則是：**堆積記憶體加上 25%，並且至少保留一 GB 的備用空間。** 8 GB 的堆積記憶體需要 10 GB 的機器。

## 更多 RAM 不等於更高效能

Minecraft 在其大部分操作中都受限於單一執行緒。為一個擁有 40 個模組的伺服器分配 16 GB 記憶體並不會讓區塊生成得更快；它只會讓每次垃圾回收的暫停時間更長，因為需要處理的內容更多。一個每隔三十秒就會卡頓的伺服器，通常是因為堆積記憶體過多，而不是過少。

當您看到以下情況時才應增加堆積記憶體，否則不必：

- 日誌中出現 `java.lang.OutOfMemoryError: Java heap space`。
- 計時器中出現反覆的「無法跟上！伺服器是否過載？」以及垃圾回收暫停。
- 記憶體使用量爬升到上限並數小時保持在那裡。

## 為什麼您的伺服器在沒有人上線時顯示使用了 12 GB

因為您這樣設定了。兩個預設值共同作用：

1. 常見的 Docker 映像檔將起始堆積記憶體設定為等於最大值，因此 `-Xms` 和 `-Xmx` 都是您的設定值。Java 會預先佔用它，而不是逐漸增加。
2. 流行的 Aikar 標誌集包含 `-XX:+AlwaysPreTouch`，它會在啟動時遍歷該堆積記憶體的每一頁，以便真正分配這些頁面。這是故意的：它以較慢的啟動時間和較高的閒置記憶體佔用量為代價，來換取後續更少的暫停。

在 Paper 1.21.1 上，使用 2 GB 堆積記憶體和 4 GB 容器進行測試，在世界載入完成後取樣三分鐘：

| 設定                                    | 常駐記憶體 |
| --------------------------------------- | ---------- |
| 無標誌                                  | 2.60 GiB   |
| Aikar 標誌                              | 2.59 GiB   |
| 移除 `AlwaysPreTouch` 的 Aikar 標誌     | 1.95 GiB   |
| 具有 512 MB 起始堆積記憶體的 Aikar 標誌 | 1.38 GiB   |
| 無標誌且具有 512 MB 起始堆積記憶體      | 1.25 GiB   |

因此，一個閒置時「使用」12 GB 的伺服器通常是預先觸碰過的 12 GB 堆積記憶體，而不是記憶體洩漏。您的監控程式讀取的數字是正確的；只是這個數字的意義並不像看起來那樣。

如果您想要一個準確的閒置記憶體數字，請將起始堆積記憶體設定得低於最大值。您需要為此付出一些代價，在早期會有更多的垃圾回收。如果您寧願擁有穩定的幀時間，那就保持原樣，不要再關注那個圖表了。

## 玩家數量的影響比您想像的要小

玩家數量從 10 位增加到 20 位所花費的成本，遠低於增加 50 個模組。玩家主要增加實體和載入的區塊，這些的擴展是平緩的。模組則會增加類別資料、登錄檔、世界生成功能以及它們自己的快取，這些的擴展並非平緩。首先考慮模組包的大小，然後為每個普通玩家增加約 100 到 200 MB 的記憶體。

視距是另一個重要的影響因素。將視距從 12 個區塊降至 8 個區塊，可以在繁忙的伺服器上節省一 GB 的記憶體，而且在遊戲中幾乎察覺不到。

## 在 Minecraft Server Manager 中

每個伺服器都有兩個獨立的欄位：**Java 堆積記憶體**和**容器記憶體限制**，這正是因為它們是不同的問題。建立精靈會為您將容器限制設定為比堆積記憶體高 50%，並且面板會拒絕儲存容器限制低於其堆積記憶體的伺服器，因為這種組合會導致退出代碼 137 而不是錯誤訊息。

伺服器上的記憶體計量器顯示容器實際使用的記憶體量，並在堆積記憶體被預先佔用時進行提示，因此預先觸碰過的堆積記憶體不會被誤判為失控。被核心因記憶體不足而終止的伺服器，會在歷史記錄中準確記錄為該情況，而不是作為一個神秘的崩潰。
