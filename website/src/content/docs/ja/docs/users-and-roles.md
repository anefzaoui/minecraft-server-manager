このパネルはマルチユーザーに対応しています。アカウントの管理は **設定 → ユーザー** から行えます。

![ユーザー](/docs/images/settings-users.png)

## 3つのロール

| ロール       | すべてのサーバーでのデフォルト権限                                                                                         |
| ------------ | -------------------------------------------------------------------------------------------------------------------------- |
| **admin**    | すべて：ユーザー管理、APIキー、グローバルファイル、高度なDockerオーバーライド、およびすべてのサーバー操作。                |
| **operator** | サーバーの実行と設定（起動/停止、コンソール、バックアップ、ワールド、MOD、ほとんどの設定）、ただし管理者専用エリアは不可。 |
| **viewer**   | 読み取り専用。サーバーとそのステータスの閲覧のみ可能で、変更は不可。                                                       |

すべてのユーザー（viewerを含む）は、自身の [二要素認証](/docs/two-factor-authentication/) を管理できます。自身のログインを保護することは、サーバー管理操作には含まれないためです。

ロールはすべてのサーバーに対する**デフォルト**権限です。特定のサーバーで異なる権限を与えたい場合は、以下のサーバーごとの権限設定を使用してください。

## サーバーごとの権限

**権限**ページ（サイドバー、または **設定 → ユーザー** 内の **サーバー権限**）にはグリッドが表示されます。縦軸にすべてのoperatorとviewer、横軸にすべてのサーバーが並んでいます。セルをクリックすることで、そのユーザーがそのサーバーに対して何を行えるかを決定できます。adminは常にすべての権限を持っているため、ここには表示されません。

![権限](/docs/images/settings-permissions.png)

各セルは以下の権限セットで構成されています：

| 権限         | そのサーバーで許可される操作                                                                                                 |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| **View**     | サーバー、ステータス、コンソール出力、プレイヤー、履歴、統計の閲覧。                                                         |
| **Power**    | サーバーの起動、停止、再起動、強制終了、再構築。                                                                             |
| **Console**  | コンソールコマンドの実行、ワールドのクイック操作、チャット送信、チャットコマンドの管理。                                     |
| **Players**  | プレイヤーのキック、BAN、ホワイトリスト登録、OP権限付与、メモの編集。                                                        |
| **Content**  | MOD、プラグイン、パック、ワールド、データパックのインストールと削除、インベントリの編集。                                    |
| **Backups**  | バックアップの作成、復元、ダウンロード、削除。                                                                               |
| **Files**    | サーバーファイル、アーカイブされたログ、ログバンドルの閲覧、編集、アップロード、ダウンロード、ブループリントのエクスポート。 |
| **Settings** | サーバー設定、プロパティ、統合、アイコンの変更、バージョンのアップグレード。                                                 |
| **Delete**   | サーバーの削除。                                                                                                             |

![権限エディター](/docs/images/permissions-editor.png)

グリッドの下にある **各権限の対象範囲** を開くと、各権限で何ができるか、何が含まれないか、そしてどのパネルルートが解放されるかが詳細に表示されます。このリストは、テストスイートによって実行中のコードと照合されます。

![権限リファレンス](/docs/images/permissions-reference.png)

スマートフォンでは、グリッドはユーザーごとに1枚のカードとしてスタックされ、サーバーごとに1行ずつ表示されます。

仕組みの概要：

- **ロールがデフォルトとなります。** operatorはすべてのサーバーですべての権限を持って開始し、viewerはViewのみで開始します。薄い文字のセル（ツールチップに「ロールのデフォルト」と表示されます）は、まだ変更されていないことを示します。
- **セルは、そのサーバーのみロール設定を上書きします。** あるサーバーでviewerにPowerとConsoleを与えればそのサーバーを操作できますが、他のすべてのサーバーは読み取り専用のままです。メインサーバーでoperatorからDelete権限を剥奪しても、他の権限は維持されます。
- **すべての権限にはViewが含まれます。** 見ることができないサーバーを操作することはできません。
- **すべての権限をオフにすると、サーバーを非表示にできます。** サイドバー、ダッシュボード、バックアップ、スケジュール、アクティビティ、アップデート、MODパック、ライブステータス、実行中のタスク、ブループリントからサーバーが消え、ワールドライブラリにも表示されなくなります。直接リンク、API呼び出し、コンソールソケットに対しては、存在しないサーバーと同様に「見つかりません」と返されます。
- **パネル全体の操作は引き続きロールに従います。** サーバーの作成（クローンを含む）、ストレージ、ユーザー、APIキー、グローバル設定、パネル全体のスケジュールはサーバーごとの設定ではないため、特定のサーバーに権限を持つviewerであってもこれらを実行することはできません。サーバー作成とパネル全体のスケジュールはoperatorが保持し、ストレージ、ユーザー、APIキー、グローバル設定はadmin専用です。
- **スケジュールはサーバーに従います。** サーバーのスケジュールされた再起動、バックアップ、コマンドには、ロールに関係なく、そのサーバーでの対応する権限（Power、Backups、またはConsole）が必要です。
- **ブループリントもサーバーに従います。** サーバーをブループリントとしてエクスポートするには、そのサーバーでのFiles権限が必要です。アーカイブにはファイルが含まれるためです。誰かが閲覧できないサーバーからエクスポートされたブループリントは、そのユーザーからも隠されます。
- **admin専用エリアはすべてのサーバーでadmin専用です。** チャットボット、バックアップの保持期間、高度なDockerオーバーライドが該当します。

すべての変更は、誰が何を変更したかという情報とともにアクティビティログに書き込まれます。これらのエントリはadminのみが閲覧可能です。ユーザーを削除するとそのユーザーの行は削除されます。サーバーを削除しても履歴は残るため、誰かから隠されていたサーバーは、履歴や保持されているバックアップ内でも隠されたままになります。

既存のインストール環境はそのまま動作します。adminがセルを編集するまで、各ユーザーはロールによって与えられた権限をそのまま保持します。

## admin専用の理由

いくつかの機能は、意図的にadminのみに制限されています：

- **ユーザー管理、ストレージ、グローバル設定、APIキー、グローバルファイル。**
- **[パブリックAPI](/docs/public-api/)**: `/api/v1` の有効化、および読み取り専用Bearerトークンの作成、スコープ設定、取り消し。
- **高度なDockerオーバーライド**: コンテナ名のカスタマイズ、追加のポート公開、バインドマウント。バインドマウントはホストの任意のパスをコンテナにマッピングできるため、パネルのDockerアクセス権と組み合わせると、実質的にホストのroot権限を持つことになります。これらのフィールドはadminにのみ表示されます。

また、カスタムコンテナ名はパネル自身の `msm-` 名前空間を使用できないため、手動で命名されたコンテナが他のサーバーのコンテナを隠蔽し、停止やコマンドを誤ったインスタンスに送信してしまうことはありません。

## アカウントの管理

![プロフィール画像](/docs/images/profile-picture.png)

adminは「ユーザー」テーブルから、ユーザーの作成、ロールの変更、パスワードのリセット、アカウントの削除を行えます。**2FA**列には各ユーザーの二要素認証の有効状況が表示されます。adminはユーザーのアクションメニューにある **2FAをリセット** から他ユーザーの2FAをリセットできます（紛失時などの対応）。ただし、自身の2FAをパスワードなしで無効化することはできず、セルフサービスフローで行う必要があります。

ログイン失敗はアカウントごとにレート制限されます（IPごとおよびアカウント全体の両方でカウント）。これによりブルートフォース攻撃を遅延させます。同じ制限が2FAコードの入力ステップにも適用されるため、正しいパスワードを入力しても、コードを推測する前にカウントをリセットすることはできません。その手前には、ログイン/2FA/セットアップのエンドポイントに対して、クライアントIPごとのより広範なリクエスト制限が設けられています。これは `RATE_LIMIT_AUTH_PER_15MIN` で調整可能です（デフォルトは100。リバースプロキシ配下の場合は `TRUST_PROXY` を設定して実際のクライアントIPを判定できるようにしてください）。
