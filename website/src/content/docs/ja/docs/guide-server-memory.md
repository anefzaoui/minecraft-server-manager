簡単な目安です。実際にプレイするサーバーの場合：

| 実行しているもの                             | Javaヒープ | マシンに割り当てるメモリ |
| -------------------------------------------- | ---------- | ------------------------ |
| Vanilla または Paper、最大10プレイヤー       | 2 GB       | 4 GB                     |
| プラグイン入り Paper、10〜30プレイヤー       | 4 GB       | 6 GB                     |
| 軽量MODパック、40〜80個のMOD                 | 4 GB       | 6 GB                     |
| 大規模なMODパック、150〜300個のMOD           | 6〜8 GB    | 10 GB                    |
| GregTech New Horizons およびそれに類するもの | 8〜12 GB   | 16 GB                    |

1つの数字ではなく2つの数字です。多くのガイドが省略している部分であり、人々が4 GBのサーバーを購入し、Javaに4 GBを割り当てて、サーバーがクラッシュする原因となっています。

## ヒープとマシンメモリは異なる数字です

Javaヒープ (`-Xmx`) は、ゲーム自体がワールド、エンティティ、MODデータを格納するために使用できるメモリ量です。マシン、つまりコンテナは、そのヒープ **に加えて** Javaが必要とするすべてのもの（クラスメタデータ、スレッドスタック、ガベージコレクタの管理、ネットワークバッファ、JVM自体）を保持する必要があります。MODが多数入ったサーバーの場合、このオーバーヘッドは約0.5〜1.5 GBです。

ヒープメモリがマシンのメモリ量と等しい場合、Javaがオーバーヘッドにアクセスした瞬間にカーネルがサーバーを強制終了します。Dockerでは、これは終了コード137として表示され、ログには何も表示されません。プロセスは単純に途中で消滅します。通常、MODのせいだと考えられます。

安全なルール：**ヒープメモリに25%を追加し、最低でも1 GBの空きメモリを確保してください。** 8 GBのヒープメモリには10 GBのマシンメモリが必要です。

## RAMが多いほどパフォーマンスが向上するわけではありません

Minecraftのほとんどの処理はシングルスレッドに依存しています。40個のMODが入ったパックに16 GBを割り当てても、チャンクの生成が速くなるわけではありません。むしろ、ガベージコレクションの停止時間が長くなります。30秒ごとにカクつくサーバーは、メモリ不足ではなく、ヒープメモリが多すぎる場合が多いです。

以下の状況が発生した場合にのみ、ヒープメモリを増やしてください。

- ログに `java.lang.OutOfMemoryError: Java heap space` が表示される。
- タイミングログでガベージコレクションの停止を伴う「追いつけません！サーバーは過負荷ですか？」が繰り返し表示される。
- メモリ使用量が上限に達し、数時間そのままの状態が続く。

## 誰もオンラインでないのに、サーバーが12 GB使用中と表示される理由

あなたがそう設定したからです。一般的な2つのデフォルト設定が原因です。

1.  一般的なDockerイメージは、開始ヒープと最大ヒープを同じ値に設定するため、`-Xms` と `-Xmx` が両方とも指定した値になります。Javaは、メモリを徐々に増やすのではなく、最初から確保します。
2.  広く使われているAikarのフラグセットには`-XX:+AlwaysPreTouch`が含まれており、これは起動時にヒープのすべてのページをウォークして、ページが実際に割り当てられるようにします。これは意図的なもので、起動時間は遅くなりますが、アイドル時のメモリ使用量は多くなりますが、後での停止時間は短くなります。

Paper 1.21.1で2 GBのヒープメモリを4 GBのコンテナで実行し、ワールドのロード完了後3分間サンプリングした場合の測定結果：

| 設定                                      | 常駐メモリ |
| ----------------------------------------- | ---------- |
| フラグなし                                | 2.60 GiB   |
| Aikarフラグ                               | 2.59 GiB   |
| `AlwaysPreTouch` なしのAikarフラグ        | 1.95 GiB   |
| 512 MBの開始ヒープメモリを持つAikarフラグ | 1.38 GiB   |
| 512 MBの開始ヒープメモリを持つフラグなし  | 1.25 GiB   |

したがって、アイドル時に12 GBを「使用」しているサーバーは、実際にはプリタッチされた12 GBのヒープメモリであり、メモリリークではありません。監視ツールは正しく読み取っていますが、その数字は見た目通りの意味ではありません。

正確なアイドル時のメモリ使用量を知りたい場合は、開始ヒープメモリを最大値よりも低く設定してください。これにより、初期のガベージコレクションが増加しますが、その分メモリ使用量は少なくなります。フレームタイムの安定性を優先する場合は、そのままにしてグラフの監視をやめてください。

## プレイヤー数は思ったほど重要ではありません

プレイヤー数が10人から20人に倍増しても、MODを50個追加するよりもはるかにコストがかかりません。プレイヤーは主にエンティティとロードされたチャンクを追加しますが、これらは緩やかにスケールします。MODはクラスデータ、レジストリ、ワールド生成機能、およびそれ自身のキャッシュを追加しますが、これらはそうではありません。まずMODパックのサイズに合わせてメモリを割り当て、その後、MOD入りサーバーではプレイヤー1人あたり約100〜200 MBを追加してください。

描画距離ももう一つの重要な要素です。描画距離を12チャンクから8チャンクに減らすと、賑やかなサーバーでは1 GB節約でき、プレイ中の体感差はほとんどありません。

## Minecraft Server Manager では

各サーバーには、**Javaヒープ**と**コンテナメモリ制限**という2つの別々のフィールドがあります。これは、それらが異なるものであるためです。作成ウィザードでは、コンテナ制限をヒープメモリの50%増しで自動設定します。また、パネルはコンテナ制限がヒープメモリを下回るサーバーの保存を拒否します。なぜなら、その組み合わせはエラーメッセージではなく、終了コード137につながるからです。

サーバーのメモリメーターは、コンテナが実際に使用しているメモリ量を示し、ヒープメモリが事前に確保された場合はその旨が表示されるため、プリタッチされたヒープメモリが暴走しているように見えません。メモリ不足でカーネルによって強制終了されたサーバーは、履歴に謎のクラッシュではなく、そのように正確に記録されます。
