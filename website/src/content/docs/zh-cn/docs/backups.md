**备份**页面显示您所有服务器的快照，包含大小、原因和时长，并可按服务器和原因进行筛选。

![Backups](/docs/images/backups.png)

## 创建备份

您可以从服务器的**备份**选项卡（或通过[计划任务](/docs/schedules/)）一键快照整个服务器目录。面板会先使世界静止（`save-off` → `save-all`），然后压缩数据，最后重新启用保存（`save-on`），因此即使在运行中的服务器上，备份也是一致的。压缩在后台工作线程中运行，不会阻塞面板。通过 API 启动的备份可以附带备注。

每个存档在写入的瞬间都会进行**完整性检查**：面板会重新打开 zip 文件并读取其目录。损坏或无法打开的存档将被删除，备份操作会立即失败，而不是在数月后需要恢复时才发现问题。零条目的存档（从未启动过的服务器）是允许的，但会在事件中标记出来。

勾选**“同时缩小世界”**（在备份选项卡或备份计划任务中）可在存档安全写入后移除不常访问的区块（参见**[缩小世界](/docs/world-shrink/)**）。缩小操作仅在服务器停止时运行；在运行中的服务器上，备份仍会进行，而缩小操作将被跳过。

![Server backups](/docs/images/server-backups.png)

## 备份原因

备份会根据其创建原因进行标记：

- **手动**：您点击了**立即备份**。用库中的世界替换服务器的活动世界时，也会先进行一次`manual`备份。
- **计划任务**：由[计划任务](/docs/schedules/)创建。每台新服务器还会自动生成一个每日计划备份（在凌晨 02:00 至 05:59 之间错开进行），因此服务器从第一天起就具有自动覆盖，而不仅仅是在更新前。
- **更新前**：在包升级或 Minecraft 版本更改之前自动进行，因此升级总是可逆的。
- **恢复前**：在恢复或重置世界之前自动进行，作为安全网，以防恢复结果不符合预期。

## 保留策略

保留策略**按服务器、按原因**进行限制：每个组中保留最新的，旧的在每次成功备份后自动修剪：

| 原因     | 默认保留数量 |
| -------- | ------------ |
| 计划任务 | 10           |
| 更新前   | 10           |
| 手动     | 20           |
| 恢复前   | 5            |

`pre-restore`（在面板中称为安全备份）有其自己的小存储空间，正是为了防止自动安全备份覆盖您刻意保留的`manual`备份。

除了按原因限制外，还有两个可选的全局限制，均默认关闭：**最大年龄**（无论原因如何，超过 N 天的备份将被修剪）和**每个服务器的最大总大小**（将修剪最旧的备份直到总大小符合要求：优先修剪安全备份，然后是计划任务备份，最后是其余备份）。服务器的最新备份永远不会被这两种限制修剪。

### 修改保留策略

管理员在**设置**页面的**备份保留策略**卡片中设置全局策略（**填充内置值**会将上述默认值重新填入表单，准备保存）。服务器可以在任何六个值上有所不同：打开其**备份**选项卡并展开**此服务器的保留策略**。除非该服务器设置了某个值，否则该字段为空，空白字段将遵循全局值（显示在字段内）。因此，服务器可以例如保留 3 个计划任务备份，而其他所有设置都使用全局值；清除一个字段会使其恢复到全局值。

![The Backup Retention card in Settings](/docs/images/settings-retention.png)

![Retention for This Server on a server's Backups tab](/docs/images/server-retention.png)

保存操作本身不会删除任何内容。如果新限制会导致现有备份超出数量，面板将按服务器列出将要删除的备份数量、释放的空间以及最旧备份的年龄。它还会说明服务器在本次更改之前是否已经超出其限制（例如，在之前的**从下次备份开始**之后），因为立即应用会修剪所有超出限制的内容，而不仅仅是本次编辑添加的内容。然后，它会询问如何应用这些限制：

- **立即删除**：精确删除刚刚列出的备份，不多也不少：在此期间创建的备份将等待下次修剪。在设置页面，正在进行恢复、备份或类似操作的服务器将被跳过，并在其下次备份后进行修剪；在服务器自己的备份选项卡上，您将被要求在操作完成后重试。在删除服务器的旧备份时（通常需要几秒钟），该服务器上的其他操作必须等待：计划的备份或启动操作会尝试每分钟重试一次，直到成功（最多 30 分钟），崩溃的服务器会在完成约 20 秒后重启（最多 30 分钟），而计划的重启或停止操作如果在此期间发生，将被推迟到下一个时间点。
- **从下次备份开始**：暂时保留它们；每个服务器将在下次创建备份时像往常一样修剪其备份。

![The dialog listing what new limits would remove](/docs/images/retention-preview.png)

正在恢复的备份在恢复期间永远不会被删除：保留策略会忽略它（并且不会删除其他备份来为其腾出空间），并且在恢复完成之前，手动删除它会被拒绝。

相同的设置也可通过脚本作为管理员 API 端点访问：`GET`/`POST /api/backups/retention` 和 `/api/servers/:id/backups/retention`。全局值不能为 `null`。对于服务器，值为 `null`（或 `""`）会移除该特定键，使其再次遵循全局值，而 `{ "reset": true }` 会移除所有这些键。在这两个路径下，`POST …/preview` 会报告更改将删除什么而不实际删除（返回 `backups`、`bytes`、`servers` 和按服务器的 `byServer` 细分），`POST …/apply` 会立即应用保存的策略并返回全局范围的 `{ deleted, skipped }`（`skipped` 计算繁忙的服务器）或单个服务器的 `{ deleted }`。发送预览的 `{ "token": "..." }`（保留 10 分钟）或其 `{ "ids": [...] }` 来仅删除这些；如果没有两者，则删除所有超出限制的内容。对繁忙服务器执行的单服务器应用操作会返回 409。

备份可以从备份列表中**重命名**（每行的重命名按钮）。磁盘上的存档和面板的记录会一起移动，因此下载、恢复和保留策略都能在新名称下正常工作。

![Rename a backup](/docs/images/backup-rename.png)

> 保留策略会自动限制数量，但大型模组存档仍会计入服务器的[磁盘配额](/docs/storage/)，因此请留意大型包的总大小。

## 恢复

恢复备份会停止服务器（在操作文件前验证容器是否确实已停止），进行一次`pre-restore`安全备份，将**整个服务器目录**替换为快照，然后保持服务器停止状态供您重新启动。存档会先解压到旁边，直到完全解压后才进行替换，因此部分失败的恢复操作不会影响当前文件。由于包升级总是先进行`pre-update`备份，因此您总是可以回滚错误的升级。

## 面板自身的数据库

服务器备份仅涵盖服务器自身文件夹。面板自身的数据库（`panel.db`，包含用户、角色、2FA 密钥、计划任务、包固定和历史记录）会在每日维护定时器中单独进行快照：

- `VACUUM INTO` 将一致的、碎片整理后的副本写入数据文件夹中的 `backups/_panel/`；保留最新的 **14** 个。
- 启动时，面板会运行 `PRAGMA integrity_check`，如果失败会发出响亮的日志，并指向 `backups/_panel` 以获取最新的良好副本。

备份整个数据文件夹（其中还包含 `.secret-key`，即静态加密密钥），就相当于备份了所有内容。
