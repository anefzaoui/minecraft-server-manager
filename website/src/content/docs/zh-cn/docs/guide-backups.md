大多数服务器都有备份。但真正能用的备份却少之又少，而两者的区别往往只会在最糟糕的那一天才显现出来。它们之间的区别在于三点：备份是**一致的**，它**存储在别处**，并且**有人至少测试过一次恢复**。

## 复制未写入的世界

运行中的服务器会持续写入区域文件。如果在写入过程中复制它们，你将得到一个半新半旧的文件，这个文件要么无法加载，要么加载后会发现某个玩家的基地凭空消失了。而且没有任何警告，因为复制本身是成功的。

有两种正确的方法可以进行复制：

1.  **停止服务器**，复制，然后重新启动。简单、直接，但因为停机时间而不受欢迎。
2.  **先让游戏停止写入**。运行 `save-off`，然后运行 `save-all flush`，等待其完成，进行复制，然后运行 `save-on`。在复制期间，世界是完整且静止的。

绝不要跳过前面的步骤直接复制。文件系统或卷级别的快照只有在真正原子化的情况下才有用，而玩家放置方块时进行的 `cp -r` 操作则不是。

## 备份的内容不止世界

仅恢复世界只会得到地形，而服务器本身却丢失了。你还需要：

- `server.properties`，以及其他任何设置规则的文件。
- 模组或插件的 jar 文件，必须是运行时的确切版本。没有创建了其方块的模组，世界将无法加载。
- 玩家数据，包括 `whitelist.json`、`ops.json` 以及统计信息和进度文件夹。
- 如果来自整合包，则需要整合包的版本。记录下来也算。

对任何备份进行快速的健全性检查：你能仅凭存档重建这个服务器吗？如果答案需要一个以“然后我将重新安装”开头的句子，那么它就不是一个完整的备份。

## 存储在同一磁盘上的一个副本不是备份

保护它所在的机器上的备份只能应对一种故障：你删除了某些东西。它无法应对磁盘损坏、服务提供商暂停账户，或导致整个目录被删除的错误。

保持简单而不是追求完美：

- 一个本地副本，用于处理常见情况，例如有人破坏或糟糕的更新。
- 一个存储在别处的副本。可以是另一台机器、对象存储，或者通过 SSH 每晚拉取的家庭 NAS。
- 足够的历史记录，以应对你没有立即注意到的问题。损坏通常在几天后才被发现，如果你只保留三天的备份，你可能已经覆盖了好的那个。

七个每日备份加上四个每周备份，几乎可以应对所有实际的事件，而且成本非常低。

## 在需要之前测试恢复

选择一个备份，将其恢复到一个备用服务器，然后加入游戏。这就是整个测试过程，只需要十五分钟，并且可以发现所有常见的故障：存档丢失了模组文件夹、世界需要一个你不再运行的版本、权限导致文件无法读取、上传损坏。

在设置备份时进行一次，在服务器进行任何重大更改后再次进行。

## 大小，以及如何保持合理

世界会因为玩家的探索而增长。一个玩家直线飞行了十万格的世界，会永远携带沿途的每一个区块，而其中大多数区块将永远不会被再次访问。

有三个方法，按收益大小排序：

1.  **修剪未访问的区块**。通常通过最后访问时间来修剪的工具，可以移除大量已充分探索的世界的区块，而不会对游戏产生可见的影响。
2.  **正确压缩**。区域文件本身压缩效果很好；对它们的存档进行额外的压缩收益不大。
3.  **不要一年都保留每一个小时的副本**。保留比压缩更重要。

## 在 Minecraft Server Manager 中

备份会采用 `save-off`、flush、复制、`save-on` 的流程，并且在备份过程中请求停止或重启会被拒绝，直到复制完成为止，而不是与之竞争。存档会覆盖整个服务器目录，因此模组、配置和玩家数据会随世界一起迁移。

备份可以与重启和命令一起按计划运行，并且每个新服务器都默认启用每日备份计划。保留策略会分开计算每种类型的备份，因此自动累积的十个计划内备份不会覆盖你在进行风险更改前手动创建的那个备份，并且在此之上还会有年龄和大小限制。管理员可以在“设置”页面或服务器的“备份”选项卡中更改所有这些设置。恢复操作会先创建一个新的备份，因此恢复到错误的时间点本身是可以撤销的。世界可以单独缩小，也可以作为备份的一部分进行缩小，这是对大小影响最大的控制手段。

整个面板，包括每一个备份，都位于一个目录下。将该目录复制到别处是离线备份的一半，而且它故意是唯一需要复制的东西。
