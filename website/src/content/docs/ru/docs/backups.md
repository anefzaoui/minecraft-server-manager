Страница **Резервные копии** отображает все снимки состояния вашей инфраструктуры с указанием размера, причины создания и возраста, с возможностью фильтрации по серверу и причине.

![Резервные копии](/docs/images/backups.png)

## Создание резервной копии

На вкладке **Резервные копии** сервера (или через [расписание](/docs/schedules/)) вы можете создать снимок всего каталога сервера одним кликом. Панель сначала приостанавливает мир (`save-off` → `save-all`), архивирует данные, а затем снова включает сохранение (`save-on`), поэтому резервные копии остаются согласованными даже на работающем сервере. Сжатие выполняется в фоновом потоке, чтобы не блокировать панель. Резервная копия, созданная через API, может содержать примечание.

Каждый архив **проверяется на целостность** в момент записи: панель повторно открывает zip-архив и читает его содержимое. Поврежденный или не открывающийся архив удаляется, и запрос на создание резервной копии завершается ошибкой немедленно, а не через месяцы, когда проблема проявится при попытке восстановления. Архив с нулевым количеством записей (сервер, который никогда не запускался) допускается, но помечается в журнале событий.

Установите флажок **"Также сжать мир после этого"** (на вкладке "Резервные копии" или в расписании резервного копирования), чтобы удалить редко посещаемые чанки после безопасной записи архива (см. **[Сжатие мира](/docs/world-shrink/)**). Сжатие выполняется только при остановленном сервере; на работающем сервере резервная копия все равно создается, а сжатие пропускается.

![Резервные копии сервера](/docs/images/server-backups.png)

## Причины создания резервных копий

Резервные копии помечаются причиной их создания:

- **ручная**: вы нажали **Создать резервную копию сейчас**. Замена активного мира сервера на один из библиотеки также сначала создает `ручную` резервную копию.
- **по расписанию**: создана по [расписанию](/docs/schedules/). Каждый новый сервер также автоматически получает ежедневную резервную копию по расписанию (с разбивкой между 02:00 и 05:59), поэтому сервер имеет автоматическое покрытие с первого дня, а не только перед обновлениями.
- **перед обновлением**: создается автоматически перед обновлением сборки или изменением версии Minecraft, поэтому обновление всегда можно отменить.
- **перед восстановлением**: создается автоматически непосредственно перед восстановлением или сбросом мира, в качестве меры предосторожности на случай, если восстановление окажется не тем, что вы хотели.

## Хранение

Хранение ограничено **на сервер, на причину**: сохраняются самые новые копии в каждой группе, старые автоматически удаляются после каждого успешного создания резервной копии:

| Причина               | Сохраняется по умолчанию |
| --------------------- | ------------------------ |
| по расписанию         | 10                       |
| перед обновлением     | 10                       |
| ручная                | 20                       |
| перед восстановлением | 5                        |

`перед восстановлением` (называемые в панели "резервные копии безопасности") имеют свой собственный небольшой "контейнер", именно для того, чтобы автоматическая резервная копия безопасности никогда не могла вытеснить `ручную` резервную копию, которую вы намеренно сохранили.

Два необязательных верхних предела применяются в дополнение к количеству на причину, оба отключены по умолчанию: **максимальный возраст** (резервные копии старше N дней удаляются, независимо от причины) и **максимальный общий размер** на сервер (самые старые удаляются до тех пор, пока общий размер не уложится в лимит: сначала резервные копии безопасности, затем по расписанию, затем остальные). Самая новая резервная копия сервера никогда не удаляется ни по одному из этих ограничений.

### Изменение настроек

Администраторы устанавливают общесистемную политику в карточке **Хранение резервных копий** на странице **Настройки** (**Заполнить встроенные значения** помещает приведенные выше значения по умолчанию в форму, готовую к сохранению). Сервер может отличаться по любому из шести значений: откройте его вкладку **Резервные копии** и разверните **Хранение для этого сервера**. Каждое поле там пусто, если этот сервер его не устанавливает, и пустое поле следует общесистемному значению (отображается внутри него). Таким образом, сервер может, например, хранить 3 резервные копии по расписанию и использовать общесистемные значения для всего остального; очистка поля возвращает его к общесистемному значению.

![Карточка "Хранение резервных копий" в Настройках](/docs/images/settings-retention.png)

![Хранение для этого сервера на вкладке "Резервные копии" сервера](/docs/images/server-retention.png)

Сохранение само по себе ничего не удаляет. Если новые лимиты оставят существующие резервные копии сверх лимита, панель отобразит для каждого сервера, сколько резервных копий каждого типа будет удалено, сколько места это освободит и сколько лет самой старой из них. Она также сообщит, если сервер уже превышал свои лимиты до этого изменения (например, после предыдущего **С следующей резервной копии**), поскольку применение сейчас обрезает все, что превышает лимит, а не только то, что добавляет это изменение. Затем она спросит, как их применить:

- **Удалить сейчас** удаляет ровно те резервные копии, которые были перечислены, и ничего больше: резервная копия, созданная в промежутке, будет ждать следующей очистки. На странице "Настройки" сервер, находящийся в середине процесса восстановления, создания резервной копии или аналогичного действия, пропускается и очищается после следующего создания резервной копии; на собственной вкладке "Резервные копии" сервера вам будет предложено повторить попытку после завершения этого действия. Пока старые резервные копии сервера удаляются (обычно несколько секунд), другие действия на этом сервере должны ждать: запланированное создание резервной копии или запуск, которое совпадает по времени, будет повторяться каждую минуту до тех пор, пока не сможет (до 30 минут), аварийно завершившийся сервер перезапускается примерно через 20 секунд после завершения (до 30 минут), а запланированный перезапуск или остановка, совпадающая с этим, пропускается до следующего раза.
- **С следующей резервной копии** сохраняет их на данный момент; каждый сервер очищает свои резервные копии при следующем их создании, как это всегда и было.

![Диалоговое окно с перечислением того, что удалят новые лимиты](/docs/images/retention-preview.png)

Резервная копия, которая восстанавливается, никогда не удаляется во время выполнения восстановления: хранение игнорирует ее (и не удаляет другие резервные копии, чтобы освободить для нее место), а ручное удаление запрещено до завершения восстановления.

Те же настройки доступны для скриптов в виде конечных точек административного API: `GET`/`POST /api/backups/retention` и `/api/servers/:id/backups/retention`. Общесистемные значения не могут быть `null`. Для сервера значение `null` (или `""`) удаляет этот конкретный ключ, поэтому он снова следует общесистемному значению, а `{ "reset": true }` удаляет их все. По каждому из этих двух путей `POST …/preview` сообщает, что изменение удалит, не удаляя (`backups`, `bytes`, `servers`, `ids` и разбивка по серверам `byServer`), а `POST …/apply` применяет сохраненную политику немедленно и отвечает `{ deleted, skipped }` для всей системы (`skipped` подсчитывает занятые серверы) или `{ deleted }` для одного сервера. Отправьте `{ "token": "..." }` из предварительного просмотра (действителен 10 минут) или `{ "ids": [...] }` для удаления только этих элементов; без них удаляется все, что превышает лимит. Применение для одного сервера на занятом сервере возвращает 409.

Резервные копии можно **переименовывать** из списка резервных копий (кнопка переименования в каждой строке). Архив на диске и запись в панели перемещаются вместе, поэтому загрузка, восстановление и хранение продолжают работать с новым именем.

![Переименование резервной копии](/docs/images/backup-rename.png)

> Хранение автоматически ограничивается, но большие архивы с модами по-прежнему учитываются в [квоте дискового пространства](/docs/storage/) сервера, поэтому следите за общим объемом для больших сборок.

## Восстановление

Восстановление резервной копии останавливает сервер (проверяя, что контейнер действительно остановлен, прежде чем прикасаться к каким-либо файлам), создает резервную копию безопасности `перед восстановлением`, заменяет **весь каталог сервера** снимком и оставляет его остановленным, чтобы вы могли запустить его снова. Архив сначала распаковывается в сторону и подменяется только после полного извлечения, поэтому восстановление, которое завершается ошибкой на полпути, оставляет текущие файлы нетронутыми. Поскольку обновления сборок всегда сначала создают резервную копию `перед обновлением`, вы всегда можете отменить неудачное обновление.

## Собственная база данных панели

Резервные копии серверов охватывают только папку каждого сервера. Собственная база данных панели (`panel.db`, содержащая пользователей, роли, секреты 2FA, расписания, закрепленные сборки и историю) копируется отдельно во время ежедневного обслуживания:

- `VACUUM INTO` записывает согласованную, дефрагментированную копию в `backups/_panel/` в папке данных; сохраняются самые новые **14** копий.
- При загрузке панель выполняет `PRAGMA integrity_check` и громко регистрирует ошибку, если она возникает, указывая на `backups/_panel` для самой новой рабочей копии.

Создав резервную копию всей папки данных (она также содержит `.secret-key`, ключ шифрования в состоянии покоя), вы создадите резервную копию всего.
