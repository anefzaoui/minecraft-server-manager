Minecraft Server Manager — это однопроцессное, рендерируемое на стороне сервера приложение Node.js. Оно управляет
серверами Minecraft, работающими как Docker-контейнеры, используя образ
[itzg/docker-minecraft-server](https://github.com/itzg/docker-minecraft-server), взаимодействуя с
Docker daemon через его API (никогда не вызывая `docker` CLI).

## Структура времени выполнения

- **Express + Handlebars** рендерят страницы на стороне сервера. SPA отсутствует; JavaScript браузера в `public/js/`
  является написанным вручную прогрессивным улучшением. Шаг esbuild (`pnpm run build:js`) собирает и
  минифицирует его в `public/dist/js/`; приложение обслуживает этот бандл при его наличии и исходный код в противном случае, так что разработка без сборки все равно работает.
- **`node:sqlite`** (встроен в Node; панель требует Node ≥ 24) — это база данных: синхронная,
  без нативных модулей, в режиме WAL. Небольшой менеджер миграций применяет `src/db/migrations/*` при
  загрузке. Подготовленные выражения кэшируются в `src/db/index.js` по текстовому ключу SQL.
- **`ws`** обеспечивает потоки живой консоли и статистики. Оба **брокеруются**: один исходящий поток
  `docker logs --follow` (или `docker stats`) на сервер, демультиплексируемый один раз и рассылаемый каждому
  подключенному вкладке, вместо одного исходящего потока на каждого зрителя. Брокер консоли хранит небольшой буфер повтора для поздно присоединившихся вкладок и отключает подписчика, чей сокет отстает слишком сильно, вместо того чтобы замедлять общий поток.
- **dockerode** — единственный способ взаимодействия приложения с Docker. Конечная точка определяется автоматически для каждой платформы (именованный канал Windows против Unix-сокет).
- **Все постоянное состояние хранится в одной директории** (`$DATA_DIR`, по умолчанию `./data`). Копирование этой
  директории мигрирует всю панель.

## Слои

Зависимости текут в одном направлении:

```
                 ┌─────────────────────────────┐
   HTTP  ───────▶│  web/routes/*  (+ middleware)│   парсинг и валидация ввода, формирование ответов
                 └──────────────┬──────────────┘
                                │
                 ┌──────────────▼──────────────┐
                 │         services/*          │   доменная логика (реальные функции)
                 └───┬─────────┬─────────┬─────┘
                     │         │         │
        ┌────────────▼──┐ ┌────▼────┐ ┌──▼──────────┐
        │   docker/*    │ │  db/*   │ │  storage/*  │   инфраструктура
        └───────────────┘ └─────────┘ └─────────────┘
```

- **`web/routes/`** — один маршрутизатор на домен (`servers`, `players`, `worlds`, `crashes`, `blueprints`,
  `files`, …), смонтированный в `web/app.js`. Маршрутизаторы валидируют с помощью zod, вызывают сервис и возвращают JSON
  или рендерят представление. Бизнес-логика здесь не должна находиться. Два маршрутизатора смонтированы в **общей зоне**, перед `requireAuth`: `routes/status.js` (страницы статуса HTML для каждого сервера по выбору) и
  `routes/apiV1.js` (`/api/v1`, JSON API только для чтения, аутентифицированный токеном Bearer, выданным администратором, из `services/apiTokens.js`, отключен, если не включен в Настройках; см. `docs/public-api.md`).
- **`services/`** — сердце приложения. Каждый сервис отвечает за один домен и может зависеть от
  инфраструктуры и других сервисов.
- **`docker/`** — обертки dockerode: `connect` (определение конечной точки + состояние демона), `containers`
  (создание/запуск/остановка/пересоздание с bind mounts, ограничениями памяти/CPU и метками), `logs`, `stats`,
  `images` и `watcher`, который преобразует события Docker в историю + обнаружение сбоев.
- **`db/`** — обертка SQLite и менеджер миграций.
- **`storage/`** — загрузка `./data`, **защита путей** (`safeJoin`, основа безопасности файлов) и фоновый индексатор размера + контроль квот.

Сквозные аспекты:

- **`config/`** — конфигурация окружения плюс **каталог полей**: единственный источник истины для
  настроек сервера. Каждая переменная окружения itzg каталогизирована (метка, справка, тип, единица измерения, значение по умолчанию,
  валидация, раздел, флаги опасности). Мастер настройки, формы настроек и валидация zod выводятся из него, поэтому добавление новой настройки — это изменение данных, а не новая обвязка UI.
- **`events/`** — `recordEvent()` — единственная точка входа для журнала истории; события жизненного цикла также записывают выдержки из логов контейнеров в `data/logs/<id>/events/`.
- **`ws/`** — аутентифицированные WebSockets консоли + статистики (проверка cookie сессии при обновлении, проверка `Origin` для блокировки межсайтового угона), брокеруемые на сервер (см. "Структура времени выполнения").
- **`logger.js` + `instrument.js`** — `require('./logger')(label)` возвращает [Pino](https://getpino.io) логгер для каждого модуля; уровень из `LOG_LEVEL`, `makeFailureThrottle()` поддерживает один лог-файл для постоянно сбоящего фонового цикла плюс строку "восстановлено".
  `src/utils/logSanitize.js` удаляет ключи, похожие на учетные данные, и токены веб-хуков из структурированных метаданных; `src/config/logLevel.js` — общий список разрешенных уровней (хранится отдельно, чтобы избежать цикла зависимостей с `config`). `src/instrument.js` — неактивный стык Sentry, загружаемый первым в
  `src/server.js`. `src/web/middleware/requestLog.js` записывает одну строку access-лога на запрос
  (пропуская `/healthz` и статические файлы). ESLint обеспечивает `no-console` в `src/**`, с исключениями для `preflight.js`, `instrument.js` и `config/index.js` (они выполняются до существования логгера).
- **Ограничение скорости** — `src/web/middleware/rateLimit.js` помещает `express-rate-limit` перед `/api`
  (`RATE_LIMIT_API_PER_MIN`, по умолчанию 1200) и POST-запросами входа / 2FA / настройки
  (`RATE_LIMIT_AUTH_PER_15MIN`, по умолчанию 100); `0` отключает ограничитель. Он использует `req.ip` в качестве ключа, поэтому
  `TRUST_PROXY` имеет значение за прокси. `/api/v1` имеет свой собственный ограничитель на токен
  (`RATE_LIMIT_PUBLIC_API_PER_MIN`, по умолчанию 120), ключом которого является хэш токена Bearer с резервным вариантом по IP. Отдельный мягкий счетчик на учетную запись в
  `src/web/middleware/auth.js` обрабатывает блокировку входа (по IP и глобально по учетной записи, с затуханием).

## Ключевое поведение домена

- **Modpacks всегда закреплены.** Образ автоматически обновляет незакрепленные пакеты при каждом перезапуске, поэтому панель разрешает "latest" в конкретный идентификатор версии при установке и закрепляет его. Обновления — это явный оркестрованный поток (`updates/`): предварительный просмотр → резервное копирование перед обновлением → плавное завершение → перекрепление → пересоздание → мониторинг работоспособности → откат в один клик.
- **Оверлей пользовательских модов** управляется панелью: добавленные пользователем моды попадают в дедуплицированную библиотеку и жестко связаны с сервером, поэтому они переживают обновления пакетов. Отключение зависит от класса.
- **Порты** выделяются из базовой схемы (игра от `PORT_GAME_START` и выше, RCON = игра +
  `PORT_RCON_OFFSET`, Bedrock от `PORT_BEDROCK_START`), проверяются на доступность и резервируются в
  БД.
- **Квоты диска** принудительно применяются панелью, поскольку Docker не может ограничить использование bind-mount: индексатор
  кэширует размеры каталогов, а операции увеличения диска зависят от них.
- **Секреты** (пароли RCON, ключи API, секреты TOTP, URL веб-хука Discord) шифруются при хранении с помощью AES-256-GCM с использованием выделенного случайного ключа в `$DATA_DIR/.secret-key` (режим `0600`,
  автоматически генерируемый). Он независим от `SESSION_SECRET`; ключ, производный от `SESSION_SECRET`, сохраняется как резервный вариант только для расшифровки для значений, записанных до существования выделенного ключа, а
  `src/services/secretsMigration.js` перешифровывает их под выделенным ключом один раз при загрузке.
  Существующий `.secret-key`, который не может быть разобран, является критической ошибкой при загрузке (он никогда не будет молча
  перегенерирован поверх существующего). Экспорт чертежей удаляет все секреты.

## Форматы данных и передачи

- **`data/panel.db`** — база данных SQLite. Ежедневно снимки через `VACUUM INTO` в
  `data/backups/_panel/` (сохраняется 14 последних); `PRAGMA integrity_check` выполняется при загрузке.
- **`data/.session-secret`** — автоматически генерируемый секрет для подписи cookie, создаваемый при первом запуске, если `SESSION_SECRET` не установлен. Удаление этого файла меняет секрет (что аннулирует сессии).
- **`data/.secret-key`** — выделенный 32-байтный ключ шифрования при хранении (режим `0600`), автоматически создаваемый при первом запуске. Независим от `SESSION_SECRET`; его удаление делает каждую сохраненную учетную запись нерасшифровываемой, поэтому он должен храниться вместе с вашими резервными копиями.
- **Чертежи (`.mcserver.zip`)** — zip-архив с `manifest.json`, описывающим конфигурацию, ресурсы, закрепленную ссылку на пакет, манифест оверлея (URL-адреса источников + sha256), выбранные файлы конфигурации и, опционально, мир. Импорт повторно загружает и проверяет хэш каждого мода и назначает новые порты.
- **Docker-контейнеры**, созданные панелью, имеют имена и метки, чтобы наблюдатель мог их найти;
  панель отвечает за их полный жизненный цикл.

## Последовательность загрузки

1. `require('./instrument')` (стык Sentry) прежде всего, затем `require('./preflight')`
   для четкого сообщения об ошибке при неподдерживаемой версии Node.
2. Загрузка конфигурации; обеспечение/генерация `.session-secret` **и** `.secret-key`.
3. `ensureDataRoot()` — создание структуры `./data`, очистка `tmp/`.
4. Выполнение миграций БД, затем `PRAGMA integrity_check` (громко логирует, указывает на `data/backups/_panel`
   в случае сбоя).
5. Перешифрование любых устаревших секретов, зашифрованных ключом `SESSION_SECRET`, под `.secret-key` (`secretsMigration`).
6. Заполнение стартовых чертежей (защищено).
7. Запуск HTTP + WS сервера. При доступном подключении выводит PIN-код для первого запуска `/setup`.
8. Установка пост-загрузочного защитного механизма времени выполнения (перехватывает необработанные ошибки; `MSM_EXIT_ON_FATAL=1` заставляет жестко завершать работу для управляемых развертываний).
9. Запуск фоновых служб: брокер WS, индексатор хранилища, наблюдатели за сбоями + инвентарем, планировщик,
   мост событий Discord и **ежедневный таймер обслуживания** (удаление старых строк аналитики + снимок
   `panel.db`).
10. Инициализация Docker **в фоновом режиме**. UI полностью работоспособен, пока демон недоступен;
    функции Docker активируются, когда он становится доступен. После подключения `refreshStatuses({ boot })`
    синхронизирует кэшированные статусы, генерирует одноразовое событие `offline-after-restart` для сервера, который был включен до перезапуска панели и не будет запущен снова, и цикл загрузки запускает
    серверы `auto_start` плюс восстанавливает серверы `auto_restart`, найденные сбойными во время простоя
    (с учетом задержки при циклическом сбое).

> Порядок instrument-before-preflight — это сознательный компромисс: он позволяет будущему исправлению Sentry сначала подключить среду выполнения, за счет менее дружелюбного сообщения при очень старой версии Node.

## Конвейер сборки

`pnpm run build` = `build:css` (Tailwind → `public/css/app.css`) + `build:js` (esbuild →
`public/dist/js/`, ESM с разделением кода). `postinstall` выполняет **только CSS**. `public/css/app.css`
и `public/dist/` — это артефакты сборки, игнорируемые Git; стадия сборки Dockerfile выполняет полный
`pnpm run build` и копирует `public/` в образ времени выполнения. Статические файлы обслуживаются с
`immutable`/долгим кэшированием для файлов с отпечатками, коротким кэшированием для CSS/JS и `no-cache` для HTML и
`/api`.
