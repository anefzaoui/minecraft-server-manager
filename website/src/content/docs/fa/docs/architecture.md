Minecraft Server Manager یک برنامه Node.js تک‌فرآیندی و رندر شده در سمت سرور است. این برنامه سرورهای Minecraft را که به عنوان کانتینرهای Docker با استفاده از ایمیج
[itzg/docker-minecraft-server](https://github.com/itzg/docker-minecraft-server) اجرا می‌شوند، مدیریت می‌کند و از طریق API خود با دیمون Docker ارتباط برقرار می‌کند (هرگز با اجرای دستور `docker` در خط فرمان).

## ساختار زمان اجرا

- **Express + Handlebars** صفحات را در سمت سرور رندر می‌کنند. هیچ SPA ای وجود ندارد؛ جاوا اسکریپت مرورگر در `public/js/`
  به صورت دستی برای بهبود تدریجی نوشته شده است. یک مرحله esbuild (`pnpm run build:js`) آن را به `public/dist/js/` باندل و کوچک می‌کند؛ برنامه این باندل را در صورت وجود و سورس خام در غیر این صورت سرو می‌کند، بنابراین اجرای توسعه بدون ساخت نیز کار می‌کند.
- **`node:sqlite`** (ساخته شده در Node؛ پنل به Node ≥ 24 نیاز دارد) پایگاه داده است - همزمان، بدون ماژول‌های نیتیو، حالت WAL. یک اجرا کننده مهاجرت نسخه کوچک، `src/db/migrations/*` را در هنگام راه‌اندازی اعمال می‌کند. دستورات آماده شده در `src/db/index.js` با کلید متن SQL کش می‌شوند.
- **`ws`** جریان‌های کنسول و آمار زنده را حمل می‌کند. هر دو **کارگزاری شده** هستند: یک `docker logs --follow` (یا `docker stats`) بالادستی برای هر سرور، که یک بار دیمولتی‌پلکس شده و به هر تب متصل شده پخش می‌شود، به جای یک بالادستی برای هر بیننده. کارگزار کنسول یک بافر بازپخش کوچک برای تب‌هایی که دیرتر می‌پیوندند نگه می‌دارد و مشترکی را که سوکتش بیش از حد عقب افتاده است، حذف می‌کند به جای اینکه جریان مشترک را متوقف کند.
- **dockerode** تنها راهی است که برنامه با Docker صحبت می‌کند. نقطه پایانی به طور خودکار بر اساس پلتفرم تشخیص داده می‌شود (لوله نام‌گذاری شده ویندوز در مقابل سوکت یونیکس).
- **تمام وضعیت پایدار در یک دایرکتوری قرار دارد** (`$DATA_DIR`، پیش‌فرض `./data`). کپی کردن آن دایرکتوری کل پنل را مهاجرت می‌دهد.

## لایه‌بندی

وابستگی‌ها در یک جهت جریان دارند:

```
                 ┌─────────────────────────────┐
   HTTP  ───────▶│  web/routes/*  (+ middleware)│   ورودی را تجزیه و اعتبارسنجی می‌کند، پاسخ‌ها را شکل می‌دهد
                 └──────────────┬──────────────┘
                                │
                 ┌──────────────▼──────────────┐
                 │         services/*          │   منطق دامنه (ویژگی‌های واقعی)
                 └───┬─────────┬─────────┬─────┘
                     │         │         │
        ┌────────────▼──┐ ┌────▼────┐ ┌──▼──────────┐
        │   docker/*    │ │  db/*   │ │  storage/*  │   زیرساخت
        └───────────────┘ └─────────┘ └─────────────┘
```

- **`web/routes/`** - یک روتر برای هر دامنه (`players`, `worlds`, `crashes`, `blueprints`, `files`, …).
  `web/app.js` روترهای سطح بالا را نصب می‌کند (`api.js`، API JSON جلسه که همچنین مسیرهای اصلی سرور را نگه می‌دارد و روترهای دامنه مخصوص سرور را نصب می‌کند؛ `index.js`، صفحات؛ `auth`, `account`, `tasks`, …). روترها با zod اعتبارسنجی می‌کنند، یک سرویس را فراخوانی می‌کنند و JSON را برمی‌گردانند یا یک نما را رندر می‌کنند. منطق کسب و کار نباید در اینجا قرار گیرد. دو روتر در **منطقه عمومی**، قبل از `requireAuth` نصب می‌شوند: `routes/status.js` (صفحات وضعیت HTML مخصوص سرور اختیاری) و `routes/apiV1.js` (`/api/v1`، یک API JSON فقط خواندنی که با یک توکن Bearer صادر شده توسط مدیر از `services/apiTokens.js` احراز هویت می‌شود، غیرفعال مگر اینکه در تنظیمات فعال شود؛ به `docs/public-api.md` مراجعه کنید).
- **`services/`** - قلب برنامه. هر سرویس مالک یک دامنه است و ممکن است به زیرساخت و سرویس‌های دیگر وابسته باشد.
- **`docker/`** - wrapperهای dockerode: `connect` (تشخیص نقطه پایانی + سلامت دیمون)، `containers` (ایجاد/شروع/توقف/بازسازی با bind mount ها، محدودیت‌های حافظه/CPU و برچسب‌ها)، `logs`, `stats`, `images`, `networks` (کشف شبکه میزبان)، `hostPath` (مسیرهای bind را تحت `DATA_DIR_HOST` دوباره ریشه‌دار می‌کند)، و یک `watcher` که رویدادهای Docker را به تاریخچه + تشخیص خرابی تبدیل می‌کند.
- **`db/`** - wrapper SQLite و اجرا کننده مهاجرت.
- **`storage/`** - راه‌اندازی `./data`، **نگهبان مسیر** (`safeJoin`، ستون فقرات ایمنی فایل)، و شاخص‌کننده اندازه پس‌زمینه + اجرای محدودیت سهمیه.

متقاطع:

- **`config/`** - پیکربندی محیط به علاوه **کاتالوگ فیلد**: منبع واحد حقیقت برای تنظیمات سرور. هر متغیر محیطی itzg فهرست شده است (برچسب، راهنما، نوع، واحد، پیش‌فرض، اعتبارسنجی، بخش، پرچم‌های خطر). جادوگر، فرم‌های تنظیمات و اعتبارسنجی zod همگی از آن مشتق شده‌اند، بنابراین افشای یک تنظیم جدید یک تغییر داده است، نه لوله‌کشی UI جدید.
- **`events/`** - `recordEvent()` تنها نقطه ورود برای لاگ تاریخچه است؛ رویدادهای چرخه حیات همچنین بخش‌هایی از لاگ کانتینر را به `data/logs/<id>/events/` ثبت می‌کنند.
- **`ws/`** - سوکت‌های وب کنسول + آمار احراز هویت شده (کوکی جلسه در هنگام ارتقا تأیید شده، `Origin` برای مسدود کردن ربودن بین سایتی بررسی می‌شود)، کارگزاری شده برای هر سرور (به "ساختار زمان اجرا" مراجعه کنید).
- **`logger.js` + `instrument.js`** - `require('./logger')(label)` یک لاگر [Pino](https://getpino.io) مخصوص ماژول را برمی‌گرداند؛ سطح از `LOG_LEVEL`، `makeFailureThrottle()` یک حلقه پس‌زمینه که به طور مداوم شکست می‌خورد را در یک خط لاگ به علاوه یک خط "بازیابی شده" نگه می‌دارد. `src/utils/logSanitize.js` کلیدهای با شکل اعتبارنامه و توکن‌های وب‌هوک را از فراداده ساختاریافته حذف می‌کند؛ `src/config/logLevel.js` لیست مجاز سطح مشترک است (برای جلوگیری از چرخه نیازمندی با `config` جدا نگه داشته شده است). `src/instrument.js` یک نقطه اتصال Sentry غیرفعال است که اولین بار در `src/server.js` بارگذاری می‌شود. `src/web/middleware/requestLog.js` یک خط لاگ دسترسی برای هر درخواست می‌نویسد (با نادیده گرفتن `/healthz` و دارایی‌های ثابت). ESLint `no-console` را تحت `src/**` اعمال می‌کند، با معافیت `preflight.js`, `instrument.js`, و `config/index.js` (آنها قبل از وجود لاگر اجرا می‌شوند).
- **محدودیت نرخ** - `src/web/middleware/rateLimit.js` `express-rate-limit` را جلوی `/api` (`RATE_LIMIT_API_PER_MIN`، پیش‌فرض 1200) و ورود / 2FA / POST های راه‌اندازی (`RATE_LIMIT_AUTH_PER_15MIN`، پیش‌فرض 100) قرار می‌دهد؛ `0` یک محدود کننده را غیرفعال می‌کند. این بر اساس `req.ip` کلید می‌خورد، بنابراین `TRUST_PROXY` در پشت پروکسی مهم است. `/api/v1` محدودکننده‌های خاص خود را دارد: یک سقف در هر IP کلاینت (پنج برابر بودجه در هر توکن) که قبل از تأیید توکن اجرا می‌شود، سپس یک بودجه در هر توکن (`RATE_LIMIT_PUBLIC_API_PER_MIN`، پیش‌فرض 120) که بر اساس شناسه توکن تأیید شده کلید می‌خورد. یک شمارنده نرم جداگانه در هر حساب در
  `src/web/middleware/auth.js` قفل ورود (در هر IP و در سطح حساب جهانی، با کاهش) را مدیریت می‌کند.
- **مجوز دسترسی**: دو لایه. نقش جهانی (`requireAuth` → `requireRole` / `requireWrite` در `src/web/middleware/auth.js`) اقدامات کل پنل را محدود می‌کند و پیش‌فرض در هر سرور است. مجوزهای مخصوص سرور (`src/services/permissions.js`، نه قابلیت که به صورت لیست JSON برای هر `(user, server)` در `user_server_permissions` ذخیره می‌شود) آن پیش‌فرض را برای یک سرور اصلاح می‌کند؛ هر مسیر `/api/servers/:id`، نصب روتر فرعی، صفحه، وب‌سوکت و لیست در سطح ناوگان از طریق `src/web/middleware/serverAccess.js` (`serverScope`، نصب شده بر روی پیشوند `/servers/:id` هم API و هم روتر صفحه، سرور را بدون `view` به عنوان 404 پنهان می‌کند؛ `requireCap(cap)` قابلیت مورد نیاز یک مسیر را نام می‌برد). نوشتن‌هایی که سرور خود را در بدنه نام‌گذاری می‌کنند (زمان‌بندی‌ها، استخراج و نصب جهان، صادرات طرح‌بندی) برای بینندگان توسط `requireWrite` فقط برای آن سرور باز می‌شوند، و هر یک از این مسیرها قابلیت را خود بررسی می‌کند. `test/permissions-routes.test.js` پشته‌های روتر زنده را پیمایش می‌کند و در صورتی که مسیر نوشتن در سطح سرور، نصب یا صفحه فاقد دروازه باشد، شکست می‌خورد.

## رفتارهای کلیدی دامنه

- **Modpack ها همیشه پین می‌شوند.** ایمیج به طور خودکار بسته‌های پین نشده را در هر راه‌اندازی مجدد ارتقا می‌دهد، بنابراین پنل "آخرین" را در زمان نصب به یک شناسه نسخه مشخص تبدیل کرده و آن را پین می‌کند. ارتقاها یک جریان هماهنگ صریح هستند (`updates/`): پیش‌نمایش → پشتیبان‌گیری قبل از ارتقا → توقف آرام → بازپین → بازسازی → مانیتور سلامت → بازگشت با یک کلیک.
- **پوشش مد سفارشی** توسط پنل مدیریت می‌شود: مد‌های اضافه شده توسط کاربر به کتابخانه حذف تکرار شده وارد می‌شوند و به صورت سخت‌پیوند به سرور وارد می‌شوند تا در برابر به‌روزرسانی‌های بسته مقاومت کنند. غیرفعال کردن وابسته به کلاس است. از آنجایی که کتابخانه هر بیلد دانلود شده را نگه می‌دارد، یک به‌روزرسانی بیلد جایگزین شده (`server_content.previous_*`) را ثبت می‌کند و می‌تواند از فایل‌های محلی به تنهایی بازگردانده شود. غیرفعال کردن مد بسته، متغیر محیطی حذف بسته را به جای آن می‌نویسد؛ `packs.applyPack` آن و بقیه تنظیمات بسته (`PACK_TUNING_KEYS`) را در طول تغییر نسخه همان بسته حمل می‌کند و هنگام تغییر بسته آن را حذف می‌کند.
- **ارتقاء نسخه Minecraft باید به دست آید.** `services/compat.js` مد‌های سرور را اسکن می‌کند - که از ردیف‌های نصب شده توسط پنل، سپس مانیفست بسته CurseForge، سپس با هش محتوا در برابر Modrinth/CurseForge حل می‌شوند - و یک ماتریس پشتیبانی (لودر، نسخه Minecraft) برای هر پروژه از `latestFilesIndexes` (200 پروژه در هر درخواست) CurseForge و لیست نسخه مخصوص پروژه Modrinth (یک درخواست برای هر پروژه، که لودر و نسخه را جفت نگه می‌دارد) می‌سازد. بررسی کننده به‌روزرسانی فقط جدیدترین نسخه‌ای را که EVERY مد پشتیبانی می‌کند، ارائه می‌دهد و در صورت عدم امکان تعیین پاسخ، هیچ چیزی ارائه نمی‌دهد: هیچ اسکن، اسکن برای نسخه یا لودر متفاوت، اسکن که هرگز تمام نشده است، یا جار که هیچ یک از رجیستری‌ها آن را تشخیص نمی‌دهد. اسکن‌ها فقط دستی هستند و پیشرفت و نتایج جزئی آنها در `version_compat` قرار دارد (نه در `services/tasks.js` در حافظه)، بنابراین یک تازه‌سازی یا راه‌اندازی مجدد پنل به جای گیر کردن روی یک اسپینر، از سر گرفته می‌شود؛ `reconcileScans()` اسکن‌های یتیم شده توسط خاموشی را در راه‌اندازی بعدی علامت‌گذاری می‌کند.
- **نسخه لودر مد یک پین است، مانند همه چیز.** `services/loaderPin.js` بیلد نصب شده را از مانیفست نصب خود ایمیج (`.forge-manifest.json` و موارد مشابه) می‌خواند و پین را می‌نویسد: متغیر itzg لودر در یک سرور ساده (`FORGE_VERSION`, …)، یا `CF_MOD_LOADER_VERSION` در یک بسته CurseForge Forge یا Fabric، که نسخه اعلام شده توسط بسته را لغو می‌کند. نصب کننده CurseForge ایمیج آن را برای NeoForge نادیده می‌گیرد، و بسته‌های Modrinth و FTB هیچ کدام ندارند، بنابراین لودر آنها بسته را دنبال می‌کند. `packs.applyPack` تمام متغیرهای `CF_` را در هنگام به‌روزرسانی یا بازگردانی بسته حذف می‌کند، که یک لغو را با بقیه حذف می‌کند. یک بیلد تایپ شده ابتدا در برابر لیست کامل رجیستری بررسی می‌شود (`services/loaderVersions.js`؛ Forge از متادیتای maven خود می‌آید که اعداد را رد می‌کند؛ یک مورد از دست رفته یک بار دیگر در برابر خود رجیستری بررسی می‌شود)، سپس تغییر پشتیبان‌گیری می‌شود → پین (بر روی محیط همانطور که پس از پشتیبان‌گیری است) → بازسازی.
- **پورت‌ها** از یک طرح پایه تخصیص داده می‌شوند (بازی از `PORT_GAME_START` به بالا، RCON = بازی + `PORT_RCON_OFFSET`، Bedrock از `PORT_BEDROCK_START`)، برای در دسترس بودن بررسی می‌شوند و در پایگاه داده رزرو می‌شوند. "گرفته شده" اتحادیه ادعاهای هر سرور است (پورت‌های زنده، به علاوه یک جفت در انتظار در زیر)، هر پورت میزبان که هر کانتینر Docker منتشر می‌کند (`containers.publishedHostPorts`: اتصالات زنده کانتینرهای در حال اجرا به علاوه اتصالات پیکربندی شده هر کانتینر متوقف شده، زیرا یک بررسی پورت سیستم عامل از داخل کانتینر خود پنل فقط فضای شبکه آن کانتینر را می‌بیند)، و بررسی سیستم عامل. بخش Docker به مدت 3 ثانیه کش می‌شود و محدود است: لیستی که در 2.5 ثانیه پاسخ نمی‌دهد فقط بخش Docker را حذف می‌کند، و یک بازرسی کند فقط هزینه پورت آن کانتینر را دارد. ایجاد سرور و `servers.changeGamePort` پورت‌ها را از طریق یک زنجیره سریال‌سازی انتخاب می‌کنند که فقط انتخاب و ادعای آن را پوشش می‌دهد (نوشتن ردیف برای ایجاد، رزرو در حافظه برای تغییر پورت)؛ انتخابگر پورت BlueMap و لغوهای پورت اضافی در آن نیستند و Docker را مشورت نمی‌کنند. تغییر پورت در یک سرور موجود (`servers.changeGamePort`، تحت قفل عملیاتی سرور) بلافاصله اعمال می‌شود، زیرا Docker اتصالات پورت را در زمان ایجاد کانتینر رفع می‌کند: جفت جدید (RCON همیشه بازی + `PORT_RCON_OFFSET`) در حافظه بررسی و رزرو می‌شود (`ports.reserve`، هم جفت قدیمی و هم جدید، که توسط هر انتخاب دیگری رعایت می‌شود) تحت قفل پورت. این رد می‌شود (409 `PENDING_CHANGES`) در حالی که تنظیمات دیگر منتظر بازسازی هستند، بنابراین فقط یک کانتینر را که قبلاً اجرا شده است، در یک پورت جدید بازسازی می‌کند؛ و یک سرور در حال اجرا فقط زمانی تغییر می‌کند که درخواست `restart: true` را بگوید (در غیر این صورت 409 `NEEDS_CONFIRM`). ایمیج کش شده و نام کانتینر سفارشی قبل از دست زدن به هر چیزی بررسی می‌شود. یک سرور در حال اجرا متوقف می‌شود؛ سپس جفت جدید با `pending_recreate = 1` نوشته می‌شود (بنابراین یک خرابی پنل از آنجا یک "بازسازی در انتظار" صادقانه باقی می‌گذارد)، کانتینر حذف می‌شود، با جفت جدید بازسازی می‌شود و راه‌اندازی می‌شود. اگر هر مرحله پس از توقف شکست بخورد، `putBackOnOldPort` جفت قدیمی را برمی‌گرداند، آن را بازسازی می‌کند (و در صورت اجرا بودن، راه‌اندازی مجدد می‌کند) و ثبت می‌کند که کدام مرحله شکست خورده است؛ تاریخچه و هشدارها می‌گویند که آیا حتی آن هم شکست خورده است، که سرور را تا زمانی که کسی آن را راه‌اندازی کند، متوقف می‌گذارد. قابلیت `settings` کافی است، از جمله سرور در حال اجرا. غیر مدیران فقط می‌توانند از `PORT_GAME_START` به بالا انتخاب کنند.
  (ستون‌های `port_*_pending` از مهاجرت 029 متعلق به یک طرح قبلی، منتشر نشده هستند و استفاده نمی‌شوند؛ 031 آنها را پاک می‌کند.) برخورد قفل با 409 با `code: 'BUSY'` پاسخ می‌دهد، که فراخوان‌های در حال تلاش مجدد در زیر به جای متن آن را بررسی می‌کنند. راه‌اندازی مجدد خودکار خرابی
  (`watcher.restartAfterCrash`) و پشتیبان‌گیری یا شروع زمان‌بندی شده (`scheduler.runTaskWithRetry`) که سرور را در حال انجام اقدام دیگری پیدا می‌کنند، هر 20 ثانیه / 60 ثانیه تا 30 دقیقه دوباره تلاش می‌کنند، و به‌روزرسانی یا بازگردانی بسته مراحل قفل شده خود را به همین ترتیب دوباره امتحان می‌کند (`opLock.retryWhileBusy`)؛ یک راه‌اندازی مجدد خرابی یا شروع زمان‌بندی شده منتظر، زمانی که کسی سرور را از زمان شروع متوقف، کشته یا راه‌اندازی کرده است، تسلیم می‌شود (`events.lifecycleActionSince`)، و راه‌اندازی مجدد خرابی همچنین زمانی که راه‌اندازی مجدد خودکار خاموش است یا سرور رفته است. راه‌اندازی مجدد، توقف و دستورات زمان‌بندی شده دوباره امتحان نمی‌شوند، و یک زمان‌بندی که آخرین اجرای آن هنوز در انتظار است، شلیک بعدی خود را رد می‌کند.
- **سهمیه‌های دیسک** توسط پنل اجرا می‌شوند زیرا Docker نمی‌تواند استفاده از bind-mount را محدود کند: شاخص‌کننده اندازه‌های دایرکتوری را کش می‌کند و عملیات افزایش دیسک بر اساس آنها محدود می‌شوند.
- **رازها** (رمزهای عبور RCON، کلیدهای API، رازهای TOTP، URL وب‌هوک Discord) با AES-256-GCM با استفاده از یک کلید تصادفی اختصاصی در `$DATA_DIR/.secret-key` (حالت `0600`، خودکار تولید شده) در حالت استراحت رمزگذاری می‌شوند. این مستقل از `SESSION_SECRET` است؛ یک کلید مشتق شده از `SESSION_SECRET` به عنوان یک پشتیبان فقط رمزگشایی برای مقادیری که قبل از وجود کلید اختصاصی نوشته شده‌اند، نگهداری می‌شود و `src/services/secretsMigration.js` آنها را یک بار در هنگام راه‌اندازی تحت کلید اختصاصی دوباره رمزگذاری می‌کند. یک `.secret-key` که وجود دارد اما تجزیه نمی‌شود، یک خطای راه‌اندازی سخت است (هرگز به طور خاموش بازنویسی نمی‌شود). طرح‌بندی‌ها تمام رازها را هنگام صادرات حذف می‌کنند.
- **`server.properties` متعلق به پنل است اما توسط محیط سایه زده می‌شود.** ایمیج itzg هر ویژگی مبتنی بر محیط را در هر راه‌اندازی مجدد مجدداً تأیید می‌کند (`OVERRIDE_SERVER_PROPERTIES` به طور پیش‌فرض true است)، بنابراین مقداری که پنل مستقیماً ویرایش می‌کند - PvP/مشکل بازی World Controls، سوئیچ whitelist، ویرایشگر فایل - در راه‌اندازی مجدد بعدی به طور خاموش بازگردانده می‌شود مگر اینکه متغیر محیطی مطابق حذف شده و کانتینر بازسازی شود. هر نوشتن مستقیم ویژگی از طریق `writeServerProperties()` (کل فایل) یا `setServerProperty()` (یک کلید) در `src/services/servers.js` می‌گذرد، که به طور اتمی فایل را بازنویسی می‌کند، متغیر محیطی پشت هر کلید تغییر یافته را حذف می‌کند (از طریق ویژگی `prop:` در فیلدهای کاتالوگ، که در تست‌ها در برابر تعاریف ویژگی خود ایمیج بررسی می‌شود)، و `pending_recreate` را علامت‌گذاری می‌کند. مشکل به فایل نوشته می‌شود و همچنین از طریق RCON ارسال می‌شود، زیرا یک سرور اختصاصی ویژگی `difficulty` را در هر راه‌اندازی مجدد مجدداً اعمال می‌کند. خود Minecraft server.properties را از مقادیر زمان راه‌اندازی خود در هنگام `whitelist on/off` دوباره ذخیره می‌کند، که ویرایش‌های انجام شده در حالی که سرور در حال اجرا است را لغو می‌کند، بنابراین سوئیچ whitelist در حال اجرا ابتدا فایل را اسنپ‌شات می‌کند و آن را با تغییر فقط `white-list` دوباره می‌نویسد. متغیرهای محیطی در زمان ایجاد کاملاً قابل پیکربندی باقی می‌مانند (جادوگر آنها را رندر می‌کند و آنها یک بار اعمال می‌شوند)؛ آنها فقط اولین بار که پنل ویژگی زیربنایی را ویرایش می‌کند، از پین خارج می‌شوند. MOTD همان قرارداد را دارد: یک ویرایش مستقیم فایل `motd` آن را حذف می‌کند، بنابراین آخرین نوشته برنده می‌شود.

## فرمت‌های داده و سیم

- **`data/panel.db`** - پایگاه داده SQLite. روزانه از طریق `VACUUM INTO` به `data/backups/_panel/` اسنپ‌شات می‌شود (آخرین 14 عدد نگهداری می‌شوند)؛ `PRAGMA integrity_check` در هنگام راه‌اندازی اجرا می‌شود.
- **`data/.session-secret`** - راز امضای کوکی که خودکار تولید می‌شود، در اولین اجرا در صورت عدم تنظیم `SESSION_SECRET` ایجاد می‌شود. حذف آن راز را می‌چرخاند (که جلسات را نامعتبر می‌کند).
- **`data/.secret-key`** - کلید رمزگذاری در حالت استراحت 32 بایتی اختصاصی (حالت `0600`)، خودکار در اولین اجرا ایجاد می‌شود. مستقل از `SESSION_SECRET`؛ حذف آن باعث می‌شود هر اعتبار ذخیره شده غیرقابل رمزگشایی شود، بنابراین متعلق به پشتیبان‌های شما است.
- **طرح‌بندی‌ها (`.mcserver.zip`)** - یک زیپ با `manifest.json` که پیکربندی، منابع، مرجع بسته پین شده، مانیفست پوشش (URL های منبع + sha256)، فایل‌های پیکربندی انتخاب شده و به طور اختیاری یک جهان را توصیف می‌کند. واردات مجدداً هر مد را دانلود و هش-تأیید می‌کند و پورت‌های تازه اختصاص می‌دهد.
- **کانتینرهای Docker** ایجاد شده توسط پنل نام‌گذاری و برچسب‌گذاری شده‌اند تا واچر بتواند آنها را پیدا کند؛ پنل مالک چرخه کامل حیات آنها است.

## توالی راه‌اندازی

1. `require('./instrument')` (نقطه اتصال Sentry) قبل از هر چیز دیگر، سپس `require('./preflight')` برای شکست واضح در نسخه Node پشتیبانی نشده.
2. بارگذاری پیکربندی؛ اطمینان از/تولید `.session-secret` **و** `.secret-key`.
3. `ensureDataRoot()` - طرح‌بندی `./data` را ایجاد می‌کند، `tmp/` را پاک می‌کند.
4. اجرای مهاجرت‌های پایگاه داده، سپس `PRAGMA integrity_check` (به طور پر سر و صدا لاگ می‌کند، در صورت شکست به `data/backups/_panel` اشاره می‌کند).
5. رمزگذاری مجدد هر راز قدیمی با کلید `SESSION_SECRET` تحت `.secret-key` (`secretsMigration`).
6. وارد کردن کلیدهای API از محیط یک بار (`apiKeys.importFromEnvOnce()`)، پین کردن هر سروری که هنوز یک انتخابگر مد پین نشده را حمل می‌کند (`packPins.pinUnpinnedServers()`)، علامت‌گذاری اسکن‌های سازگاری نسخه که توسط یک فرآیند قبلی در حال اجرا باقی مانده‌اند به عنوان قطع شده (`compat.reconcileScans()`)، سپس طرح‌بندی‌های شروع کننده را بذر می‌دهد (محافظت شده).
7. راه‌اندازی سرور HTTP + WS. در یک اتصال در معرض دید، پین `/setup` اولین اجرا را چاپ می‌کند.
8. نصب نگهبان زمان اجرای پس از راه‌اندازی (خطاهای دریافت نشده را می‌گیرد؛ `MSM_EXIT_ON_FATAL=1` آن را برای استقرارهای نظارت شده به شدت خارج می‌کند).
9. راه‌اندازی سرویس‌های پس‌زمینه: کارگزار WS، شاخص‌کننده ذخیره‌سازی، واچرهای خرابی + موجودی، زمان‌بند، پل رویداد Discord، واچر دسترسی چت‌بات، و **تایمر نگهداری روزانه** (پاک کردن ردیف‌های تحلیلی قدیمی، رونوشت‌های چت‌بات، تاریخچه رویداد (365 روز) و ردیف‌های کش API، سپس اسنپ‌شات `panel.db`).
10. راه‌اندازی Docker **در پس‌زمینه**. رابط کاربری کاملاً قابل استفاده است در حالی که دیمون پایین است؛ ویژگی‌های Docker زمانی که قابل دسترسی می‌شوند روشن می‌شوند. پس از اتصال، `refreshStatuses({ boot })` وضعیت‌های کش شده را تطبیق می‌دهد، یک رویداد `offline-after-restart` یک‌باره برای سروری که قبل از راه‌اندازی مجدد پنل روشن بود و دوباره راه‌اندازی نمی‌شود، منتشر می‌کند، و حلقه راه‌اندازی سرورهای `auto_start` را شروع می‌کند به علاوه سرورهای `auto_restart` که در طول قطعی در حال خرابی پیدا شده‌اند را بازیابی می‌کند (با احترام به عقب‌گرد حلقه خرابی).

> ترتیب instrument-before-preflight یک مصالحه عمدی است: این اجازه می‌دهد تا یک سیم‌کشی Sentry آینده ابتدا زمان اجرا را وصله کند، با هزینه یک پیام کمی دوستانه‌تر در یک Node بسیار قدیمی.

## خط لوله ساخت

`pnpm run build` = `build:css` (Tailwind → `public/css/app.css`) + `build:js` (esbuild →
`public/dist/js/`، ESM با تقسیم کد). `postinstall` **فقط CSS** را اجرا می‌کند. `public/css/app.css`
و `public/dist/` مصنوعات ساخت gitignored هستند؛ مرحله ساخت Dockerfile کل `pnpm run build` را اجرا می‌کند و `public/` را به ایمیج زمان اجرا کپی می‌کند. دارایی‌های ثابت
`immutable`/long-cache برای فایل‌های اثر انگشتی، short-cache برای CSS/JS، و `no-cache` برای HTML و
`/api` سرو می‌شوند.
