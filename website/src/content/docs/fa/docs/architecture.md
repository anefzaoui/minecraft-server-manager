Minecraft Server Manager یک برنامه Node.js تک‌فرآیندی و رندر شده در سمت سرور است. این برنامه سرورهای Minecraft را که با استفاده از ایمیج [itzg/docker-minecraft-server](https://github.com/itzg/docker-minecraft-server) به عنوان کانتینرهای Docker اجرا می‌شوند، مدیریت می‌کند و از طریق API خود با دیمون Docker ارتباط برقرار می‌کند (هرگز با اجرای دستور `docker` در خط فرمان).

## ساختار زمان اجرا

- **Express + Handlebars** صفحات را در سمت سرور رندر می‌کنند. هیچ SPA وجود ندارد؛ جاوا اسکریپت مرورگر در `public/js/` به صورت دستی برای بهبود تدریجی نوشته شده است. یک مرحله esbuild (`pnpm run build:js`) آن را در `public/dist/js/` باندل و کوچک می‌کند؛ برنامه این باندل را در صورت وجود و سورس خام در غیر این صورت سرو می‌کند، بنابراین اجرای توسعه بدون ساخت نیز کار می‌کند.
- **`node:sqlite`** (که در Node داخلی است؛ پنل به Node ≥ 24 نیاز دارد) پایگاه داده است - همزمان، بدون ماژول‌های نیتیو، حالت WAL. یک اجرا کننده کوچک مهاجرت نسخه‌بندی شده، `src/db/migrations/*` را هنگام راه‌اندازی اعمال می‌کند. دستورات آماده شده در `src/db/index.js` با کلید متن SQL کش می‌شوند.
- **`ws`** جریان‌های کنسول زنده و آمار را حمل می‌کند. هر دو **کارگزاری شده** هستند: یک `docker logs --follow` (یا `docker stats`) بالادستی برای هر سرور، که یک بار دیمولتی‌پلکس شده و به هر تب متصل شده توزیع می‌شود، به جای یک جریان بالادستی برای هر بیننده. کارگزار کنسول یک بافر پخش کوچک برای تب‌هایی که دیرتر می‌پیوندند نگه می‌دارد و یک مشترک را که سوکت آن بیش از حد عقب افتاده است، حذف می‌کند تا از کند شدن جریان مشترک جلوگیری شود.
- **`dockerode`** تنها راهی است که برنامه با Docker صحبت می‌کند. نقطه پایانی بر اساس پلتفرم به طور خودکار تشخیص داده می‌شود (نام لوله ویندوز در مقابل سوکت یونیکس).
- **تمام وضعیت پایدار در یک دایرکتوری قرار دارد** (`$DATA_DIR`، پیش‌فرض `./data`). کپی کردن آن دایرکتوری کل پنل را منتقل می‌کند.

## لایه‌بندی

وابستگی‌ها در یک جهت جریان دارند:

```
                 ┌─────────────────────────────┐
   HTTP  ───────▶│  web/routes/*  (+ middleware)│   تجزیه و اعتبارسنجی ورودی، شکل‌دهی پاسخ‌ها
                 └──────────────┬──────────────┘
                                │
                 ┌──────────────▼──────────────┐
                 │         services/*          │   منطق دامنه (ویژگی‌های واقعی)
                 └───┬─────────┬─────────┬─────┘
                     │         │         │
        ┌────────────▼──┐ ┌────▼────┐ ┌──▼──────────┐
        │   docker/*    │ │  db/*   │ │  storage/*  │   زیرساخت
        └───────────────┘ └─────────┘ └─────────────┘
```

- **`web/routes/`** - یک روتر برای هر دامنه (`servers`, `players`, `worlds`, `crashes`, `blueprints`, `files`, …)، که در `web/app.js` بارگذاری شده است. روترها با zod اعتبارسنجی می‌کنند، یک سرویس را فراخوانی می‌کنند و JSON را برمی‌گردانند یا یک نما را رندر می‌کنند. منطق تجاری نباید در اینجا قرار گیرد. دو روتر در **منطقه عمومی**، قبل از `requireAuth` بارگذاری شده‌اند: `routes/status.js` (صفحات وضعیت HTML اختیاری برای هر سرور) و `routes/apiV1.js` (`/api/v1`، یک API JSON فقط خواندنی که توسط یک توکن Bearer صادر شده توسط مدیر از `services/apiTokens.js` احراز هویت می‌شود، در صورت غیرفعال بودن در تنظیمات؛ به `docs/public-api.md` مراجعه کنید).
- **`services/`** - قلب برنامه. هر سرویس مالک یک دامنه است و ممکن است به زیرساخت و سایر سرویس‌ها وابسته باشد.
- **`docker/`** - پوشش‌های dockerode: `connect` (تشخیص نقطه پایانی + سلامت دیمون)، `containers` (ایجاد/شروع/توقف/بازسازی با bind mountها، محدودیت‌های حافظه/CPU و برچسب‌ها)، `logs`، `stats`، `images` و یک `watcher` که رویدادهای Docker را به تاریخچه + تشخیص خرابی تبدیل می‌کند.
- **`db/`** - پوشش SQLite و اجرا کننده مهاجرت.
- **`storage/`** - راه‌اندازی `./data`، **نگهبان مسیر** (`safeJoin`، ستون فقرات ایمنی فایل) و شاخص‌کننده اندازه پس‌زمینه + اجرای محدودیت سهمیه.

متقاطع:

- **`config/`** - پیکربندی محیط به علاوه **کاتالوگ فیلد**: منبع واحد حقیقت برای تنظیمات سرور. هر متغیر محیطی itzg فهرست شده است (برچسب، راهنما، نوع، واحد، پیش‌فرض، اعتبارسنجی، بخش، پرچم‌های خطر). جادوگر، فرم‌های تنظیمات و اعتبارسنجی zod همگی از آن مشتق شده‌اند، بنابراین نمایش یک تنظیم جدید یک تغییر داده است، نه لوله‌کشی UI جدید.
- **`events/`** - `recordEvent()` تنها نقطه ورود برای گزارش تاریخچه است؛ رویدادهای چرخه حیات همچنین بخش‌هایی از گزارش کانتینر را به `data/logs/<id>/events/` ثبت می‌کنند.
- **`ws/`** - سوکت‌های وب کنسول + آمار احراز هویت شده (کوکی جلسه هنگام ارتقا تأیید شده، `Origin` برای مسدود کردن ربایش بین سایتی بررسی می‌شود)، کارگزاری شده برای هر سرور (به "ساختار زمان اجرا" مراجعه کنید).
- **`logger.js` + `instrument.js`** - `require('./logger')(label)` یک لاگر [Pino](https://getpino.io) برای هر ماژول برمی‌گرداند؛ سطح از `LOG_LEVEL`، `makeFailureThrottle()` یک حلقه پس‌زمینه که به طور مداوم شکست می‌خورد را به یک خط لاگ به علاوه یک خط "بازیابی شده" نگه می‌دارد. `src/utils/logSanitize.js` کلیدهای با شکل اعتبارنامه و توکن‌های وب‌هوک را از فراداده ساختاریافته حذف می‌کند؛ `src/config/logLevel.js` لیست مجاز سطح مشترک است (برای جلوگیری از چرخه نیازمندی با `config` جدا نگه داشته شده است). `src/instrument.js` یک نقطه اتصال Sentry غیرفعال است که اولین بار در `src/server.js` بارگذاری می‌شود. `src/web/middleware/requestLog.js` یک خط لاگ دسترسی برای هر درخواست می‌نویسد (با نادیده گرفتن `/healthz` و دارایی‌های ثابت). ESLint `no-console` را در `src/**` اعمال می‌کند، با معافیت `preflight.js`، `instrument.js` و `config/index.js` (آنها قبل از وجود لاگر اجرا می‌شوند).
- **محدودیت نرخ** - `src/web/middleware/rateLimit.js` `express-rate-limit` را در جلوی `/api` (`RATE_LIMIT_API_PER_MIN`، پیش‌فرض 1200) و POSTهای ورود / 2FA / راه‌اندازی (`RATE_LIMIT_AUTH_PER_15MIN`، پیش‌فرض 100) قرار می‌دهد؛ `0` یک محدود کننده را غیرفعال می‌کند. این محدود کننده بر اساس `req.ip` کلید می‌زند، بنابراین `TRUST_PROXY` در پشت پروکسی اهمیت دارد. `/api/v1` محدود کننده مخصوص به خود را دارد (per-token) (`RATE_LIMIT_PUBLIC_API_PER_MIN`، پیش‌فرض 120)، که بر اساس هش توکن Bearer با یک fallback IP کلید می‌زند. یک شمارنده نرم جداگانه مخصوص به حساب در `src/web/middleware/auth.js` قفل ورود را مدیریت می‌کند (مخصوص IP و سراسری حساب، با کاهش).

## رفتارهای کلیدی دامنه

- **بسته‌های ماد همیشه پین می‌شوند.** ایمیج بسته‌های پین نشده را در هر راه‌اندازی مجدد به طور خودکار ارتقا می‌دهد، بنابراین پنل "latest" را در زمان نصب به یک شناسه نسخه مشخص تبدیل کرده و آن را پین می‌کند. ارتقاها یک جریان هماهنگ صریح هستند (`updates/`): پیش‌نمایش → پشتیبان‌گیری قبل از ارتقا → توقف آرام → بازپین کردن → بازسازی → مانیتور سلامت → بازگشت با یک کلیک.
- **پوشش ماد سفارشی** توسط پنل مدیریت می‌شود: مادهای اضافه شده توسط کاربر در کتابخانه حذف تکرار شده قرار می‌گیرند و به سرور پیوند سخت داده می‌شوند تا در برابر به‌روزرسانی‌های بسته مقاومت کنند. غیرفعال کردن وابسته به کلاس است.
- **پورت‌ها** از یک طرح پایه تخصیص داده می‌شوند (بازی از `PORT_GAME_START` به بالا، RCON = بازی + `PORT_RCON_OFFSET`، Bedrock از `PORT_BEDROCK_START`)، برای در دسترس بودن بررسی می‌شوند و در پایگاه داده رزرو می‌شوند.
- **سهمیه‌های دیسک** توسط پنل اجرا می‌شوند زیرا Docker نمی‌تواند استفاده از bind-mount را محدود کند: شاخص‌کننده اندازه‌های هر دایرکتوری را کش می‌کند و عملیات رشد دیسک بر اساس آنها محدود می‌شود.
- **رازها** (رمزهای عبور RCON، کلیدهای API، رازهای TOTP، URL وب‌هوک Discord) با AES-256-GCM با استفاده از یک کلید تصادفی اختصاصی در `$DATA_DIR/.secret-key` (حالت `0600`، خودکار تولید شده) در حالت استراحت رمزگذاری می‌شوند. این کلید مستقل از `SESSION_SECRET` است؛ یک کلید مشتق شده از `SESSION_SECRET` به عنوان یک fallback فقط برای رمزگشایی برای مقادیری که قبل از وجود کلید اختصاصی نوشته شده‌اند، نگهداری می‌شود و `src/services/secretsMigration.js` آن مقادیر را هنگام راه‌اندازی مجدداً تحت کلید اختصاصی رمزگذاری می‌کند. یک `.secret-key` که وجود دارد اما قابل تجزیه نیست، یک خطای راه‌اندازی سخت است (هرگز به طور بی‌صدا بازنویسی نمی‌شود). طرح‌های کلی هنگام صادرات تمام رازها را حذف می‌کنند.

## فرمت‌های داده و سیم

- **`data/panel.db`** - پایگاه داده SQLite. روزانه از طریق `VACUUM INTO` به `data/backups/_panel/` (14 مورد آخر نگهداری می‌شوند) اسنپ‌شات می‌شود؛ `PRAGMA integrity_check` هنگام راه‌اندازی اجرا می‌شود.
- **`data/.session-secret`** - راز امضای کوکی که خودکار تولید می‌شود، در اولین اجرا در صورت عدم تنظیم `SESSION_SECRET` ایجاد می‌شود. حذف آن راز را می‌چرخاند (که جلسات را نامعتبر می‌کند).
- **`data/.secret-key`** - کلید رمزگذاری اختصاصی 32 بایتی در حالت استراحت (حالت `0600`)، خودکار در اولین اجرا ایجاد می‌شود. مستقل از `SESSION_SECRET`؛ حذف آن باعث می‌شود هر اعتبارنامه ذخیره شده غیرقابل رمزگشایی شود، بنابراین با پشتیبان‌های شما همراه است.
- **طرح‌های کلی (`.mcserver.zip`)** - یک فایل زیپ با `manifest.json` که پیکربندی، منابع، مرجع بسته پین شده، مانیفست پوشش (URLهای منبع + sha256)، فایل‌های پیکربندی انتخاب شده و به طور اختیاری یک جهان را توصیف می‌کند. واردات مجدداً دانلود و هش-تأیید می‌کند هر ماد و پورت‌های تازه را اختصاص می‌دهد.
- **کانتینرهای Docker** ایجاد شده توسط پنل نام‌گذاری و برچسب‌گذاری شده‌اند تا واچر بتواند آنها را پیدا کند؛ پنل مالک چرخه حیات کامل آنها است.

## توالی راه‌اندازی

1. `require('./instrument')` (نقطه اتصال Sentry) قبل از هر چیز دیگر، سپس `require('./preflight')` برای شکست واضح در نسخه Node پشتیبانی نشده.
2. بارگذاری پیکربندی؛ اطمینان از/تولید `.session-secret` **و** `.secret-key`.
3. `ensureDataRoot()` - طرح‌بندی `./data` را ایجاد می‌کند، `tmp/` را پاک می‌کند.
4. اجرای مهاجرت‌های پایگاه داده، سپس `PRAGMA integrity_check` (به طور بلند لاگ می‌کند، در صورت شکست به `data/backups/_panel` اشاره می‌کند).
5. رمزگذاری مجدد هر راز قدیمی با کلید `SESSION_SECRET` تحت `.secret-key` (`secretsMigration`).
6. بذرافشانی طرح‌های کلی شروع‌کننده (محافظت شده).
7. راه‌اندازی سرور HTTP + WS. در یک اتصال باز، پین `/setup` اولین اجرا را چاپ می‌کند.
8. نگهبان زمان اجرای پس از راه‌اندازی را نصب می‌کند (خطاهای پیش‌بینی نشده را می‌گیرد؛ `MSM_EXIT_ON_FATAL=1` آن را برای استقرارهای نظارت شده به شدت خارج می‌کند).
9. راه‌اندازی سرویس‌های پس‌زمینه: کارگزار WS، شاخص‌کننده ذخیره‌سازی، واچرهای خرابی + موجودی، زمان‌بند، پل رویداد Discord و **تایمر نگهداری روزانه** (ردیف‌های تحلیلی قدیمی را پاک می‌کند + از `panel.db` اسنپ‌شات می‌گیرد).
10. راه‌اندازی Docker **در پس‌زمینه**. رابط کاربری کاملاً قابل استفاده است در حالی که دیمون خاموش است؛ ویژگی‌های Docker زمانی که قابل دسترسی می‌شوند، فعال می‌شوند. پس از اتصال، `refreshStatuses({ boot })` وضعیت‌های کش شده را مجدداً هماهنگ می‌کند، یک رویداد یک‌باره `offline-after-restart` را برای سروری که قبل از راه‌اندازی مجدد پنل روشن بود و بازگردانده نمی‌شود، منتشر می‌کند، و حلقه راه‌اندازی سرورهای `auto_start` را شروع کرده و سرورهای `auto_restart` که در طول قطعی خراب پیدا شده‌اند را بازیابی می‌کند (با در نظر گرفتن backoff حلقه خرابی).

> ترتیب instrument-before-preflight یک مصالحه عمدی است: این اجازه می‌دهد تا یک سیم‌کشی Sentry آینده زمان اجرا را در ابتدا وصله کند، با هزینه یک پیام کمی کمتر دوستانه در یک Node بسیار قدیمی.

## خط لوله ساخت

`pnpm run build` = `build:css` (Tailwind → `public/css/app.css`) + `build:js` (esbuild → `public/dist/js/`، ESM با تقسیم کد). `postinstall` **فقط CSS** را اجرا می‌کند. `public/css/app.css` و `public/dist/` مصنوعات ساخت gitignore شده هستند؛ مرحله ساخت Dockerfile `pnpm run build` کامل را اجرا کرده و `public/` را به ایمیج زمان اجرا کپی می‌کند. دارایی‌های ثابت به صورت `immutable`/long-cache برای فایل‌های اثر انگشتی، short-cache برای CSS/JS و `no-cache` برای HTML و `/api` سرو می‌شوند.
