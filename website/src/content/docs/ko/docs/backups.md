**백업** 페이지에서는 모든 서버의 스냅샷을 크기, 이유, 생성 시점별로 확인할 수 있으며, 서버별 또는 이유별로 필터링할 수 있습니다.

![백업](/docs/images/backups.png)

## 백업 생성하기

서버의 **백업** 탭(또는 [예약](/docs/schedules/)을 통해)에서 클릭 한 번으로 전체 서버 디렉터리를 스냅샷할 수 있습니다. 패널은 월드를 먼저 동결(`save-off` → `save-all`)하고 데이터를 압축한 다음, 저장 기능을 다시 활성화(`save-on`)하므로 실행 중인 서버에서도 일관된 백업이 가능합니다. 압축은 백그라운드 워커 스레드에서 실행되므로 패널이 멈추지 않습니다. API를 통해 시작된 백업에는 메모를 추가할 수 있습니다.

모든 아카이브는 작성되는 즉시 **무결성 검사**를 거칩니다. 패널은 zip 파일을 다시 열어 디렉터리를 읽습니다. 손상되었거나 열 수 없는 아카이브는 삭제되며, 복원 시점에 문제가 발생하는 대신 백업 호출이 즉시 실패합니다. 시작된 적이 없는 서버의 빈 아카이브는 허용되지만 이벤트에 플래그가 지정됩니다.

**"월드 축소도 함께 진행"**을 선택하면(백업 탭 또는 백업 예약에서) 아카이브가 안전하게 작성된 후 방문 빈도가 낮은 청크를 제거합니다(**[월드 축소](/docs/world-shrink/)** 참조). 축소는 서버가 중지된 동안에만 실행됩니다. 실행 중인 서버에서는 백업이 계속 진행되고 축소는 건너뜁니다.

![서버 백업](/docs/images/server-backups.png)

## 백업 이유

백업은 생성된 이유에 따라 태그가 지정됩니다.

- **수동**: **지금 백업**을 클릭한 경우입니다. 라이브러리의 월드를 서버의 활성 월드로 교체할 때도 먼저 `수동` 백업을 수행합니다.
- **예약**: [예약](/docs/schedules/)에 의해 생성됩니다. 모든 새 서버에는 매일 예약 백업이 자동으로 생성됩니다(02:00~05:59 사이). 따라서 서버는 업데이트 전뿐만 아니라 첫날부터 자동으로 보호됩니다.
- **업데이트 전**: 팩 업그레이드 또는 Minecraft 버전 변경 전에 자동으로 수행되므로 업그레이드는 항상 되돌릴 수 있습니다.
- **복원 전**: 복원 또는 월드 재설정 직전에 자동으로 수행되어 복원이 예상과 다를 경우 안전망 역할을 합니다.

## 보존 정책

보존은 **서버별, 이유별로** 제한됩니다. 각 그룹에서 가장 최신 백업이 유지되며, 성공적인 백업이 완료될 때마다 오래된 백업은 자동으로 정리됩니다.

| 이유        | 기본 유지 개수 |
| ----------- | -------------- |
| 예약        | 10             |
| 업데이트 전 | 10             |
| 수동        | 20             |
| 복원 전     | 5              |

`복원 전`(패널에서 안전 백업이라고 함)은 별도의 작은 공간을 가지므로 자동 안전 백업이 의도적으로 보관한 `수동` 백업을 덮어쓰지 않습니다.

각 이유별 개수 외에 두 가지 선택적 제한이 적용되며, 둘 다 기본적으로 비활성화되어 있습니다. **최대 보존 기간**(이유에 관계없이 N일보다 오래된 백업은 정리됨) 및 **서버당 최대 총 크기**(총 크기가 맞을 때까지 가장 오래된 백업이 정리됨: 안전 백업 우선, 다음 예약 백업, 그 다음 나머지). 서버의 가장 최신 백업은 이 제한에 의해 정리되지 않습니다.

### 변경 방법

관리자는 **설정** 페이지의 **백업 보존** 카드에서 패널 전체 정책을 설정합니다(**기본값 채우기**는 위의 기본값을 양식에 다시 채워 저장할 준비를 합니다). 서버는 6가지 값 중 어느 것이든 다를 수 있습니다. 해당 서버의 **백업** 탭을 열고 **이 서버의 보존 정책**을 확장합니다. 해당 필드는 서버가 설정하지 않는 한 비어 있으며, 빈 필드는 패널 전체 값을 따릅니다(필드 안에 표시됨). 따라서 서버는 예를 들어 3개의 예약 백업을 유지하고 나머지 모든 항목에 대해 패널 전체 값을 사용할 수 있습니다. 필드를 지우면 패널 전체 값으로 돌아갑니다.

![설정의 백업 보존 카드](/docs/images/settings-retention.png)

![서버 백업 탭의 서버 보존 정책](/docs/images/server-retention.png)

저장한다고 해서 백업이 즉시 삭제되지는 않습니다. 새 제한으로 인해 기존 백업이 제한을 초과하는 경우, 패널은 서버별로 각 종류별로 몇 개의 백업이 삭제될지, 얼마만큼의 공간이 확보될지, 가장 오래된 백업이 얼마나 오래되었는지 나열합니다. 또한 이전에 이미 제한을 초과한 경우(예: 이전 **다음 백업부터** 이후)도 표시합니다. 현재 적용하면 이 편집으로 추가된 것뿐만 아니라 제한을 초과하는 모든 것이 정리됩니다. 그런 다음 적용 방법을 묻습니다.

- **지금 삭제**: 방금 나열된 백업만 정확히 삭제합니다. 그 사이에 생성된 백업은 다음 정리 시까지 기다립니다. 설정 페이지에서 복원, 백업 또는 유사한 작업을 진행 중인 서버는 건너뛰고 다음 백업 후에 정리됩니다. 서버 자체의 백업 탭에서는 해당 작업이 완료된 후 다시 시도하라는 메시지가 표시됩니다. 서버의 오래된 백업이 삭제되는 동안(보통 몇 초) 해당 서버의 다른 작업은 기다려야 합니다. 예약된 백업 또는 시작이 충돌하면(최대 30분 동안) 1분마다 다시 시도하고, 충돌한 서버 재시작은 완료 후 약 20초 이내에 다시 시도합니다(최대 30분 동안). 예약된 재시작 또는 중지는 충돌 시 다음 시간까지 건너뜁니다.
- **다음 백업부터**: 지금은 유지하고, 각 서버는 항상 그랬듯이 다음 백업 시에 백업을 정리합니다.

![새 제한으로 인해 삭제될 항목을 나열하는 대화 상자](/docs/images/retention-preview.png)

복원 중인 백업은 복원이 실행되는 동안에는 절대 제거되지 않습니다. 보존 정책은 백업을 그대로 두고(공간을 만들기 위해 다른 백업을 삭제하지 않음) 수동으로 삭제하려고 하면 복원이 완료될 때까지 거부됩니다.

관리자 API 엔드포인트와 동일한 설정이 스크립트에서도 사용 가능합니다: `GET`/`POST /api/backups/retention` 및 `/api/servers/:id/backups/retention`. 패널 전체 값은 `null`일 수 없습니다. 서버의 경우, `null`(`""` 포함) 값은 해당 키를 제거하여 패널 전체 값을 따르게 하며, `{ "reset": true }`는 모든 키를 제거합니다. 두 경로 모두 아래에 `POST …/preview`는 변경 사항이 삭제할 항목을 삭제하지 않고 보고하고(`backups`, `bytes`, `servers`, `ids` 및 서버별 `byServer` 분석), `POST …/apply`는 정책을 즉시 적용하고 `{ deleted, skipped }` (패널 전체) 또는 `{ deleted }` (단일 서버)를 반환합니다. 미리 보기의 `{ "token": "..." }` (10분 동안 유지됨) 또는 `{ "ids": [...] }`를 보내 해당 항목만 삭제하거나, 둘 다 없으면 제한을 초과하는 모든 항목이 삭제됩니다. 바쁜 서버에 대한 서버별 적용은 409를 반환합니다.

백업은 백업 목록에서 **이름을 변경**할 수 있습니다(각 행의 이름 변경 버튼). 디스크의 아카이브와 패널의 기록이 함께 이동하므로 다운로드, 복원 및 보존 정책은 새 이름으로 계속 작동합니다.

![백업 이름 변경](/docs/images/backup-rename.png)

> 보존 정책은 자동으로 제한되지만, 대규모 모드 팩 아카이브는 서버의 [디스크 할당량](/docs/storage/)에 포함되므로 대규모 팩의 총량을 주시하십시오.

## 복원하기

백업을 복원하면 서버가 중지되고(파일을 건드리기 전에 컨테이너가 실제로 중지되었는지 확인), `복원 전` 안전 백업을 수행한 다음, **전체 서버 디렉터리**를 스냅샷으로 교체하고, 사용자가 다시 시작할 수 있도록 중지된 상태로 둡니다. 아카이브는 먼저 옆에 압축 해제되고 완전히 추출된 후에야 교체되므로, 복원이 중간에 실패하면 현재 파일은 그대로 유지됩니다. 팩 업그레이드는 항상 `업데이트 전` 백업을 먼저 수행하므로, 잘못된 업그레이드는 항상 롤백할 수 있습니다.

## 패널 자체 데이터베이스

서버 백업은 각 서버의 폴더만 포함합니다. 패널 자체 데이터베이스(`panel.db`, 사용자, 역할, 2FA 비밀, 예약, 팩 고정 및 기록 저장)는 일일 유지 관리 타이머에서 별도로 스냅샷됩니다.

- `VACUUM INTO`는 데이터 폴더의 `backups/_panel/`에 일관되고 조각 모음된 복사본을 씁니다. 가장 최신 **14개**가 유지됩니다.
- 부팅 시 패널은 `PRAGMA integrity_check`를 실행하고 실패하면 크게 기록하며, 가장 최신 유효 복사본을 `backups/_panel`에서 찾도록 안내합니다.

전체 데이터 폴더(암호화 키인 `.secret-key`도 포함)를 백업하면 모든 것이 백업됩니다.
