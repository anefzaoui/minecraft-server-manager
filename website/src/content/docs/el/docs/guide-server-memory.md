Σύντομη απάντηση, για έναν server που θα παίζεται πραγματικά:

| Τι εκτελείτε                                       | Σωρός Java (heap) | Δώστε στη μηχανή |
| -------------------------------------------------- | ----------------- | ---------------- |
| Vanilla ή Paper, έως 10 παίκτες                    | 2 GB              | 4 GB             |
| Paper με plugins, 10 έως 30 παίκτες                | 4 GB              | 6 GB             |
| Ένα ελαφρύ πακέτο mods, 40 έως 80 mods             | 4 GB              | 6 GB             |
| Ένα μεγάλο πακέτο "kitchen-sink", 150 έως 300 mods | 6 έως 8 GB        | 10 GB            |
| GregTech New Horizons και παρόμοια τέρατα          | 8 έως 12 GB       | 16 GB            |

Δύο αριθμοί, όχι ένας. Αυτό είναι το κομμάτι που παραλείπουν οι περισσότεροι οδηγοί, και είναι ο λόγος που οι άνθρωποι αγοράζουν έναν server 4 GB, δίνουν στη Java 4 GB, και μετά τον βλέπουν να πεθαίνει.

## Ο σωρός (heap) και η μηχανή είναι διαφορετικοί αριθμοί

Ο σωρός Java (`-Xmx`) είναι το πόση μνήμη μπορεί να χρησιμοποιήσει το ίδιο το παιχνίδι για τον κόσμο, τις οντότητες και τα δεδομένα των mods. Η μηχανή, ή το container, πρέπει να φιλοξενήσει αυτόν τον σωρό **συν** όλα τα άλλα που χρειάζεται η Java: μεταδεδομένα κλάσεων, στοίβες νημάτων (thread stacks), διαχείριση συλλογής απορριμμάτων (garbage-collector bookkeeping), buffers δικτύου και την ίδια την JVM. Αυτό το επιπλέον κόστος είναι περίπου 0,5 έως 1,5 GB για έναν modded server.

Αν ο σωρός ισούται με τη μνήμη της μηχανής, ο πυρήνας (kernel) τερματίζει τον server τη στιγμή που η Java φτάνει σε αυτό το επιπλέον κόστος. Στο Docker, αυτό εμφανίζεται ως κωδικός εξόδου 137, και στα αρχεία καταγραφής (logs) τίποτα απολύτως: η διαδικασία απλώς εξαφανίζεται στη μέση μιας πρότασης. Οι άνθρωποι συνήθως κατηγορούν ένα mod.

Ένας ασφαλής κανόνας: **σωρός συν 25 τοις εκατό, και τουλάχιστον ένα GB ελεύθερο.** Ένας σωρός 8 GB θέλει μια μηχανή 10 GB.

## Περισσότερη RAM δεν σημαίνει περισσότερη απόδοση

Το Minecraft είναι περιορισμένο από ένα μόνο νήμα (single-thread bound) στα περισσότερα από όσα κάνει. Το να δώσεις σε ένα πακέτο 40 mods 16 GB δεν κάνει τη δημιουργία τμημάτων (chunks) ταχύτερη· κάνει κάθε παύση συλλογής απορριμμάτων μεγαλύτερη, επειδή υπάρχει περισσότερο να διασχιστεί. Ένας server που τραυλίζει κάθε τριάντα δευτερόλεπτα είναι συχνά ένας server με υπερβολικά μεγάλο σωρό, όχι πολύ λίγο.

Αυξήστε τον σωρό όταν βλέπετε αυτά, και όχι αλλιώς:

- `java.lang.OutOfMemoryError: Java heap space` στο log.
- Επαναλαμβανόμενο "Can't keep up! Is the server overloaded?" με παύσεις συλλογής απορριμμάτων στα timings.
- Χρήση μνήμης που ανεβαίνει στην οροφή και παραμένει εκεί για ώρες.

## Γιατί ο server σας δείχνει 12 GB χρησιμοποιούμενα ενώ κανείς δεν είναι συνδεδεμένος

Επειδή έτσι τον ορίσατε. Δύο προεπιλογές συνωμοτούν:

1. Η κοινή εικόνα Docker (Docker image) ορίζει τον αρχικό σωρό ίσο με τον μέγιστο, οπότε `-Xms` και `-Xmx` είναι και οι δύο ο αριθμός σας. Η Java τον διεκδικεί αμέσως αντί να τον αυξάνει σταδιακά.
2. Το δημοφιλές σύνολο παραμέτρων (flags) του Aikar περιλαμβάνει το `-XX:+AlwaysPreTouch`, το οποίο διατρέχει κάθε σελίδα αυτού του σωρού κατά την εκκίνηση, ώστε οι σελίδες να έχουν πραγματικά εκχωρηθεί. Είναι σκόπιμο: ανταλλάσσει μια πιο αργή εκκίνηση και μια μεγάλη τιμή αδράνειας για λιγότερες παύσεις αργότερα.

Μετρημένο σε Paper 1.21.1 με σωρό 2 GB σε container 4 GB, δειγματοληπτημένο για τρία λεπτά μετά τη φόρτωση του κόσμου:

| Διαμόρφωση                         | Εγκατεστημένη μνήμη (Resident memory) |
| ---------------------------------- | ------------------------------------- |
| Χωρίς flags                        | 2.60 GiB                              |
| Flags Aikar                        | 2.59 GiB                              |
| Flags Aikar χωρίς `AlwaysPreTouch` | 1.95 GiB                              |
| Flags Aikar με αρχικό σωρό 512 MB  | 1.38 GiB                              |
| Χωρίς flags με αρχικό σωρό 512 MB  | 1.25 GiB                              |

Έτσι, ένας server που "χρησιμοποιεί" 12 GB σε αδράνεια είναι συνήθως ένας σωρός 12 GB που έχει προ-αγγιχτεί (pre-touched), όχι μια διαρροή (leak). Η παρακολούθησή σας το διαβάζει σωστά· ο αριθμός απλώς δεν σημαίνει αυτό που φαίνεται.

Αν θέλετε μια ειλικρινή τιμή αδράνειας, ορίστε τον αρχικό σωρό χαμηλότερο από τον μέγιστο. Πληρώνετε γι' αυτό με μερικές περισσότερες συλλογές απορριμμάτων νωρίς. Αν προτιμάτε σταθερούς χρόνους καρέ (frame times), αφήστε το ως έχει και σταματήστε να παρακολουθείτε το γράφημα.

## Οι παίκτες έχουν λιγότερη σημασία από ό,τι νομίζετε

Το διπλασιασμό από 10 σε 20 παίκτες κοστίζει πολύ λιγότερο από την προσθήκη πενήντα mods. Οι παίκτες προσθέτουν κυρίως οντότητες και φορτωμένα τμήματα, τα οποία κλιμακώνονται ήπια. Τα mods προσθέτουν δεδομένα κλάσεων, μητρώα (registries), χαρακτηριστικά δημιουργίας κόσμου και τις δικές τους κρυφές μνήμες (caches), τα οποία δεν το κάνουν. Το μέγεθος για το πακέτο πρώτα, μετά προσθέστε περίπου 100 έως 200 MB ανά κανονικό παίκτη σε έναν modded server.

Η απόσταση προβολής (View distance) είναι ο άλλος μεγάλος μοχλός. Η μείωση από 12 σε 8 τμήματα μπορεί να εξοικονομήσει ένα gigabyte σε έναν πολυάσχολο server και είναι μετά βίας αισθητή στο παιχνίδι.

## Στο Minecraft Server Manager

Κάθε server έχει δύο ξεχωριστά πεδία, **Java heap** και **container memory limit**, ακριβώς επειδή είναι διαφορετικά ερωτήματα. Ο οδηγός δημιουργίας ορίζει το όριο του container 50 τοις εκατό πάνω από τον σωρό για εσάς, και ο πίνακας ελέγχου αρνείται να αποθηκεύσει έναν server του οποίου το όριο του container δεν είναι πάνω από τον σωρό του, επειδή αυτός ο συνδυασμός καταλήγει σε κωδικό εξόδου 137 αντί για μήνυμα λάθους.

Ο μετρητής μνήμης σε έναν server δείχνει τι χρησιμοποιεί πραγματικά το container, με μια σημείωση όταν ο σωρός διεκδικήθηκε αμέσως, έτσι ώστε ένας προ-αγγιχμένος σωρός να μην διαβάζεται ως ανεξέλεγκτος. Ένας server που ο πυρήνας τερμάτισε λόγω μνήμης καταγράφεται ακριβώς έτσι στο ιστορικό, αντί ως μυστήριο σφάλμα.
