Το Minecraft Server Manager είναι μια εφαρμογή Node.js που αποδίδει σελίδες στον διακομιστή, με μία μόνο διεργασία. Διαχειρίζεται διακομιστές Minecraft που εκτελούνται ως κοντέινερ Docker χρησιμοποιώντας την εικόνα [itzg/docker-minecraft-server](https://github.com/itzg/docker-minecraft-server), επικοινωνώντας με τον δαίμονα Docker μέσω του API του (ποτέ με κλήση της γραμμής εντολών `docker`).

## Δομή χρόνου εκτέλεσης

- **Express + Handlebars** αποδίδουν σελίδες στον διακομιστή. Δεν υπάρχει SPA. Το JavaScript του προγράμματος περιήγησης στο `public/js/` είναι χειροποίητη προοδευτική ενίσχυση. Ένα βήμα esbuild (`pnpm run build:js`) το συσκευάζει και το συμπιέζει σε `public/dist/js/`. Η εφαρμογή εξυπηρετεί αυτό το πακέτο όταν υπάρχει και την ακατέργαστη πηγή διαφορετικά, οπότε μια εκτέλεση ανάπτυξης χωρίς build εξακολουθεί να λειτουργεί.
- **`node:sqlite`** (ενσωματωμένο στο Node· το πάνελ απαιτεί Node ≥ 24) είναι η βάση δεδομένων - σύγχρονη, μηδενικές εγγενείς ενότητες, λειτουργία WAL. Ένας μικρός δρομέας μετεγκατάστασης εκδόσεων εφαρμόζει τα `src/db/migrations/*` κατά την εκκίνηση. Οι προετοιμασμένες δηλώσεις αποθηκεύονται στην κρυφή μνήμη στο `src/db/index.js` με κλειδί το κείμενο SQL.
- **`ws`** μεταφέρει τις ροές κονσόλας και στατιστικών σε πραγματικό χρόνο. Και οι δύο είναι **μεσολαβητές**: ένα upstream `docker logs --follow` (ή `docker stats`) ανά διακομιστή, αποδιαμεσολαβείται μία φορά και διανέμεται σε κάθε συνδεδεμένη καρτέλα, αντί για ένα upstream ανά θεατή. Ο μεσολαβητής κονσόλας διατηρεί ένα μικρό buffer επανάληψης για καρτέλες που συνδέονται αργά και απορρίπτει έναν συνδρομητή του οποίου η υποδοχή πέφτει πολύ πίσω, αντί να καθυστερεί την κοινή ροή.
- **`dockerode`** είναι ο μόνος τρόπος με τον οποίο η εφαρμογή επικοινωνεί με το Docker. Το τελικό σημείο ανιχνεύεται αυτόματα ανά πλατφόρμα (ονομασμένος σωλήνας Windows έναντι υποδοχής Unix).
- **Όλη η επίμονη κατάσταση βρίσκεται σε έναν κατάλογο** (`$DATA_DIR`, προεπιλογή `./data`). Η αντιγραφή αυτού του καταλόγου μεταφέρει ολόκληρο το πάνελ.

## Στρώματα

Οι εξαρτήσεις ρέουν προς μία κατεύθυνση:

```
                 ┌─────────────────────────────┐
   HTTP  ───────▶│  web/routes/*  (+ middleware)│   ανάλυση & επικύρωση εισόδου, διαμόρφωση αποκρίσεων
                 └──────────────┬──────────────┘
                                │
                 ┌──────────────▼──────────────┐
                 │         services/*          │   λογική τομέα (οι πραγματικές λειτουργίες)
                 └───┬─────────┬─────────┬─────┘
                     │         │         │
        ┌────────────▼──┐ ┌────▼────┐ ┌──▼──────────┐
        │   docker/*    │ │  db/*   │ │  storage/*  │   υποδομή
        └───────────────┘ └─────────┘ └─────────────┘
```

- **`web/routes/`** - ένας δρομολογητής ανά τομέα (`players`, `worlds`, `crashes`, `blueprints`, `files`, …). Το `web/app.js` προσαρτά τα κορυφαία επίπεδα (`api.js`, το API JSON συνεδρίας που περιέχει επίσης τις βασικές διαδρομές διακομιστή και προσαρτά τους δρομολογητές τομέα ανά διακομιστή· `index.js`, οι σελίδες· `auth`, `account`, `tasks`, …). Οι δρομολογητές επικυρώνουν με zod, καλούν μια υπηρεσία και επιστρέφουν JSON ή αποδίδουν μια προβολή. Η επιχειρησιακή λογική δεν ανήκει εδώ. Δύο δρομολογητές προσαρτώνται στη **δημόσια ζώνη**, πριν από το `requireAuth`: `routes/status.js` (προαιρετικές σελίδες κατάστασης ανά διακομιστή HTML) και `routes/apiV1.js` (`/api/v1`, ένα API JSON μόνο για ανάγνωση πιστοποιημένο από ένα διακριτικό Bearer που έχει εκδοθεί από διαχειριστή από το `services/apiTokens.js`, απενεργοποιημένο εκτός αν είναι ενεργοποιημένο στις Ρυθμίσεις· δείτε το `docs/public-api.md`).
- **`services/`** - η καρδιά της εφαρμογής. Κάθε υπηρεσία κατέχει έναν τομέα και μπορεί να εξαρτάται από την υποδομή και από άλλες υπηρεσίες.
- **`docker/`** - περιτυλίγματα dockerode: `connect` (ανίχνευση τελικού σημείου + υγεία δαίμονα), `containers` (δημιουργία/εκκίνηση/διακοπή/επανδημιουργία με bind mounts, όρια μνήμης/CPU και ετικέτες), `logs`, `stats`, `images`, `networks` (ανακάλυψη δικτύου host), `hostPath` (επανεπανατοποθετεί bind paths κάτω από το `DATA_DIR_HOST`), και ένας `watcher` που μετατρέπει τα συμβάντα Docker σε ιστορικό + ανίχνευση σφαλμάτων.
- **`db/`** - το περιτύλιγμα SQLite και ο δρομέας μετεγκατάστασης.
- **`storage/`** - η εκκίνηση του `./data`, ο **φύλακας διαδρομής** (`safeJoin`, η ραχοκοκαλιά ασφάλειας αρχείων) και ο δείκτης μεγέθους στο παρασκήνιο + επιβολή ποσοστώσεων.

Διασταυρούμενες:

- **`config/`** - ρύθμιση παραμέτρων περιβάλλοντος συν το **κατάλογος πεδίων**: η μοναδική πηγή αλήθειας για τις ρυθμίσεις του διακομιστή. Κάθε μεταβλητή περιβάλλοντος itzg καταλογογραφείται (ετικέτα, βοήθεια, τύπος, μονάδα, προεπιλογή, επικύρωση, ενότητα, σημαίες κινδύνου). Ο οδηγός, οι φόρμες ρυθμίσεων και η επικύρωση zod προέρχονται όλοι από αυτό, οπότε η έκθεση μιας νέας ρύθμισης είναι μια αλλαγή δεδομένων, όχι νέα υδραυλική εγκατάσταση UI.
- **`events/`** - το `recordEvent()` είναι το μοναδικό σημείο εισόδου για το αρχείο καταγραφής ιστορικού· τα συμβάντα κύκλου ζωής καταγράφουν επίσης αποσπάσματα αρχείων καταγραφής διακομιστή στο `data/logs/<id>/events/`.
- **`ws/`** - πιστοποιημένα WebSockets κονσόλας + στατιστικών (το cookie συνεδρίας επαληθεύεται κατά την αναβάθμιση, το `Origin` ελέγχεται για αποκλεισμό υποκλοπής διασχίσεων ιστοτόπων), μεσολαβητής ανά διακομιστή (δείτε "Δομή χρόνου εκτέλεσης").
- **`logger.js` + `instrument.js`** - το `require('./logger')(label)` επιστρέφει έναν καταγραφέα [Pino](https://getpino.io) ανά ενότητα· επίπεδο από το `LOG_LEVEL`, το `makeFailureThrottle()` διατηρεί έναν βρόχο παρασκηνίου που αποτυγχάνει επίμονα σε μία γραμμή καταγραφής συν μια γραμμή "ανακτήθηκε". Το `src/utils/logSanitize.js` αφαιρεί κλειδιά σχήματος διαπιστευτηρίων και διακριτικά webhook από τα δομημένα μεταδεδομένα· το `src/config/logLevel.js` είναι η κοινή λίστα επιτρεπόμενων επιπέδων (διατηρείται ξεχωριστά για να αποφευχθεί ένας κύκλος απαίτησης με το `config`). Το `src/instrument.js` είναι μια αδρανής σύνδεση Sentry, φορτωμένη πρώτα στο `src/server.js`. Το `src/web/middleware/requestLog.js` γράφει μία γραμμή αρχείου καταγραφής πρόσβασης ανά αίτημα (παραλείποντας το `/healthz` και τα στατικά στοιχεία). Το ESLint επιβάλλει το `no-console` κάτω από το `src/**`, με τα `preflight.js`, `instrument.js` και `config/index.js` να εξαιρούνται (εκτελούνται πριν υπάρξει ο καταγραφέας).
- **Περιορισμός ρυθμού** - το `src/web/middleware/rateLimit.js` τοποθετεί το `express-rate-limit` μπροστά από το `/api` (`RATE_LIMIT_API_PER_MIN`, προεπιλογή 1200) και τις POST για σύνδεση / 2FA / ρύθμιση (`RATE_LIMIT_AUTH_PER_15MIN`, προεπιλογή 100)· το `0` απενεργοποιεί έναν περιοριστή. Βασίζεται στο `req.ip`, οπότε το `TRUST_PROXY` έχει σημασία πίσω από έναν διαμεσολαβητή. Το `/api/v1` έχει τους δικούς του περιοριστές: ένα όριο ανά IP πελάτη (πέντε φορές τον προϋπολογισμό ανά διακριτικό) που εκτελείται πριν επαληθευτεί το διακριτικό, στη συνέχεια ένας προϋπολογισμός ανά διακριτικό (`RATE_LIMIT_PUBLIC_API_PER_MIN`, προεπιλογή 120) με κλειδί το αναγνωριστικό του επαληθευμένου διακριτικού. Ένας ξεχωριστός μετρητής μαλακής κατάστασης ανά λογαριασμό στο `src/web/middleware/auth.js` χειρίζεται το κλείδωμα σύνδεσης (ανά IP και καθολικό λογαριασμού, φθίνουσα).
- **Εξουσιοδότηση**: δύο επίπεδα. Ο καθολικός ρόλος (`requireAuth` → `requireRole` / `requireWrite` στο `src/web/middleware/auth.js`) ελέγχει τις ενέργειες σε ολόκληρο το πάνελ και είναι η προεπιλογή σε κάθε διακομιστή. Τα δικαιώματα ανά διακομιστή (`src/services/permissions.js`, εννέα δυνατότητες αποθηκευμένες ως λίστα JSON ανά `(user, server)` στο `user_server_permissions`) βελτιώνουν αυτήν την προεπιλογή για έναν διακομιστή· κάθε διαδρομή `/api/servers/:id`, προσαρμογή δρομολογητή, σελίδα, WebSocket και λίστα σε όλο τον στόλο περνά από το `src/web/middleware/serverAccess.js` (`serverScope`, προσαρτημένο στο πρόθεμα `/servers/:id` τόσο του API όσο και του δρομολογητή σελίδας, αποκρύπτει έναν διακομιστή χωρίς `view` ως 404· `requireCap(cap)` ονομάζει τη δυνατότητα που χρειάζεται μια διαδρομή). Οι εγγραφές που ονομάζουν τον διακομιστή τους στο σώμα (προγραμματισμοί, εξαγωγή και εγκατάσταση κόσμου, εξαγωγή σχεδίου) ανοίγουν για θεατές μόνο από το `requireWrite` για αυτόν τον διακομιστή, και κάθε τέτοια διαδρομή ελέγχει η ίδια τη δυνατότητα. Το `test/permissions-routes.test.js` διατρέχει τις στοίβες ζωντανών δρομολογητών και αποτυγχάνει εάν μια διαδρομή εγγραφής με εμβέλεια διακομιστή, προσαρμογή ή σελίδα δεν έχει πύλη.

## Βασικές συμπεριφορές τομέα

- **Τα Modpacks είναι πάντα καρφιτσωμένα.** Η εικόνα αναβαθμίζει αυτόματα τα μη καρφιτσωμένα πακέτα σε κάθε επανεκκίνηση, οπότε το πάνελ επιλύει το "latest" σε ένα συγκεκριμένο αναγνωριστικό έκδοσης κατά τον χρόνο εγκατάστασης και το καρφιτσώνει. Οι αναβαθμίσεις είναι μια ρητή ενορχηστρωμένη ροή (`updates/`): προεπισκόπηση → αντίγραφο ασφαλείας πριν από την αναβάθμιση → ομαλή διακοπή → επανακαρφίτσωμα → επανδημιουργία → παρακολούθηση υγείας → επαναφορά με ένα κλικ.
- **Η επικάλυψη προσαρμοσμένων τροποποιήσεων** διαχειρίζεται από το πάνελ: οι τροποποιήσεις που προστέθηκαν από τον χρήστη προσγειώνονται στη βιβλιοθήκη που έχει αφαιρεθεί η διπλοεγγραφή και συνδέονται σκληρά στον διακομιστή, ώστε να επιβιώνουν από τις ενημερώσεις πακέτων. Η απενεργοποίηση είναι ευαίσθητη στην κλάση. Επειδή η βιβλιοθήκη διατηρεί κάθε build που έχει κατεβάσει, μια ενημέρωση καταγράφει το build που αντικατέστησε (`server_content.previous_*`) και μπορεί να αναιρεθεί μόνο από τοπικά αρχεία. Η απενεργοποίηση μιας τροποποίησης πακέτου γράφει την μεταβλητή περιβάλλοντος αποκλεισμού του πακέτου αντ' αυτού· το `packs.applyPack` μεταφέρει αυτήν και το υπόλοιπο της ρύθμισης του πακέτου (`PACK_TUNING_KEYS`) κατά τη διάρκεια μιας αλλαγής έκδοσης του ίδιου πακέτου, και την απορρίπτει όταν αλλάζει το πακέτο.
- **Μια αναβάθμιση έκδοσης Minecraft πρέπει να κερδηθεί.** Το `services/compat.js` σαρώνει τις τροποποιήσεις ενός διακομιστή - που επιλύονται από τις τροποποιήσεις που έχουν εγκατασταθεί από το πάνελ, στη συνέχεια τον κατάλογο πακέτων CurseForge, στη συνέχεια με hash περιεχομένου έναντι Modrinth/CurseForge - και δημιουργεί έναν πίνακα υποστήριξης (φορτωτής, έκδοση Minecraft) ανά έργο από τα `latestFilesIndexes` του CurseForge (200 έργα ανά αίτημα) και τη λίστα εκδόσεων ανά έργο του Modrinth (ένα αίτημα ανά έργο, το οποίο διατηρεί τον φορτωτή και την έκδοση ζευγαρωμένα). Ο έλεγχος ενημερώσεων προσφέρει μόνο την νεότερη έκδοση που υποστηρίζουν ΟΛΕΣ οι τροποποιήσεις, και δεν προσφέρει τίποτα καθόλου όταν η απάντηση δεν μπορεί να καθοριστεί: καμία σάρωση, σάρωση για διαφορετική έκδοση ή φορτωτή, μια που δεν ολοκληρώθηκε ποτέ, ή ένα jar που κανένα μητρώο δεν αναγνωρίζει. Οι σαρώσεις είναι μόνο χειροκίνητες, και η πρόοδός τους και τα μερικά αποτελέσματα βρίσκονται στο `version_compat` (όχι στο `services/tasks.js` στη μνήμη), οπότε μια ανανέωση ή μια επανεκκίνηση του πάνελ συνεχίζει αντί να κολλάει σε έναν περιστρεφόμενο δείκτη· το `reconcileScans()` επισημαίνει τις σαρώσεις που έχουν εγκαταλειφθεί από μια διακοπή κατά την επόμενη εκκίνηση.
- **Η έκδοση του φορτωτή τροποποιήσεων είναι μια καρφίτσα, όπως όλα τα άλλα.** Το `services/loaderPin.js` διαβάζει το εγκατεστημένο build από τον δικό του κατάλογο εγκατάστασης της εικόνας (`.forge-manifest.json` και φίλοι) και γράφει την καρφίτσα: τη μεταβλητή itzg του φορτωτή σε έναν απλό διακομιστή (`FORGE_VERSION`, …), ή `CF_MOD_LOADER_VERSION` σε ένα πακέτο CurseForge Forge ή Fabric, το οποίο αντικαθιστά την έκδοση που δηλώνει το πακέτο. Ο εγκαταστάτης CurseForge της εικόνας αγνοεί αυτήν την αντικατάσταση για το NeoForge, και τα πακέτα Modrinth και FTB δεν έχουν καμία, οπότε ο φορτωτής τους ακολουθεί το πακέτο. Το `packs.applyPack` αφαιρεί όλες τις μεταβλητές `CF_` κατά την ενημέρωση ή επαναφορά ενός πακέτου, η οποία απορρίπτει μια αντικατάσταση με τα υπόλοιπα. Μια τυποποιημένη κατασκευή ελέγχεται πρώτα έναντι της πλήρους λίστας του μητρώου (`services/loaderVersions.js`· η Forge προέρχεται από τα μεταδεδομένα maven της, τα οποία παραλείπουν αριθμούς· μια αποτυχία ελέγχεται ξανά μία φορά έναντι του ίδιου του μητρώου), στη συνέχεια η αλλαγή είναι αντίγραφο ασφαλείας → καρφίτσα (πάνω από το περιβάλλον όπως είναι μετά το αντίγραφο ασφαλείας) → επανδημιουργία.
- **Οι θύρες** εκχωρούνται από ένα βασικό σχήμα (παιχνίδι από το `PORT_GAME_START` και μετά, RCON = παιχνίδι + `PORT_RCON_OFFSET`, Bedrock από το `PORT_BEDROCK_START`), ελέγχονται για διαθεσιμότητα και δεσμεύονται στη βάση δεδομένων. Το "Κατειλημμένο" είναι η ένωση όλων των διεκδικήσεων κάθε διακομιστή (ζωντανές θύρες, συν ένα εκκρεμές ζεύγος παρακάτω), όλες οι θύρες host που δημοσιεύει οποιοδήποτε κοντέινερ Docker (`containers.publishedHostPorts`: ζωντανές συνδέσεις τρεχόντων κοντέινερ συν τις διαμορφωμένες του κάθε σταματημένου κοντέινερ, επειδή ένας έλεγχος bind του λειτουργικού συστήματος από το εσωτερικό του δικού του κοντέινερ του πάνελ βλέπει μόνο τον χώρο ονομάτων δικτύου αυτού του κοντέινερ), και ο έλεγχος του λειτουργικού συστήματος. Το μέρος του Docker αποθηκεύεται στην κρυφή μνήμη για 3 δευτερόλεπτα και οριοθετείται: μια λίστα που δεν απαντά σε 2,5 δευτερόλεπτα απορρίπτει μόνο το μέρος του Docker, και μια αργή επιθεώρηση κοστίζει μόνο τις θύρες αυτού του κοντέινερ. Οι δημιουργίες διακομιστών και το `servers.changeGamePort` επιλέγουν θύρες μέσω μιας αλυσίδας σειριοποίησης που καλύπτει μόνο την επιλογή και τη διεκδίκησή της (η εγγραφή γραμμής για μια δημιουργία, η κράτηση στη μνήμη για μια αλλαγή θύρας)· ο επιλογέας θύρας του BlueMap και οι αντικαταστάσεις επιπλέον θυρών δεν είναι σε αυτό και δεν συμβουλεύονται το Docker. Μια αλλαγή θύρας σε έναν υπάρχοντα διακομιστή (`servers.changeGamePort`, κάτω από την κλειδαριά op του διακομιστή) εφαρμόζεται αμέσως, επειδή το Docker διορθώνει τις συνδέσεις θυρών κατά τη δημιουργία του κοντέινερ: το νέο ζεύγος (RCON πάντα παιχνίδι + `PORT_RCON_OFFSET`) ελέγχεται και δεσμεύεται στη μνήμη (`ports.reserve`, τόσο το παλιό όσο και το νέο ζεύγος, τιμώνται από κάθε άλλη επιλογή) κάτω από την κλειδαριά θύρας. Απορρίπτεται (409 `PENDING_CHANGES`) ενώ άλλες ρυθμίσεις περιμένουν επανδημιουργία, οπότε επαναδημιουργεί μόνο ένα κοντέινερ που έχει ήδη εκτελεστεί, σε μια νέα θύρα· και ένας ενεργός διακομιστής αλλάζει μόνο όταν το αίτημα λέει `restart: true` (διαφορετικά 409 `NEEDS_CONFIRM`). Η εικόνα γίνεται λήψη και ελέγχεται ένα προσαρμοσμένο όνομα κοντέινερ πριν αγγιχτεί οτιδήποτε. Ένας ενεργός διακομιστής διακόπτεται· στη συνέχεια, το νέο ζεύγος γράφεται με `pending_recreate = 1` (έτσι μια κατάρρευση του πάνελ από εκεί αφήνει ένα ειλικρινές "επανδημιουργία εκκρεμεί"), το κοντέινερ αφαιρείται, επαναδημιουργείται στο νέο ζεύγος και ξεκινά. Εάν οποιοδήποτε βήμα μετά τη διακοπή αποτύχει, το `putBackOnOldPort` γράφει ξανά το παλιό ζεύγος, επαναδημιουργεί (και επανεκκινεί, αν ήταν ενεργό) σε αυτό και καταγράφει ποιο βήμα απέτυχε· το ιστορικό και οι ειδοποιήσεις λένε αν απέτυχε ακόμη και αυτό, αφήνοντας τον διακομιστή σταματημένο μέχρι κάποιος να τον ξεκινήσει. Η δυνατότητα `settings` είναι αρκετή, συμπεριλαμβανομένου του ενεργού διακομιστή. Οι μη διαχειριστές μπορούν να επιλέξουν μόνο από το `PORT_GAME_START` και πάνω. (Οι στήλες `port_*_pending` από τη μετεγκατάσταση 029 ανήκουν σε ένα προηγούμενο, μη εκδοθέν σχέδιο και δεν χρησιμοποιούνται· το 031 τις καθαρίζει.) Μια σύγκρουση κλειδαριάς απαντά 409 με `code: 'BUSY'`, την οποία οι καλούντες που επαναπροσπαθούν ελέγχουν αντί για τη διατύπωση. Μια αυτόματη επανεκκίνηση σφάλματος (`watcher.restartAfterCrash`) και ένα προγραμματισμένο αντίγραφο ασφαλείας ή εκκίνηση (`scheduler.runTaskWithRetry`) που βρίσκουν τον διακομιστή απασχολημένο με άλλη ενέργεια, προσπαθούν ξανά κάθε 20 δευτ. / 60 δευτ. για έως και 30 λεπτά, και μια ενημέρωση ή επαναφορά πακέτου επαναπροσπαθεί τα κλειδωμένα βήματά της με τον ίδιο τρόπο (`opLock.retryWhileBusy`)· μια επανεκκίνηση σφάλματος ή μια αναμονή προγραμματισμένης εκκίνησης εγκαταλείπει μόλις κάποιος έχει σταματήσει, τερματίσει ή ξεκινήσει τον διακομιστή από τότε (`events.lifecycleActionSince`), και η επανεκκίνηση σφάλματος επίσης όταν η αυτόματη επανεκκίνηση είναι απενεργοποιημένη ή ο διακομιστής έχει φύγει. Οι προγραμματισμένες επανεκκινήσεις, διακοπές και εντολές δεν επαναπροσπαθούνται, και ένα πρόγραμμα του οποίου η τελευταία εκτέλεση εξακολουθεί να περιμένει παραλείπει την επόμενη ενεργοποίησή του.
- **Οι ποσοστώσεις δίσκου** επιβάλλονται από το πάνελ επειδή το Docker δεν μπορεί να περιορίσει τη χρήση bind-mount: ο δείκτης αποθηκεύει στην κρυφή μνήμη τα μεγέθη ανά κατάλογο και οι λειτουργίες αύξησης δίσκου περιορίζονται σε αυτά.
- **Μυστικά** (κωδικοί πρόσβασης RCON, κλειδιά API, μυστικά TOTP, διεύθυνση URL webhook Discord) κρυπτογραφούνται κατά την ανάπαυση με AES-256-GCM χρησιμοποιώντας ένα αποκλειστικό τυχαίο κλειδί στο `$DATA_DIR/.secret-key` (λειτουργία `0600`, αυτόματη δημιουργία). Είναι ανεξάρτητο από το `SESSION_SECRET`· ένα κλειδί που προέρχεται από το `SESSION_SECRET` διατηρείται ως εφεδρικό μόνο για αποκρυπτογράφηση για τιμές που γράφτηκαν πριν υπάρξει το αποκλειστικό κλειδί, και το `src/services/secretsMigration.js` επανακρυπτογραφεί αυτές κάτω από το αποκλειστικό κλειδί μία φορά κατά την εκκίνηση. Ένα `.secret-key` που υπάρχει αλλά δεν αναλύεται είναι ένα σοβαρό σφάλμα εκκίνησης (δεν δημιουργείται ποτέ σιωπηλά από πάνω). Τα σχέδια αφαιρούν όλα τα μυστικά κατά την εξαγωγή.
- **`server.properties` ανήκει στο πάνελ αλλά σκιάζεται από το περιβάλλον.** Η εικόνα itzg επανεπιβεβαιώνει κάθε ιδιότητα που υποστηρίζεται από το περιβάλλον σε κάθε εκκίνηση (`OVERRIDE_SERVER_PROPERTIES` προεπιλογή true), οπότε μια τιμή που επεξεργάζεται απευθείας το πάνελ - PvP/δυσκολία Ελέγχων Κόσμου, η εναλλαγή λίστας επιτρεπόμενων, ο επεξεργαστής Αρχείων - θα αναιρεθεί σιωπηλά στην επόμενη εκκίνηση εκτός εάν αφαιρεθεί η αντίστοιχη μεταβλητή περιβάλλοντος και το κοντέινερ επαναδημιουργηθεί. Κάθε άμεση εγγραφή ιδιότητας περνά από το `writeServerProperties()` (ολόκληρο το αρχείο) ή το `setServerProperty()` (ένα κλειδί) στο `src/services/servers.js`, το οποίο ξαναγράφει ατομικά το αρχείο, καταργεί την εγγραφή της μεταβλητής περιβάλλοντος πίσω από κάθε αλλαγμένο κλειδί (μέσω του χαρακτηριστικού `prop:` στα πεδία καταλόγου, ελέγχεται σε δοκιμές έναντι των δικών του ορισμών ιδιοτήτων της εικόνας) και επισημαίνει το `pending_recreate`. Η δυσκολία γράφεται στο αρχείο καθώς και αποστέλλεται μέσω RCON, επειδή ένας αποκλειστικός διακομιστής επανεφαρμόζει την ιδιότητα `difficulty` σε κάθε εκκίνηση. Το ίδιο το Minecraft ξαναγράφει το server.properties από τις τιμές εκκίνησής του κατά την εναλλαγή `whitelist on/off`, η οποία θα αναιρούσε τις επεξεργασίες που έγιναν ενώ ο διακομιστής εκτελείται, οπότε η ενεργή εναλλαγή λίστας επιτρεπόμενων αποθηκεύει το αρχείο πρώτα και το ξαναγράφει με μόνο το `white-list` αλλαγμένο. Οι μεταβλητές περιβάλλοντος παραμένουν πλήρως διαμορφώσιμες κατά τη δημιουργία (ο οδηγός τις αποδίδει και εφαρμόζονται μία φορά)· ξεκαρφιτσώνουν μόνο την πρώτη φορά που το πάνελ επεξεργάζεται την υποκείμενη ιδιότητα. Το MOTD έχει την ίδια σύμβαση: μια άμεση επεξεργασία αρχείου `motd` το καταργεί, οπότε η τελευταία εγγραφή κερδίζει.

## Μορφές δεδομένων & καλωδίων

- **`data/panel.db`** - η βάση δεδομένων SQLite. Λαμβάνει στιγμιότυπα καθημερινά μέσω `VACUUM INTO` στο `data/backups/_panel/` (διατηρούνται τα 14 νεότερα)· το `PRAGMA integrity_check` εκτελείται κατά την εκκίνηση.
- **`data/.session-secret`** - το μυστικό υπογραφής cookie που δημιουργείται αυτόματα, δημιουργείται κατά την πρώτη εκτέλεση εάν το `SESSION_SECRET` είναι ανεπίσημο. Η διαγραφή του περιστρέφει το μυστικό (το οποίο ακυρώνει τις συνεδρίες).
- **`data/.secret-key`** - το αποκλειστικό κλειδί κρυπτογράφησης κατά την ανάπαυση 32 byte (λειτουργία `0600`), δημιουργείται αυτόματα κατά την πρώτη εκτέλεση. Ανεξάρτητο από το `SESSION_SECRET`· η διαγραφή του καθιστά όλα τα αποθηκευμένα διαπιστευτήρια μη αποκρυπτογραφήσιμα, οπότε ανήκει στα αντίγραφα ασφαλείας σας.
- **Σχέδια (`.mcserver.zip`)** - ένα zip με ένα `manifest.json` που περιγράφει τη διαμόρφωση, τους πόρους, την καρφιτσωμένη αναφορά πακέτου, τον κατάλογο επικάλυψης (πηγές URL + sha256), επιλεγμένα αρχεία διαμόρφωσης και προαιρετικά έναν κόσμο. Η εισαγωγή επανα-κατεβάζει και επαληθεύει με hash κάθε τροποποίηση και αναθέτει νέες θύρες.
- **Κοντέινερ Docker** που δημιουργούνται από το πάνελ ονομάζονται και επισημαίνονται ώστε ο watcher να μπορεί να τα βρει· το πάνελ κατέχει τον πλήρη κύκλο ζωής τους.

## Ακολουθία εκκίνησης

1. `require('./instrument')` (η σύνδεση Sentry) πριν από οτιδήποτε άλλο, στη συνέχεια `require('./preflight')` για να αποτύχει σαφώς σε μια μη υποστηριζόμενη έκδοση Node.
2. Φόρτωση διαμόρφωσης· διασφάλιση/δημιουργία `.session-secret` **και** `.secret-key`.
3. `ensureDataRoot()` - δημιουργία της διάταξης `./data`, εκκαθάριση του `tmp/`.
4. Εκτέλεση μετεγκαταστάσεων DB, στη συνέχεια `PRAGMA integrity_check` (καταγράφει δυνατά, δείχνει στο `data/backups/_panel` σε περίπτωση αποτυχίας).
5. Επανακρυπτογράφηση τυχόν παλαιών μυστικών με κλειδί `SESSION_SECRET` κάτω από το `.secret-key` (`secretsMigration`).
6. Εισαγωγή κλειδιών API από το περιβάλλον μία φορά (`apiKeys.importFromEnvOnce()`), καρφίτσωμα τυχόν διακομιστών που εξακολουθούν να φέρουν έναν μη καρφιτσωμένο επιλογέα modpack (`packPins.pinUnpinnedServers()`), επισήμανση των σαρώσεων συμβατότητας εκδόσεων που έμειναν σε εκτέλεση από μια προηγούμενη διαδικασία ως διακοπείσες (`compat.reconcileScans()`), στη συνέχεια σπόρος αρχικών σχεδίων (προστατευμένα).
7. Εκκίνηση του διακομιστή HTTP + WS. Σε μια εκτεθειμένη σύνδεση, εκτύπωση του PIN πρώτης εκτέλεσης `/setup`.
8. Εγκατάσταση του φύλακα χρόνου εκτέλεσης μετά την εκκίνηση (πιάνει μη αναμενόμενα σφάλματα· το `MSM_EXIT_ON_FATAL=1` το καθιστά σκληρή έξοδο για επιβλεπόμενες αναπτύξεις).
9. Εκκίνηση υπηρεσιών παρασκηνίου: μεσολαβητής WS, δείκτης αποθήκευσης, watchers σφαλμάτων + απογραφής, προγραμματιστής, γέφυρα συμβάντων Discord, watcher εμβέλειας chatbot και ο **χρονοδιακόπτης ημερήσιας συντήρησης** (καθαρισμός παλιών γραμμών αναλυτικών στοιχείων, μεταγραφών chatbot, ιστορικού συμβάντων (365 ημερών) και γραμμών cache API, στη συνέχεια στιγμιότυπο του `panel.db`).
10. Αρχικοποίηση του Docker **στο παρασκήνιο**. Το UI είναι πλήρως χρησιμοποιήσιμο ενώ ο δαίμονας είναι κάτω· οι λειτουργίες Docker ενεργοποιούνται όταν γίνει προσβάσιμος. Μόλις συνδεθεί, το `refreshStatuses({ boot })` εναρμονίζει τις αποθηκευμένες στην κρυφή μνήμη καταστάσεις, εκπέμπει ένα εφάπαξ συμβάν `offline-after-restart` για έναν διακομιστή που ήταν ενεργός πριν από την επανεκκίνηση του πάνελ και δεν θα επανέλθει, και ο βρόχος εκκίνησης ξεκινά τους διακομιστές `auto_start` συν ανακτά τους διακομιστές `auto_restart` που βρέθηκαν σε σφάλμα κατά τη διάρκεια της διακοπής (σεβόμενος την καθυστέρηση βρόχου σφαλμάτων).

> Η σειρά instrument-before-preflight είναι μια σκόπιμη ανταλλαγή: επιτρέπει σε μια μελλοντική καλωδίωση Sentry να επιδιορθώσει τον χρόνο εκτέλεσης πρώτα, με κόστος ένα ελαφρώς λιγότερο φιλικό μήνυμα σε ένα πραγματικά παλιό Node.

## Δημιουργία αγωγού

`pnpm run build` = `build:css` (Tailwind → `public/css/app.css`) + `build:js` (esbuild → `public/dist/js/`, ESM με διαχωρισμό κώδικα). Το `postinstall` εκτελεί **μόνο CSS**. Τα `public/css/app.css` και `public/dist/` είναι αντικείμενα build που αγνοούνται από το git· το στάδιο build του Dockerfile εκτελεί το πλήρες `pnpm run build` και αντιγράφει το `public/` στο κοντέινερ χρόνου εκτέλεσης. Τα στατικά στοιχεία εξυπηρετούνται με `immutable`/μακρά cache για αρχεία με δακτυλικά αποτυπώματα, σύντομη cache για CSS/JS, και `no-cache` για HTML και `/api`.
