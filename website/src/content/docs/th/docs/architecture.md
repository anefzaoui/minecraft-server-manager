Minecraft Server Manager เป็นแอปพลิเคชัน Node.js แบบ Single-process ที่เรนเดอร์ฝั่งเซิร์ฟเวอร์ จัดการเซิร์ฟเวอร์ Minecraft ที่ทำงานเป็นคอนเทนเนอร์ Docker โดยใช้ image [itzg/docker-minecraft-server](https://github.com/itzg/docker-minecraft-server) สื่อสารกับ Docker daemon ผ่าน API (ไม่เคยเรียกใช้คำสั่ง `docker` CLI ผ่าน shell)

## รูปแบบการทำงาน

- **Express + Handlebars** ใช้เรนเดอร์หน้าเว็บฝั่งเซิร์ฟเวอร์ ไม่มี SPA; JavaScript ใน `public/js/` เป็นการปรับปรุงแบบ Progressive Enhancement ที่เขียนด้วยมือ มีขั้นตอน esbuild (`pnpm run build:js`) เพื่อรวมและย่อขนาดเป็น `public/dist/js/`; แอปจะเสิร์ฟ bundle นั้นเมื่อมีอยู่ และ source ดั้งเดิมหากไม่มี ดังนั้นการรันในโหมดพัฒนาโดยไม่มีการ build ก็ยังคงทำงานได้
- **`node:sqlite`** (ฝังมากับ Node; แผงควบคุมต้องการ Node ≥ 24) เป็นฐานข้อมูล แบบ Synchronous, ไม่มี native modules, โหมด WAL มีตัวจัดการการย้ายข้อมูลเวอร์ชันเล็กๆ ที่ใช้ `src/db/migrations/*` เมื่อบูต Prepared statements ถูกแคชไว้ใน `src/db/index.js` โดยใช้ข้อความ SQL เป็นคีย์
- **`ws`** ใช้สำหรับการสตรีมคอนโซลและสถิติแบบสด ทั้งสองอย่างเป็นแบบ **Brokered**: หนึ่ง upstream `docker logs --follow` (หรือ `docker stats`) ต่อเซิร์ฟเวอร์ หนึ่งครั้ง แล้วกระจายไปยังแท็บที่เชื่อมต่อทั้งหมด แทนที่จะเป็นหนึ่ง upstream ต่อผู้ชมแต่ละคน ตัวจัดการคอนโซลจะเก็บบัฟเฟอร์ replay ขนาดเล็กสำหรับแท็บที่เข้าร่วมล่าช้า และจะตัดผู้สมัครสมาชิกที่ socket หลุดไปไกลเกินไป แทนที่จะทำให้สตรีมที่ใช้ร่วมกันล่าช้า
- **dockerode** เป็นวิธีเดียวที่แอปใช้สื่อสารกับ Docker Endpoint จะถูกตรวจจับอัตโนมัติสำหรับแต่ละแพลตฟอร์ม (Windows named pipe เทียบกับ unix socket)
- **สถานะที่คงอยู่ทั้งหมดจะอยู่ในไดเรกทอรีเดียว** (`$DATA_DIR`, ค่าเริ่มต้นคือ `./data`) การคัดลอกไดเรกทอรีนั้นจะย้ายแผงควบคุมทั้งหมด

## การจัดชั้น

การพึ่งพาไหลไปในทิศทางเดียว:

```
                 ┌─────────────────────────────┐
   HTTP  ───────▶│  web/routes/*  (+ middleware)│   แยกวิเคราะห์และตรวจสอบความถูกต้องของอินพุต, จัดรูปแบบการตอบกลับ
                 └──────────────┬──────────────┘
                                │
                 ┌──────────────▼──────────────┐
                 │         services/*          │   ตรรกะทางธุรกิจ (ฟีเจอร์จริง)
                 └───┬─────────┬─────────┬─────┘
                     │         │         │
        ┌────────────▼──┐ ┌────▼────┐ ┌──▼──────────┐
        │   docker/*    │ │  db/*   │ │  storage/*  │   โครงสร้างพื้นฐาน
        └───────────────┘ └─────────┘ └─────────────┘
```

- **`web/routes/`** - หนึ่ง router ต่อโดเมน (`servers`, `players`, `worlds`, `crashes`, `blueprints`, `files`, …) ถูก mount ใน `web/app.js` Router จะตรวจสอบความถูกต้องด้วย zod, เรียกใช้ service, และคืนค่า JSON หรือเรนเดอร์ view ตรรกะทางธุรกิจไม่ควรอยู่ที่นี่ มีสอง router ที่ mount ใน **โซนสาธารณะ** ก่อน `requireAuth`: `routes/status.js` (หน้าสถานะ HTML ต่อเซิร์ฟเวอร์ที่เลือกเปิดใช้งาน) และ `routes/apiV1.js` (`/api/v1`, API JSON แบบอ่านอย่างเดียวที่รับรองความถูกต้องด้วยโทเค็น Bearer ที่ออกโดยผู้ดูแลระบบจาก `services/apiTokens.js`, ปิดใช้งานเว้นแต่จะเปิดใช้งานในการตั้งค่า; ดู `docs/public-api.md`)
- **`services/`** - หัวใจของแอป แต่ละ service จะเป็นเจ้าของโดเมนหนึ่งรายการและอาจพึ่งพาโครงสร้างพื้นฐานและ service อื่นๆ
- **`docker/`** - ตัวห่อหุ้ม dockerode: `connect` (การตรวจจับ endpoint + สุขภาพของ daemon), `containers` (สร้าง/เริ่ม/หยุด/สร้างใหม่พร้อม bind mounts, การจำกัดหน่วยความจำ/CPU, และ labels), `logs`, `stats`, `images`, และ `watcher` ที่แปลงเหตุการณ์ Docker เป็นประวัติ + การตรวจจับข้อขัดข้อง
- **`db/`** - ตัวห่อหุ้ม SQLite และตัวจัดการการย้ายข้อมูล
- **`storage/`** - การ bootstrap `./data`, **ตัวป้องกันเส้นทาง** (`safeJoin`, แกนหลักด้านความปลอดภัยของไฟล์), และตัวทำดัชนีขนาดพื้นหลัง + การบังคับใช้โควต้า

ส่วนที่ตัดขวาง:

- **`config/`** - การกำหนดค่าสภาพแวดล้อมพร้อมกับ **แคตตาล็อกฟิลด์**: แหล่งความจริงเดียวสำหรับการตั้งค่าเซิร์ฟเวอร์ ตัวแปรสภาพแวดล้อม itzg ทุกตัวจะถูกจัดทำเป็นแคตตาล็อก (label, help, type, unit, default, validation, section, danger flags) Wizard, ฟอร์มการตั้งค่า, และการตรวจสอบความถูกต้องด้วย zod ทั้งหมดถูกสร้างขึ้นจากสิ่งนี้ ดังนั้นการเปิดเผยการตั้งค่าใหม่จึงเป็นการเปลี่ยนแปลงข้อมูล ไม่ใช่การเดินสาย UI ใหม่
- **`events/`** - `recordEvent()` เป็นจุดเข้าใช้งานเดียวสำหรับบันทึกประวัติ; เหตุการณ์วงจรชีวิตยังบันทึกส่วนที่ตัดตอนมาจากคอนโซลล็อกไปยัง `data/logs/<id>/events/` ด้วย
- **`ws/`** - WebSockets คอนโซล + สถิติที่รับรองความถูกต้อง (ตรวจสอบ cookie เซสชันเมื่ออัปเกรด, ตรวจสอบ `Origin` เพื่อบล็อกการโจมตีแบบ cross-site hijacking), จัดการต่อเซิร์ฟเวอร์ (ดู "รูปแบบการทำงาน")
- **`logger.js` + `instrument.js`** - `require('./logger')(label)` จะคืนค่า logger [Pino](https://getpino.io) ต่อโมดูล; ระดับจาก `LOG_LEVEL`, `makeFailureThrottle()` จะเก็บ loop พื้นหลังที่ล้มเหลวอย่างต่อเนื่องไว้ที่บรรทัด log หนึ่งบรรทัดบวกกับบรรทัด "recovered" `src/utils/logSanitize.js` จะลบ keys ที่มีลักษณะเหมือนข้อมูลลับและโทเค็น webhook ออกจากข้อมูลเมตาที่มีโครงสร้าง; `src/config/logLevel.js` เป็นรายการที่อนุญาตระดับที่ใช้ร่วมกัน (แยกไว้เพื่อหลีกเลี่ยงวงจรการ require กับ `config`) `src/instrument.js` เป็นช่องทาง Sentry ที่ไม่ได้ใช้งาน โหลดเป็นอันดับแรกใน `src/server.js` `src/web/middleware/requestLog.js` เขียนบรรทัด access-log หนึ่งบรรทัดต่อ request (ข้าม `/healthz` และ static assets) ESLint บังคับใช้ `no-console` ภายใต้ `src/**` โดยมี `preflight.js`, `instrument.js`, และ `config/index.js` ได้รับการยกเว้น (ทำงานก่อนที่ logger จะมีอยู่)
- **การจำกัดอัตรา** - `src/web/middleware/rateLimit.js` วาง `express-rate-limit` ไว้หน้า `/api` (`RATE_LIMIT_API_PER_MIN`, ค่าเริ่มต้น 1200) และการ POST สำหรับการเข้าสู่ระบบ / 2FA / การตั้งค่า (`RATE_LIMIT_AUTH_PER_15MIN`, ค่าเริ่มต้น 100); `0` จะปิดใช้งานตัวจำกัดอัตรา มันใช้ `req.ip` เป็นคีย์ ดังนั้น `TRUST_PROXY` จึงมีความสำคัญหลังพร็อกซี `/api/v1` มีตัวจำกัดอัตราต่อโทเค็นของตัวเอง (`RATE_LIMIT_PUBLIC_API_PER_MIN`, ค่าเริ่มต้น 120) โดยใช้ hash ของโทเค็น Bearer เป็นคีย์พร้อม fallback เป็น IP มีตัวนับแบบ soft ต่อบัญชีแยกต่างหากใน `src/web/middleware/auth.js` จัดการการล็อกบัญชี (ต่อ IP และทั่วทั้งบัญชี, ค่อยๆ ลดลง)

## พฤติกรรมโดเมนหลัก

- **Modpacks จะถูกปักหมุดเสมอ** Image จะอัปเกรดแพ็คที่ไม่ได้ปักหมุดโดยอัตโนมัติทุกครั้งที่รีสตาร์ท ดังนั้นแผงควบคุมจะแก้ไข "latest" ให้เป็น ID เวอร์ชันที่แน่นอนเมื่อติดตั้งและปักหมุดไว้ การอัปเกรดเป็นกระบวนการที่ดำเนินการอย่างชัดเจน (`updates/`): ดูตัวอย่าง → สำรองข้อมูลก่อนอัปเดต → หยุดอย่างนุ่มนวล → ปักหมุดใหม่ → สร้างใหม่ → ตรวจสอบสุขภาพ → คืนค่าได้ในคลิกเดียว
- **Overlay mod แบบกำหนดเอง** ถูกจัดการโดยแผงควบคุม: mod ที่ผู้ใช้เพิ่มจะอยู่ในไลบรารีที่ deduplicated และจะถูก hard-link เข้าไปในเซิร์ฟเวอร์เพื่อให้รอดจากการอัปเดตแพ็ค การปิดใช้งานจะคำนึงถึงคลาส
- **พอร์ต** จะถูกจัดสรรจากแผนผังพื้นฐาน (เกมจาก `PORT_GAME_START` ขึ้นไป, RCON = เกม + `PORT_RCON_OFFSET`, Bedrock จาก `PORT_BEDROCK_START`) ตรวจสอบความพร้อมใช้งาน และจองไว้ในฐานข้อมูล
- **โควต้าดิสก์** จะถูกบังคับใช้โดยแผงควบคุมเนื่องจาก Docker ไม่สามารถจำกัดการใช้งาน bind-mount ได้: ตัวทำดัชนีจะแคชขนาดต่อไดเรกทอรี และการดำเนินการเพิ่มขนาดดิสก์จะถูกจำกัดโดยสิ่งเหล่านี้
- **ข้อมูลลับ** (รหัสผ่าน RCON, คีย์ API, ความลับ TOTP, URL Discord webhook) จะถูกเข้ารหัสขณะพักด้วย AES-256-GCM โดยใช้คีย์สุ่มเฉพาะที่ `$DATA_DIR/.secret-key` (โหมด `0600`, สร้างขึ้นอัตโนมัติ) แยกต่างหากจาก `SESSION_SECRET`; คีย์ที่ได้จาก `SESSION_SECRET` จะถูกเก็บไว้เป็น fallback สำหรับการถอดรหัสเท่านั้นสำหรับค่าที่เขียนก่อนที่คีย์เฉพาะจะมีอยู่ และ `src/services/secretsMigration.js` จะเข้ารหัสค่าเหล่านั้นใหม่ภายใต้คีย์เฉพาะเมื่อบูต `.secret-key` ที่มีอยู่แต่ไม่สามารถแยกวิเคราะห์ได้ถือเป็นข้อผิดพลาดร้ายแรงเมื่อบูต (จะไม่สร้างใหม่โดยอัตโนมัติโดยไม่แจ้งให้ทราบ) Blueprints จะลบข้อมูลลับทั้งหมดออกเมื่อส่งออก

## รูปแบบข้อมูลและข้อมูลบนสายส่ง

- **`data/panel.db`** - ฐานข้อมูล SQLite ถูก snapshot ทุกวันผ่าน `VACUUM INTO` ไปยัง `data/backups/_panel/` (เก็บไว้ 14 รายการล่าสุด); `PRAGMA integrity_check` จะทำงานเมื่อบูต
- **`data/.session-secret`** - ความลับในการลงนามคุกกี้ที่สร้างขึ้นอัตโนมัติ สร้างขึ้นเมื่อรันครั้งแรกหาก `SESSION_SECRET` ไม่ได้ตั้งค่า การลบจะหมุนเวียนความลับ (ซึ่งจะทำให้เซสชันไม่ถูกต้อง)
- **`data/.secret-key`** - คีย์การเข้ารหัสขณะพัก 32 ไบต์เฉพาะ (โหมด `0600`) สร้างขึ้นอัตโนมัติเมื่อรันครั้งแรก แยกต่างหากจาก `SESSION_SECRET`; การลบจะทำให้ข้อมูลลับที่จัดเก็บไว้ทั้งหมดไม่สามารถถอดรหัสได้ ดังนั้นจึงควรเก็บไว้พร้อมกับการสำรองข้อมูลของคุณ
- **Blueprints (`.mcserver.zip`)** - ไฟล์ zip ที่มี `manifest.json` อธิบายการกำหนดค่า, ทรัพยากร, การอ้างอิงแพ็คที่ปักหมุด, manifest ของ overlay (URL ต้นทาง + sha256), ไฟล์กำหนดค่าที่เลือก, และอาจมี world ด้วย การนำเข้าจะดาวน์โหลดใหม่และตรวจสอบ hash ของ mod แต่ละตัว และกำหนดพอร์ตใหม่
- **คอนเทนเนอร์ Docker** ที่สร้างโดยแผงควบคุมจะถูกตั้งชื่อและติดป้ายกำกับเพื่อให้ watcher สามารถค้นหาได้ แผงควบคุมจะเป็นเจ้าของวงจรชีวิตทั้งหมด

## ลำดับการบูต

1. `require('./instrument')` (ช่องทาง Sentry) ก่อนสิ่งอื่นใด จากนั้น `require('./preflight')` เพื่อแจ้งข้อผิดพลาดอย่างชัดเจนเมื่อเวอร์ชัน Node ไม่รองรับ
2. โหลดการกำหนดค่า; ตรวจสอบ/สร้าง `.session-secret` **และ** `.secret-key`
3. `ensureDataRoot()` - สร้างโครงสร้าง `./data`, ล้าง `tmp/`
4. รันการย้ายข้อมูลฐานข้อมูล จากนั้น `PRAGMA integrity_check` (จะบันทึกเสียงดัง, ชี้ไปที่ `data/backups/_panel` หากเกิดความล้มเหลว)
5. เข้ารหัสข้อมูลลับที่ใช้คีย์ `SESSION_SECRET` แบบเก่าใหม่ภายใต้ `.secret-key` (`secretsMigration`)
6. ใส่ blueprints เริ่มต้น (ได้รับการป้องกัน)
7. เริ่มเซิร์ฟเวอร์ HTTP + WS เมื่อ bind ถูกเปิดเผย จะแสดง PIN สำหรับการตั้งค่าครั้งแรก `/setup`
8. ติดตั้งตัวป้องกันรันไทม์หลังการบูต (จับข้อผิดพลาดที่ไม่ได้จัดการ; `MSM_EXIT_ON_FATAL=1` จะทำให้เกิดการออกอย่างถาวรสำหรับการปรับใช้ที่ได้รับการดูแล)
9. เริ่มบริการพื้นหลัง: ตัวจัดการ WS, ตัวทำดัชนีพื้นที่จัดเก็บ, ตัวตรวจสอบข้อขัดข้อง + สินค้าคงคลัง, ตัวจัดตารางเวลา, สะพานเชื่อมเหตุการณ์ Discord, และ **ตัวจับเวลาการบำรุงรักษารายวัน** (ลบแถววิเคราะห์เก่า + snapshot `panel.db`)
10. เริ่มต้น Docker **ในพื้นหลัง** UI สามารถใช้งานได้อย่างเต็มที่ในขณะที่ daemon ยังไม่พร้อมใช้งาน ฟีเจอร์ Docker จะทำงานเมื่อสามารถเข้าถึงได้ เมื่อเชื่อมต่อแล้ว `refreshStatuses({ boot })` จะปรับสถานะที่แคชให้สอดคล้องกัน, ปล่อยเหตุการณ์ `offline-after-restart` ครั้งเดียวสำหรับเซิร์ฟเวอร์ที่เปิดอยู่ก่อนที่แผงควบคุมจะรีสตาร์ทและจะไม่ถูกนำกลับมา, และ loop การบูตจะเริ่มเซิร์ฟเวอร์ `auto_start` บวกกับการกู้คืนเซิร์ฟเวอร์ `auto_restart` ที่พบว่าขัดข้องระหว่างช่วงที่ระบบไม่พร้อมใช้งาน (โดยคำนึงถึงการหน่วงเวลาข้อขัดข้อง)

> ลำดับการ instrument-ก่อน-preflight เป็นการแลกเปลี่ยนที่จงใจ: ช่วยให้สามารถแก้ไข runtime ด้วยการเดินสาย Sentry ในอนาคตได้ก่อน โดยแลกกับการแสดงข้อความที่เป็นมิตรน้อยลงเล็กน้อยบน Node ที่เก่ามาก

## ไปป์ไลน์การสร้าง

`pnpm run build` = `build:css` (Tailwind → `public/css/app.css`) + `build:js` (esbuild → `public/dist/js/`, ESM พร้อม code-splitting) `postinstall` จะรันเฉพาะ CSS เท่านั้น `public/css/app.css` และ `public/dist/` เป็น artifact ที่ถูก gitignore; ขั้นตอนการสร้าง Dockerfile จะรัน `pnpm run build` เต็มรูปแบบและคัดลอก `public/` เข้าไปใน runtime image Static assets จะถูกเสิร์ฟแบบ `immutable`/long-cache สำหรับไฟล์ที่มี fingerprint, short-cache สำหรับ CSS/JS, และ `no-cache` สำหรับ HTML และ `/api`
