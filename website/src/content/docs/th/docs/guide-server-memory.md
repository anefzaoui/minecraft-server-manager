คำตอบสั้นๆ สำหรับเซิร์ฟเวอร์ที่จะใช้งานจริง:

| สิ่งที่คุณกำลังรัน                            | Java heap   | จัดสรรให้เครื่อง |
| --------------------------------------------- | ----------- | ---------------- |
| Vanilla หรือ Paper, ผู้เล่นสูงสุด 10 คน       | 2 GB        | 4 GB             |
| Paper พร้อมปลั๊กอิน, ผู้เล่น 10 ถึง 30 คน     | 4 GB        | 6 GB             |
| Mod pack ขนาดเล็ก, 40 ถึง 80 mods             | 4 GB        | 6 GB             |
| Mod pack ขนาดใหญ่, 150 ถึง 300 mods           | 6 ถึง 8 GB  | 10 GB            |
| GregTech New Horizons และตัวอื่นๆ ที่คล้ายกัน | 8 ถึง 12 GB | 16 GB            |

ตัวเลขสองตัว ไม่ใช่ตัวเดียว นี่คือส่วนที่คู่มือส่วนใหญ่ข้ามไป และเป็นเหตุผลที่ผู้คนซื้อเซิร์ฟเวอร์ 4 GB, จัดสรร Java 4 GB, แล้วก็ดูมันล่ม

## Heap และเครื่องเป็นตัวเลขที่ต่างกัน

Java heap (`-Xmx`) คือปริมาณหน่วยความจำที่เกมสามารถใช้สำหรับโลก, เอนทิตี้, และข้อมูล mod ได้ เครื่อง หรือคอนเทนเนอร์, ต้องเก็บ heap นั้น **บวกกับ** ทุกอย่างที่ Java ต้องการ: ข้อมูลเมตาคลาส, thread stack, การจัดการ garbage collector, network buffer, และตัว JVM เอง ค่าใช้จ่ายเพิ่มเติมนี้ประมาณ 0.5 ถึง 1.5 GB สำหรับเซิร์ฟเวอร์ modded

หาก heap เท่ากับหน่วยความจำของเครื่อง, เคอร์เนลจะฆ่าเซิร์ฟเวอร์ทันทีที่ Java พยายามใช้ส่วนที่เกินมา ใน Docker สิ่งนี้จะแสดงเป็น exit code 137, และใน log จะไม่มีอะไรเลย: กระบวนการจะหายไปกลางคัน ผู้คนมักจะโทษ mod

กฎที่ปลอดภัย: **heap บวก 25 เปอร์เซ็นต์, และอย่างน้อยหนึ่งกิกะไบต์สำรอง** Heap ขนาด 8 GB ต้องการเครื่องขนาด 10 GB

## RAM มากขึ้นไม่ใช่ประสิทธิภาพที่มากขึ้น

Minecraft ส่วนใหญ่ทำงานแบบ single-thread การให้ mod pack 40 ตัว 16 GB ไม่ได้ทำให้ chunk สร้างเร็วขึ้น; แต่มันทำให้การหยุดทำงานของ garbage collection แต่ละครั้งนานขึ้น เพราะมีอะไรให้ตรวจสอบมากขึ้น เซิร์ฟเวอร์ที่กระตุกทุกๆ สามสิบวินาที มักจะเป็นเซิร์ฟเวอร์ที่มี heap มากเกินไป, ไม่ใช่มากเกินไป

เพิ่ม heap เมื่อคุณเห็นสิ่งเหล่านี้, และไม่ใช่กรณีอื่น:

- `java.lang.OutOfMemoryError: Java heap space` ใน log
- "Can't keep up! Is the server overloaded?" ซ้ำๆ พร้อมกับการหยุดทำงานของ garbage collection ใน timings
- การใช้หน่วยความจำที่ปีนขึ้นไปจนสุดเพดานและค้างอยู่ที่นั่นเป็นชั่วโมง

## ทำไมเซิร์ฟเวอร์ของคุณจึงแสดง 12 GB ที่ใช้งานอยู่ ในขณะที่ไม่มีใครออนไลน์

เพราะคุณสั่งให้มันทำเช่นนั้น ค่าเริ่มต้นสองอย่างทำงานร่วมกัน:

1. Docker image ทั่วไปตั้งค่า heap เริ่มต้นให้เท่ากับค่าสูงสุด, ดังนั้น `-Xms` และ `-Xmx` จึงเป็นตัวเลขของคุณทั้งคู่ Java จะจองพื้นที่ทั้งหมดทันที แทนที่จะค่อยๆ เพิ่มขึ้น
2. ชุด Aikar flag ที่ได้รับความนิยมรวมถึง `-XX:+AlwaysPreTouch`, ซึ่งจะเข้าถึงทุกหน้าของ heap นั้นเมื่อเริ่มต้น เพื่อให้หน้าเหล่านั้นถูกจัดสรรจริงๆ เป็นการตัดสินใจที่จงใจ: แลกกับการบูตที่ช้าลงและตัวเลขการใช้งานขณะไม่ได้ใช้งานที่สูง เพื่อลดการหยุดทำงานในภายหลัง

วัดบน Paper 1.21.1 ด้วย heap ขนาด 2 GB ในคอนเทนเนอร์ขนาด 4 GB, สุ่มตัวอย่างเป็นเวลาสามนาทีหลังจากโหลดโลกเสร็จ:

| การตั้งค่า                            | Resident memory |
| ------------------------------------- | --------------- |
| ไม่มี flags                           | 2.60 GiB        |
| Aikar flags                           | 2.59 GiB        |
| Aikar flags โดยไม่มี `AlwaysPreTouch` | 1.95 GiB        |
| Aikar flags ด้วย heap เริ่มต้น 512 MB | 1.38 GiB        |
| ไม่มี flags ด้วย heap เริ่มต้น 512 MB | 1.25 GiB        |

ดังนั้นเซิร์ฟเวอร์ที่ "ใช้" 12 GB ขณะไม่ได้ใช้งาน มักจะเป็น heap ขนาด 12 GB ที่ถูก pre-touched, ไม่ใช่ memory leak การตรวจสอบของคุณอ่านค่าถูกต้อง; แค่ตัวเลขนั้นไม่ได้มีความหมายตามที่คุณคิด

หากคุณต้องการตัวเลขการใช้งานขณะไม่ได้ใช้งานที่แท้จริง, ให้ตั้งค่า heap เริ่มต้นให้ต่ำกว่าค่าสูงสุด คุณจะต้องแลกกับการเก็บขยะที่มากขึ้นในช่วงแรก หากคุณต้องการ frame time ที่คงที่, ปล่อยมันไว้และหยุดดูที่กราฟ

## ผู้เล่นมีความสำคัญน้อยกว่าที่คุณคิด

การเพิ่มผู้เล่นจาก 10 เป็น 20 คน ใช้ทรัพยากรน้อยกว่าการเพิ่ม mod ห้าสิบตัว ผู้เล่นส่วนใหญ่จะเพิ่มเอนทิตี้และ chunk ที่โหลด, ซึ่งเพิ่มขึ้นอย่างค่อยเป็นค่อยไป Mod จะเพิ่มข้อมูลคลาส, registry, ฟีเจอร์การสร้างโลก, และ cache ของตัวเอง, ซึ่งไม่ได้เพิ่มขึ้นอย่างค่อยเป็นค่อยไป ให้คำนึงถึงขนาดของ mod pack ก่อน, จากนั้นค่อยเพิ่มประมาณ 100 ถึง 200 MB ต่อผู้เล่นปกติบนเซิร์ฟเวอร์ modded

ระยะการมองเห็น (View distance) เป็นอีกปัจจัยสำคัญ การลดจาก 12 เป็น 8 chunk สามารถประหยัดหนึ่งกิกะไบต์บนเซิร์ฟเวอร์ที่มีผู้เล่นจำนวนมาก และแทบไม่มีผลกับการเล่น

## ใน Minecraft Server Manager

เซิร์ฟเวอร์แต่ละเครื่องมีสองช่องแยกกัน, **Java heap** และ **container memory limit**, เพราะเป็นคำถามที่แตกต่างกัน ตัวช่วยสร้างการสร้างจะตั้งค่า container limit ให้สูงกว่า heap 50 เปอร์เซ็นต์ให้คุณ, และแผงควบคุมจะปฏิเสธที่จะบันทึกเซิร์ฟเวอร์ที่ container limit ไม่สูงกว่า heap, เพราะการตั้งค่าแบบนั้นจะจบลงด้วย exit code 137 แทนที่จะเป็นข้อความแสดงข้อผิดพลาด

มิเตอร์วัดหน่วยความจำบนเซิร์ฟเวอร์จะแสดงสิ่งที่คอนเทนเนอร์ใช้งานจริง, พร้อมหมายเหตุเมื่อ heap ถูกจองไว้ล่วงหน้า, ดังนั้น heap ที่ถูก pre-touched จะไม่ถูกอ่านว่าเป็น memory leak เซิร์ฟเวอร์ที่เคอร์เนลฆ่าเนื่องจากหน่วยความจำจะถูกบันทึกไว้ในประวัติอย่างถูกต้อง, แทนที่จะเป็นการ crash ที่ไม่ทราบสาเหตุ
