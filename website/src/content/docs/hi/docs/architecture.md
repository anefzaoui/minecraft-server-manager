Minecraft Server Manager एक सिंगल-प्रोसेस, सर्वर-रेंडर्ड Node.js एप्लिकेशन है। यह
[itzg/docker-minecraft-server](https://github.com/itzg/docker-minecraft-server) इमेज का उपयोग करके Docker कंटेनर के रूप में चलने वाले Minecraft सर्वर का प्रबंधन करता है, जो Docker डेमन के साथ उसके API पर बात करता है (कभी भी `docker` CLI को शेल आउट करके नहीं)।

## रनटाइम आकार

- **Express + Handlebars** सर्वर-साइड पेज रेंडर करते हैं। कोई SPA नहीं है; `public/js/` में ब्राउज़र JS हाथ से लिखा गया प्रोग्रेसिव एन्हांसमेंट है। एक esbuild स्टेप (`pnpm run build:js`) इसे बंडल और मिनिफाई करके `public/dist/js/` में डालता है; ऐप उस बंडल को तब सर्व करता है जब वह मौजूद होता है और अन्यथा रॉ सोर्स, इसलिए बिल्ड के बिना एक देव रन भी काम करता है।
- **`node:sqlite`** (Node में निर्मित; पैनल को Node ≥ 24 की आवश्यकता है) डेटाबेस है - सिंक्रोनस, शून्य नेटिव मॉड्यूल, WAL मोड। एक छोटा संस्करणित-माइग्रेशन रनर बूट पर `src/db/migrations/*` लागू करता है। तैयार स्टेटमेंट `src/db/index.js` में SQL टेक्स्ट पर की के रूप में कैश किए जाते हैं।
- **`ws`** लाइव कंसोल और आँकड़े स्ट्रीम ले जाता है। दोनों **ब्रोकर किए जाते हैं**: प्रति सर्वर एक अपस्ट्रीम `docker logs --follow` (या `docker stats`), एक बार डीमक्स किया जाता है और हर कनेक्टेड टैब पर फैलाया जाता है, बजाय प्रति दर्शक एक अपस्ट्रीम के। कंसोल ब्रोकर देर से जुड़ने वाले टैब के लिए एक छोटा रीप्ले बफर रखता है और साझा स्ट्रीम को धीमा करने के बजाय बहुत पीछे गिरने वाले सब्सक्राइबर को छोड़ देता है।
- **dockerode** एकमात्र तरीका है जिससे ऐप Docker से बात करता है। एंडपॉइंट प्रति प्लेटफ़ॉर्म (Windows नामित पाइप बनाम यूनिक्स सॉकेट) स्वचालित रूप से पता लगाया जाता है।
- **सभी स्थायी स्थिति एक निर्देशिका के तहत रहती है** (`$DATA_DIR`, डिफ़ॉल्ट `./data`)। उस निर्देशिका को कॉपी करने से पूरा पैनल माइग्रेट हो जाता है।

## लेयरिंग

निर्भरताएँ एक दिशा में प्रवाहित होती हैं:

```
                 ┌─────────────────────────────┐
   HTTP  ───────▶│  web/routes/*  (+ middleware)│   इनपुट को पार्स और मान्य करें, प्रतिक्रियाओं को आकार दें
                 └──────────────┬──────────────┘
                                │
                 ┌──────────────▼──────────────┐
                 │         services/*          │   डोमेन लॉजिक (वास्तविक सुविधाएँ)
                 └───┬─────────┬─────────┬─────┘
                     │         │         │
        ┌────────────▼──┐ ┌────▼────┐ ┌──▼──────────┐
        │   docker/*    │ │  db/*   │ │  storage/*  │   इंफ्रास्ट्रक्चर
        └───────────────┘ └─────────┘ └─────────────┘
```

- **`web/routes/`** - प्रति डोमेन एक राउटर (`servers`, `players`, `worlds`, `crashes`, `blueprints`, `files`, …), `web/app.js` में माउंट किया गया। राउटर zod के साथ मान्य करते हैं, एक सेवा को कॉल करते हैं, और JSON लौटाते हैं या एक व्यू रेंडर करते हैं। व्यावसायिक तर्क यहाँ नहीं होना चाहिए। दो राउटर **सार्वजनिक क्षेत्र** में माउंट किए जाते हैं, `requireAuth` से पहले: `routes/status.js` (प्रति-सर्वर HTML स्थिति पृष्ठ ऑप्ट-इन) और `routes/apiV1.js` (`/api/v1`, `services/apiTokens.js` से एडमिन-मिंटेड बेयरर टोकन द्वारा प्रमाणित एक रीड-ओनली JSON API, सेटिंग्स में सक्षम होने पर बंद; `docs/public-api.md` देखें)।
- **`services/`** - ऐप का दिल। प्रत्येक सेवा एक डोमेन का मालिक है और इंफ्रास्ट्रक्चर और अन्य सेवाओं पर निर्भर हो सकती है।
- **`docker/`** - dockerode रैपर: `connect` (एंडपॉइंट डिटेक्शन + डेमन स्वास्थ्य), `containers` (बाइंड माउंट, मेमोरी/सीपीयू सीमा, और लेबल के साथ बनाएं/शुरू/बंद/पुनः बनाएं), `logs`, `stats`, `images`, और एक `watcher` जो Docker घटनाओं को इतिहास + क्रैश डिटेक्शन में बदलता है।
- **`db/`** - SQLite रैपर और माइग्रेशन रनर।
- **`storage/`** - `./data` बूटस्ट्रैप, **पाथ गार्ड** (`safeJoin`, फ़ाइल-सुरक्षा बैकबोन), और पृष्ठभूमि आकार-इंडेक्सर + कोटा प्रवर्तन।

क्रॉस-कटिंग:

- **`config/`** - पर्यावरण कॉन्फ़िगरेशन प्लस **फ़ील्ड कैटलॉग**: सर्वर सेटिंग्स के लिए सत्य का एकल स्रोत। हर itzg पर्यावरण चर को कैटलॉग किया गया है (लेबल, सहायता, प्रकार, इकाई, डिफ़ॉल्ट, सत्यापन, अनुभाग, ख़तरा फ़्लैग)। विज़ार्ड, सेटिंग्स फ़ॉर्म, और zod सत्यापन सभी इससे प्राप्त होते हैं, इसलिए एक नई सेटिंग को उजागर करना एक डेटा परिवर्तन है, न कि नया UI प्लंबिंग।
- **`events/`** - `recordEvent()` इतिहास लॉग के लिए एकमात्र प्रवेश बिंदु है; जीवनचक्र घटनाएँ `data/logs/<id>/events/` में कंटेनर-लॉग अंशों को भी कैप्चर करती हैं।
- **`ws/`** - प्रमाणित कंसोल + आँकड़े WebSockets (अपग्रेड पर सत्र कुकी सत्यापित, क्रॉस-साइट अपहरण को ब्लॉक करने के लिए `Origin` की जाँच), प्रति सर्वर ब्रोकर किया गया (देखें "रनटाइम आकार")।
- **`logger.js` + `instrument.js`** - `require('./logger')(label)` प्रति-मॉड्यूल [Pino](https://getpino.io) लॉगर लौटाता है; `LOG_LEVEL` से स्तर, `makeFailureThrottle()` एक लगातार विफल होने वाले पृष्ठभूमि लूप को एक लॉग लाइन प्लस एक "पुनर्प्राप्त" लाइन तक रखता है। `src/utils/logSanitize.js` संरचित मेटाडेटा से क्रेडेंशियल-आकार की कुंजियों और वेबहुक टोकन को रेडैक्ट करता है; `src/config/logLevel.js` साझा स्तर अनुमति सूची है (लॉगर मौजूद होने से पहले आवश्यकता चक्र से बचने के लिए अलग रखा गया)। `src/instrument.js` एक निष्क्रिय Sentry सीम है, जिसे `src/server.js` में पहले लोड किया गया है। `src/web/middleware/requestLog.js` प्रति अनुरोध एक एक्सेस-लॉग लाइन लिखता है (`/healthz` और स्थिर संपत्तियों को छोड़कर)। ESLint `src/**` के तहत `no-console` को लागू करता है, जिसमें `preflight.js`, `instrument.js`, और `config/index.js` को छूट दी गई है (वे लॉगर के मौजूद होने से पहले चलते हैं)।
- **दर सीमा** - `src/web/middleware/rateLimit.js` `/api` (`RATE_LIMIT_API_PER_MIN`, डिफ़ॉल्ट 1200) और लॉगिन / 2FA / सेटअप POSTs (`RATE_LIMIT_AUTH_PER_15MIN`, डिफ़ॉल्ट 100) के सामने `express-rate-limit` रखता है; `0` एक लिमिटर को अक्षम करता है। यह `req.ip` पर कुंजी करता है, इसलिए `TRUST_PROXY` एक प्रॉक्सी के पीछे मायने रखता है। `/api/v1` में इसका अपना प्रति-टोकन लिमिटर (`RATE_LIMIT_PUBLIC_API_PER_MIN`, डिफ़ॉल्ट 120) है, जो बेयरर टोकन के हैश पर एक आईपी फ़ॉलबैक के साथ कुंजीबद्ध है। `src/web/middleware/auth.js` में एक अलग प्रति-खाता सॉफ्ट काउंटर लॉगिन लॉकआउट (प्रति-आईपी और खाता-वैश्विक, क्षय) को संभालता है।

## मुख्य डोमेन व्यवहार

- **मॉडपैक हमेशा पिन किए जाते हैं।** इमेज हर रीस्टार्ट पर अनपिन्ड पैक को ऑटो-अपग्रेड करती है, इसलिए पैनल इंस्टॉल समय पर "नवीनतम" को एक ठोस संस्करण आईडी में हल करता है और उसे पिन करता है। अपग्रेड एक स्पष्ट ऑर्केस्ट्रेटेड प्रवाह (`updates/`) हैं: पूर्वावलोकन → प्री-अपडेट बैकअप → ग्रेसफुल स्टॉप → री-पिन → री-क्रिएट → स्वास्थ्य-मॉनिटर → एक-क्लिक रोलबैक।
- **कस्टम-मॉड ओवरले** पैनल-प्रबंधित है: उपयोगकर्ता-जोड़े गए मॉड डिडुप्लिकेटेड लाइब्रेरी में उतरते हैं और सर्वर में हार्ड-लिंक किए जाते हैं ताकि वे पैक अपडेट से बच सकें। अक्षम करना वर्ग-जागरूक है।
- **पोर्ट** एक आधार योजना से आवंटित किए जाते हैं (गेम `PORT_GAME_START` से ऊपर, RCON = गेम + `PORT_RCON_OFFSET`, बेडरॉक `PORT_BEDROCK_START` से), उपलब्धता के लिए जांचे जाते हैं, और DB में आरक्षित किए जाते हैं।
- **डिस्क कोटा** पैनल द्वारा लागू किए जाते हैं क्योंकि Docker बाइंड-माउंट उपयोग को कैप नहीं कर सकता है: इंडेक्सर प्रति-निर्देशिका आकार को कैश करता है और डिस्क-बढ़ने वाले ऑपरेशन उन पर गेट किए जाते हैं।
- **गुप्त** (RCON पासवर्ड, API कुंजी, TOTP रहस्य, Discord वेबहुक URL) AES-256-GCM के साथ एन्क्रिप्ट किए जाते हैं, `$DATA_DIR/.secret-key` पर एक समर्पित यादृच्छिक कुंजी का उपयोग करके (मोड `0600`, ऑटो-जेनरेटेड)। यह `SESSION_SECRET` से स्वतंत्र है; एक `SESSION_SECRET`-व्युत्पन्न कुंजी समर्पित कुंजी मौजूद होने से पहले लिखे गए मानों के लिए एक डिक्रिप्ट-ओनली फ़ॉलबैक के रूप में रखी जाती है, और `src/services/secretsMigration.js` बूट पर एक बार उन लोगों को समर्पित कुंजी के तहत फिर से एन्क्रिप्ट करता है। एक `.secret-key` जो मौजूद है लेकिन पार्स नहीं होता है, एक हार्ड बूट त्रुटि है (यह कभी भी चुपचाप शीर्ष पर फिर से उत्पन्न नहीं होता है)। ब्लूप्रिंट निर्यात पर सभी रहस्यों को स्ट्रिप करते हैं।

## डेटा और वायर प्रारूप

- **`data/panel.db`** - SQLite डेटाबेस। दैनिक रूप से `VACUUM INTO` के माध्यम से `data/backups/_panel/` में स्नैपशॉट किया जाता है (नवीनतम 14 रखे जाते हैं); `PRAGMA integrity_check` बूट पर चलता है।
- **`data/.session-secret`** - ऑटो-जेनरेटेड कुकी-साइनिंग सीक्रेट, पहली बार चलने पर बनाया जाता है यदि `SESSION_SECRET` अनसेट हो। इसे हटाने से सीक्रेट घूम जाता है (जो सत्रों को अमान्य करता है)।
- **`data/.secret-key`** - समर्पित 32-बाइट एट-रेस्ट एन्क्रिप्शन कुंजी (मोड `0600`), पहली बार चलने पर ऑटो-निर्मित। `SESSION_SECRET` से स्वतंत्र; इसे हटाने से हर संग्रहीत क्रेडेंशियल अपठनीय हो जाता है, इसलिए यह आपके बैकअप के साथ रहता है।
- **ब्लूप्रिंट (`.mcserver.zip`)** - एक ज़िप जिसमें `manifest.json` कॉन्फ़िगरेशन, संसाधन, पिन किए गए पैक संदर्भ, ओवरले मैनिफ़ेस्ट (स्रोत यूआरएल + sha256), चुने गए कॉन्फ़िगरेशन फ़ाइलें, और वैकल्पिक रूप से एक दुनिया का वर्णन होता है। आयात प्रत्येक मॉड को फिर से डाउनलोड और हैश-सत्यापित करता है और ताज़ा पोर्ट असाइन करता है।
- **Docker कंटेनर** जो पैनल द्वारा बनाए गए हैं, उनका नाम और लेबल किया गया है ताकि वॉचर उन्हें ढूंढ सके; पैनल उनके पूर्ण जीवनचक्र का मालिक है।

## बूट अनुक्रम

1. किसी भी चीज़ से पहले `require('./instrument')` (Sentry सीम), फिर `require('./preflight')` एक असमर्थित Node संस्करण पर स्पष्ट रूप से विफल होने के लिए।
2. कॉन्फ़िगरेशन लोड करें; `.session-secret` **और** `.secret-key` सुनिश्चित/उत्पन्न करें।
3. `ensureDataRoot()` - `./data` लेआउट बनाएं, `tmp/` को पोंछें।
4. DB माइग्रेशन चलाएं, फिर `PRAGMA integrity_check` (जोर से लॉग करता है, विफलता पर `data/backups/_panel` की ओर इशारा करता है)।
5. किसी भी लेगेसी `SESSION_SECRET`-कीड रहस्यों को `.secret-key` के तहत फिर से एन्क्रिप्ट करें (`secretsMigration`)।
6. स्टार्टर ब्लूप्रिंट सीड करें (गार्ड किया गया)।
7. HTTP + WS सर्वर शुरू करें। एक उजागर बाइंड पर, पहली बार चलने वाले `/setup` PIN को प्रिंट करें।
8. बूट के बाद रनटाइम गार्ड स्थापित करें (अनकैप्ड दोषों को पकड़ता है; `MSM_EXIT_ON_FATAL=1` पर्यवेक्षित परिनियोजन के लिए हार्ड-एग्जिट बनाता है)।
9. पृष्ठभूमि सेवाएँ शुरू करें: WS ब्रोकर, स्टोरेज इंडेक्सर, क्रैश + इन्वेंटरी वॉचर, शेड्यूलर, Discord इवेंट ब्रिज, और **दैनिक रखरखाव टाइमर** (पुराने एनालिटिक्स पंक्तियों को प्रून करें + `panel.db` स्नैपशॉट करें)।
10. **पृष्ठभूमि में** Docker प्रारंभ करें। डेमन के डाउन होने पर UI पूरी तरह से प्रयोग करने योग्य है; जब Docker पहुंच योग्य हो जाता है तो Docker सुविधाएँ चालू हो जाती हैं। एक बार कनेक्ट होने के बाद, `refreshStatuses({ boot })` कैश किए गए स्टेटस को सुलझाता है, पैनल को पुनरारंभ करने से पहले ऊपर था और वापस नहीं लाया जाएगा, उसके लिए एक बार का `offline-after-restart` ईवेंट उत्सर्जित करता है, और बूट लूप आउटेज के दौरान क्रैश पाए गए `auto_start` सर्वर शुरू करता है और `auto_restart` सर्वर को ठीक करता है (क्रैश-लूप बैकऑफ़ का सम्मान करते हुए)।

> इंस्ट्रूमेंट-बिफोर-प्रीफ्लाइट ऑर्डर एक जानबूझकर किया गया समझौता है: यह भविष्य के Sentry वायरिंग को रनटाइम को पहले पैच करने देता है, एक वास्तविक प्राचीन Node पर थोड़े कम अनुकूल संदेश की कीमत पर।

## बिल्ड पाइपलाइन

`pnpm run build` = `build:css` (Tailwind → `public/css/app.css`) + `build:js` (esbuild → `public/dist/js/`, कोड-स्प्लिटिंग के साथ ESM)। `postinstall` **केवल CSS** चलाता है। `public/css/app.css` और `public/dist/` गिटइग्नोर किए गए बिल्ड आर्टिफैक्ट हैं; Dockerfile बिल्ड स्टेज पूर्ण `pnpm run build` चलाता है और `public/` को रनटाइम इमेज में कॉपी करता है। स्थिर संपत्तियाँ फिंगरप्रिंट की गई फ़ाइलों के लिए `immutable`/long-cache, CSS/JS के लिए short-cache, और HTML और `/api` के लिए `no-cache` के रूप में सर्व की जाती हैं।
