Minecraft Server Manager एक सिंगल-प्रोसेस, सर्वर-रेंडर्ड Node.js एप्लिकेशन है। यह Docker कंटेनर के रूप में चलने वाले Minecraft सर्वर को Docker API के माध्यम से प्रबंधित करता है (कभी भी `docker` CLI को शेल आउट करके नहीं), [itzg/docker-minecraft-server](https://github.com/itzg/docker-minecraft-server) इमेज का उपयोग करके।

## रनटाइम आकार

- **Express + Handlebars** सर्वर-साइड पेज रेंडर करते हैं। कोई SPA नहीं है; `public/js/` में ब्राउज़र JS हाथ से लिखा गया प्रोग्रेसिव एन्हांसमेंट है। एक esbuild स्टेप (`pnpm run build:js`) इसे बंडल और मिनिफाई करके `public/dist/js/` में डालता है; ऐप इसे तब सर्व करता है जब यह मौजूद होता है और अन्यथा रॉ सोर्स, इसलिए बिल्ड के बिना डेवलपर रन भी काम करता है।
- **`node:sqlite`** (Node में निर्मित; पैनल को Node ≥ 24 की आवश्यकता है) डेटाबेस है - सिंक्रोनस, शून्य नेटिव मॉड्यूल, WAL मोड। एक छोटा संस्करण-माइग्रेशन रनर बूट पर `src/db/migrations/*` लागू करता है। तैयार स्टेटमेंट `src/db/index.js` में SQL टेक्स्ट पर की के रूप में कैश किए जाते हैं।
- **`ws`** लाइव कंसोल और स्टेट्स स्ट्रीम ले जाता है। दोनों **ब्रोकर्ड** हैं: प्रति सर्वर एक अपस्ट्रीम `docker logs --follow` (या `docker stats`), एक बार डीमक्स किया गया और हर कनेक्टेड टैब पर फैलाया गया, बजाय प्रति व्यूअर एक अपस्ट्रीम के। कंसोल ब्रोकर देर से जुड़ने वाले टैब के लिए एक छोटा रीप्ले बफर रखता है और एक सब्सक्राइबर को छोड़ देता है जिसका सॉकेट साझा स्ट्रीम को धीमा करने के बजाय बहुत पीछे चला जाता है।
- **dockerode** एकमात्र तरीका है जिससे ऐप Docker से बात करता है। एंडपॉइंट प्लेटफ़ॉर्म प्रति (Windows नेम्ड पाइप बनाम यूनिक्स सॉकेट) ऑटो-डिटेक्ट किया जाता है।
- **सभी स्थायी स्थिति एक निर्देशिका के अंतर्गत रहती है** (`$DATA_DIR`, डिफ़ॉल्ट `./data`)। उस निर्देशिका को कॉपी करने से पूरा पैनल माइग्रेट हो जाता है।

## लेयरिंग

निर्भरताएँ एक दिशा में प्रवाहित होती हैं:

```
                 ┌─────────────────────────────┐
   HTTP  ───────▶│  web/routes/*  (+ middleware)│   इनपुट को पार्स और मान्य करें, प्रतिक्रियाओं को आकार दें
                 └──────────────┬──────────────┘
                                │
                 ┌──────────────▼──────────────┐
                 │         services/*          │   डोमेन लॉजिक (वास्तविक सुविधाएँ)
                 └───┬─────────┬─────────┬─────┘
                     │         │         │
        ┌────────────▼──┐ ┌────▼────┐ ┌──▼──────────┐
        │   docker/*    │ │  db/*   │ │  storage/*  │   इंफ्रास्ट्रक्चर
        └───────────────┘ └─────────┘ └─────────────┘
```

- **`web/routes/`** - डोमेन प्रति एक राउटर (`players`, `worlds`, `crashes`, `blueprints`, `files`, …)।
  `web/app.js` टॉप-लेवल वाले (`api.js`, सत्र JSON API जो कोर सर्वर रूट भी रखता है और प्रति-सर्वर डोमेन राउटर को माउंट करता है; `index.js`, पेज; `auth`, `account`, `tasks`, …) को माउंट करता है। राउटर zod के साथ मान्य करते हैं, एक सेवा को कॉल करते हैं, और JSON लौटाते हैं
  या एक व्यू रेंडर करते हैं। व्यावसायिक तर्क यहाँ नहीं होना चाहिए। दो राउटर **सार्वजनिक क्षेत्र** में माउंट किए जाते हैं, `requireAuth` से पहले: `routes/status.js` (ऑप्ट-इन प्रति-सर्वर HTML स्थिति पृष्ठ) और `routes/apiV1.js` (`/api/v1`, एक रीड-ओनली JSON API जिसे एडमिन-मिंटेड बेयरर टोकन द्वारा प्रमाणित किया जाता है `services/apiTokens.js` से, सेटिंग्स में सक्षम होने पर बंद; `docs/public-api.md` देखें)।
- **`services/`** - ऐप का दिल। प्रत्येक सेवा एक डोमेन का मालिक है और इंफ्रास्ट्रक्चर और अन्य सेवाओं पर निर्भर हो सकती है।
- **`docker/`** - dockerode रैपर: `connect` (एंडपॉइंट डिटेक्शन + डेमन स्वास्थ्य), `containers` (बाइंड माउंट, मेमोरी/सीपीयू सीमा, और लेबल के साथ बनाएं/शुरू/बंद/पुनः बनाएं), `logs`, `stats`, `images`, `networks` (होस्ट नेटवर्क खोज), `hostPath` (बाइंड पथों को `DATA_DIR_HOST` के अंतर्गत पुनः रूट करता है), और एक `watcher` जो Docker घटनाओं को इतिहास + क्रैश डिटेक्शन में बदलता है।
- **`db/`** - SQLite रैपर और माइग्रेशन रनर।
- **`storage/`** - `./data` बूटस्ट्रैप, **पथ गार्ड** (`safeJoin`, फ़ाइल-सुरक्षा रीढ़), और पृष्ठभूमि आकार-इंडेक्सर + कोटा प्रवर्तन।

क्रॉस-कटिंग:

- **`config/`** - पर्यावरण कॉन्फ़िगरेशन प्लस **फ़ील्ड कैटलॉग**: सर्वर सेटिंग्स के लिए सत्य का एकल स्रोत। हर itzg पर्यावरण चर को कैटलॉग किया गया है (लेबल, सहायता, प्रकार, इकाई, डिफ़ॉल्ट, सत्यापन, अनुभाग, खतरा फ़्लैग)। विज़ार्ड, सेटिंग्स फ़ॉर्म, और zod सत्यापन सभी इससे प्राप्त होते हैं, इसलिए एक नई सेटिंग को उजागर करना एक डेटा परिवर्तन है, न कि नया UI प्लंबिंग।
- **`events/`** - `recordEvent()` इतिहास लॉग के लिए एकमात्र प्रवेश बिंदु है; जीवनचक्र घटनाएँ कंटेनर-लॉग अंशों को `data/logs/<id>/events/` में भी कैप्चर करती हैं।
- **`ws/`** - प्रमाणित कंसोल + स्टेट्स WebSockets (सत्र कुकी अपग्रेड पर सत्यापित, `Origin` क्रॉस-साइट अपहरण को ब्लॉक करने के लिए जांचा गया), प्रति सर्वर ब्रोकर्ड (रनटाइम आकार देखें)।
- **`logger.js` + `instrument.js`** - `require('./logger')(label)` प्रति-मॉड्यूल [Pino](https://getpino.io) लॉगर लौटाता है; `LOG_LEVEL` से स्तर, `makeFailureThrottle()` एक लगातार विफल होने वाले पृष्ठभूमि लूप को एक लॉग लाइन प्लस एक "पुनर्प्राप्त" लाइन तक रखता है।
  `src/utils/logSanitize.js` संरचित मेटाडेटा से क्रेडेंशियल-आकार की कुंजियों और वेबहुक टोकन को रेडैक्ट करता है; `src/config/logLevel.js` साझा स्तर अनुमति सूची है (लॉगर मौजूद होने से पहले एक आवश्यकता चक्र से बचने के लिए अलग रखा गया है)। `src/instrument.js` एक निष्क्रिय Sentry सीम है, जिसे `src/server.js` में पहले लोड किया गया है। `src/web/middleware/requestLog.js` प्रति अनुरोध एक एक्सेस-लॉग लाइन लिखता है (`/healthz` और स्थिर संपत्तियों को छोड़कर)। ESLint `src/**` के तहत `no-console` को लागू करता है, जिसमें `preflight.js`, `instrument.js`, और `config/index.js` छूट प्राप्त हैं (वे लॉगर मौजूद होने से पहले चलते हैं)।
- **रेट लिमिटिंग** - `src/web/middleware/rateLimit.js` `/api` (`RATE_LIMIT_API_PER_MIN`, डिफ़ॉल्ट 1200) और लॉगिन / 2FA / सेटअप POSTs (`RATE_LIMIT_AUTH_PER_15MIN`, डिफ़ॉल्ट 100) के सामने `express-rate-limit` रखता है; `0` एक लिमिटर को अक्षम करता है। यह `req.ip` पर कुंजी करता है, इसलिए प्रॉक्सी के पीछे `TRUST_PROXY` मायने रखता है। `/api/v1` में अपने स्वयं के लिमिटर हैं: प्रति-क्लाइंट-आईपी कैप (प्रति-टोकन बजट का पांच गुना) जो टोकन सत्यापित होने से पहले चलता है, फिर प्रति-टोकन बजट (`RATE_LIMIT_PUBLIC_API_PER_MIN`, डिफ़ॉल्ट 120) सत्यापित टोकन की आईडी पर कुंजीकृत होता है।
  `src/web/middleware/auth.js` में एक अलग प्रति-खाता सॉफ्ट काउंटर लॉगिन लॉकआउट (प्रति-आईपी और खाता-वैश्विक, क्षय) को संभालता है।
- **प्राधिकरण**: दो परतें। वैश्विक भूमिका (`requireAuth` → `requireRole` / `requireWrite` `src/web/middleware/auth.js` में) पैनल-व्यापी क्रियाओं को गेट करती है और हर सर्वर पर डिफ़ॉल्ट है। प्रति-सर्वर अनुमतियाँ (`src/services/permissions.js`, नौ क्षमताएँ प्रति `(user, server)` `user_server_permissions` में JSON सूची के रूप में संग्रहीत) एक सर्वर के लिए उस डिफ़ॉल्ट को परिष्कृत करती हैं; हर `/api/servers/:id` रूट, सब-राउटर माउंट, पेज, WebSocket, और फ्लीट-व्यापी लिस्टिंग `src/web/middleware/serverAccess.js` (`serverScope`, API और पेज राउटर दोनों के `/servers/:id` उपसर्ग पर माउंट किया गया, `view` के बिना एक सर्वर को 404 के रूप में छिपाता है; `requireCap(cap)` रूट की आवश्यकता वाली क्षमता का नाम देता है) से होकर गुजरती है। बॉडी में अपने सर्वर का नाम लिखने वाले राइट्स (शेड्यूल, विश्व एक्सट्रैक्ट और इंस्टॉल, ब्लूप्रिंट एक्सपोर्ट) केवल उस सर्वर के लिए दर्शकों के लिए `requireWrite` द्वारा खोले जाते हैं, और प्रत्येक ऐसा रूट स्वयं क्षमता की जांच करता है। `test/permissions-routes.test.js` लाइव राउटर स्टैक को चलता है और विफल हो जाता है यदि किसी सर्वर-स्कोप वाले राइट रूट, माउंट, या पेज में कोई गेट नहीं है।

## मुख्य डोमेन व्यवहार

- **मोडपैक हमेशा पिन किए जाते हैं।** इमेज हर रीस्टार्ट पर अनपिंड पैक को ऑटो-अपग्रेड करती है, इसलिए पैनल इंस्टॉल समय पर "नवीनतम" को एक ठोस संस्करण आईडी में हल करता है और उसे पिन करता है। अपग्रेड एक स्पष्ट ऑर्केस्ट्रेटेड प्रवाह हैं (`updates/`): पूर्वावलोकन → प्री-अपडेट बैकअप → ग्रेसफुल स्टॉप → री-पिन → रीक्रिएट → हेल्थ-मॉनिटर → वन-क्लिक रोलबैक।
- **कस्टम-मोड ओवरले** पैनल-प्रबंधित है: उपयोगकर्ता-जोड़े गए मोड डी-डुप्लिकेटेड लाइब्रेरी में उतरते हैं और सर्वर में हार्ड-लिंक होते हैं ताकि वे पैक अपडेट से बच सकें। अक्षम करना वर्ग-जागरूक है। क्योंकि लाइब्रेरी अपने द्वारा डाउनलोड किए गए हर बिल्ड को रखती है, एक अपडेट उस बिल्ड को रिकॉर्ड करता है जिसे उसने बदला (`server_content.previous_*`) और केवल स्थानीय फ़ाइलों से वापस किया जा सकता है। पैक मोड को अक्षम करने से पैक का बहिष्करण env चर लिखा जाता है; `packs.applyPack` उस और पैक ट्यूनिंग (`PACK_TUNING_KEYS`) के बाकी हिस्सों को उसी पैक के संस्करण परिवर्तन के पार ले जाता है, और पैक बदलने पर उसे छोड़ देता है।
- **एक Minecraft संस्करण अपग्रेड अर्जित करना होगा।** `services/compat.js` सर्वर के मोड को स्कैन करता है - पैनल-इंस्टॉल की गई पंक्तियों से हल किया गया, फिर कर्सफ़ोर्ज पैक मैनिफ़ेस्ट, फिर Modrinth/CurseForge के विरुद्ध सामग्री हैश द्वारा - और कर्सफ़ोर्ज के `latestFilesIndexes` (प्रति अनुरोध 200 प्रोजेक्ट) और Modrinth के प्रति-प्रोजेक्ट संस्करण सूची (प्रति प्रोजेक्ट एक अनुरोध, जो लोडर और संस्करण को युग्मित रखता है) से प्रति प्रोजेक्ट (लोडर, Minecraft संस्करण) समर्थन मैट्रिक्स बनाता है। अपडेट चेकर केवल सबसे नया संस्करण प्रदान करता है जिसे हर मोड सपोर्ट करता है, और कुछ भी प्रदान नहीं करता है जब उत्तर स्थापित नहीं किया जा सकता है: कोई स्कैन नहीं, एक अलग संस्करण या लोडर के लिए स्कैन, एक जो कभी पूरा नहीं हुआ, या एक जार जिसे कोई भी रजिस्ट्री पहचानती नहीं है। स्कैन केवल मैन्युअल होते हैं, और उनकी प्रगति और आंशिक परिणाम `version_compat` में रहते हैं (इन-मेमोरी `services/tasks.js` में नहीं), इसलिए एक रीफ़्रेश या पैनल रीस्टार्ट स्पिनर पर लटकने के बजाय फिर से शुरू होता है; `reconcileScans()` अगले बूट पर शटडाउन द्वारा छोड़े गए स्कैन को चिह्नित करता है।
- **मोड लोडर संस्करण एक पिन है, बाकी सब की तरह।** `services/loaderPin.js` इमेज के स्वयं के इंस्टॉल मैनिफ़ेस्ट (`.forge-manifest.json` और मित्र) से इंस्टॉल किए गए बिल्ड को पढ़ता है और पिन लिखता है: एक सादे सर्वर पर लोडर का itzg चर (`FORGE_VERSION`, …), या एक Forge या Fabric CurseForge पैक पर `CF_MOD_LOADER_VERSION`, जो पैक द्वारा घोषित संस्करण को ओवरराइड करता है। इमेज का CurseForge इंस्टॉलर NeoForge के लिए उस ओवरराइड को अनदेखा करता है, और Modrinth और FTB पैक में कोई नहीं होता है, इसलिए उनका लोडर पैक का अनुसरण करता है। `packs.applyPack` पैक अपडेट या रोलबैक पर हर `CF_` चर को स्ट्रिप करता है, जो बाकी के साथ एक ओवरराइड छोड़ देता है। एक टाइप किया गया बिल्ड पहले रजिस्ट्री की पूरी सूची के विरुद्ध जांचा जाता है (`services/loaderVersions.js`; Forge का इसके मैवेन मेटाडेटा से आता है, जो संख्याओं को छोड़ देता है; एक मिस को रजिस्ट्री के विरुद्ध एक बार फिर से जांचा जाता है), फिर परिवर्तन बैकअप → पिन (बैकअप के बाद env के ऊपर) → पुनर्निर्माण होता है।
- **पोर्ट** एक आधार योजना से आवंटित किए जाते हैं (गेम `PORT_GAME_START` से ऊपर, RCON = गेम + `PORT_RCON_OFFSET`, बेडरॉक `PORT_BEDROCK_START` से), उपलब्धता के लिए जांचे जाते हैं, और डीबी में आरक्षित किए जाते हैं। "टेकन" हर सर्वर के दावों का संघ है (लाइव पोर्ट, प्लस एक लंबित जोड़ी नीचे), हर होस्ट पोर्ट जो कोई भी Docker कंटेनर प्रकाशित करता है (`containers.publishedHostPorts`: चल रहे कंटेनरों के लाइव बाइंडिंग प्लस प्रत्येक बंद कंटेनर के कॉन्फ़िगर किए गए वाले, क्योंकि पैनल के अपने कंटेनर के अंदर से एक OS बाइंड प्रोब केवल उस कंटेनर के नेटवर्क नेमस्पेस को देखता है), और OS प्रोब। Docker भाग 3 सेकंड के लिए कैश किया जाता है और सीमित होता है: 2.5 सेकंड में जवाब न देने वाली सूची केवल Docker भाग को छोड़ देती है, और एक धीमा निरीक्षण केवल उस कंटेनर के पोर्ट की लागत देता है। सर्वर निर्माण और `servers.changeGamePort` एक सीरियलाइज़ेशन श्रृंखला के माध्यम से पोर्ट चुनते हैं जो केवल पिक और उसके दावे को कवर करती है (निर्माण के लिए पंक्ति लेखन, पोर्ट परिवर्तन के लिए इन-मेमोरी आरक्षण); BlueMap का पोर्ट पिकर और अतिरिक्त-पोर्ट ओवरराइड इसमें नहीं हैं और Docker से परामर्श नहीं करते हैं। एक मौजूदा सर्वर पर पोर्ट परिवर्तन (`servers.changeGamePort`, सर्वर के ऑप लॉक के तहत) एक बार में लागू किया जाता है, क्योंकि Docker कंटेनर निर्माण पर पोर्ट बाइंडिंग को ठीक करता है: नया जोड़ी (RCON हमेशा गेम + `PORT_RCON_OFFSET`) मेमोरी में जांचा और आरक्षित किया जाता है (`ports.reserve`, पुराना और नया दोनों जोड़ी, हर दूसरे पिक द्वारा सम्मानित) पोर्ट लॉक के तहत। यह मना किया जाता है (409 `PENDING_CHANGES`) जबकि अन्य सेटिंग्स पुनर्निर्माण की प्रतीक्षा कर रही हैं, इसलिए यह केवल एक कंटेनर का पुनर्निर्माण करता है जो पहले से चल रहा था, एक नए पोर्ट पर; और एक चल रहे सर्वर को केवल तब बदला जाता है जब अनुरोध `restart: true` कहता है (अन्यथा 409 `NEEDS_CONFIRM`)। इमेज खींची जाती है और कुछ भी छूने से पहले एक कस्टम कंटेनर नाम की जांच की जाती है। एक चल रहे सर्वर को रोका जाता है; फिर नई जोड़ी को `pending_recreate = 1` के साथ लिखा जाता है (ताकि वहां से एक पैनल क्रैश एक ईमानदार "पुनर्निर्माण लंबित" छोड़ दे), कंटेनर हटा दिया जाता है, नई जोड़ी पर पुनर्निर्माण किया जाता है और शुरू किया जाता है। यदि स्टॉप के बाद कोई भी चरण विफल हो जाता है, तो `putBackOnOldPort` पुराने जोड़ी को वापस लिखता है, उस पर पुनर्निर्माण करता है (और यदि यह चल रहा था तो पुनरारंभ करता है) और रिकॉर्ड करता है कि कौन सा चरण विफल हुआ; इतिहास और अलर्ट कहते हैं कि यदि वह भी विफल हो गया, तो सर्वर तब तक रुका रहता है जब तक कोई उसे शुरू नहीं करता। `settings` क्षमता पर्याप्त है, जिसमें चल रहा सर्वर भी शामिल है। गैर-व्यवस्थापक केवल `PORT_GAME_START` से ऊपर से चुन सकते हैं।
  (माइग्रेशन 029 से `port_*_pending` कॉलम एक पहले, अप्रकाशित डिज़ाइन के हैं और अप्रयुक्त हैं; 031 उन्हें साफ़ करता है।) एक लॉक टकराव 409 को `code: 'BUSY'` के साथ उत्तर देता है, जिसे नीचे दिए गए रिट्रीइंग कॉलर्स जांचते हैं, न कि शब्दों को। एक क्रैश ऑटो-रीस्टार्ट
  (`watcher.restartAfterCrash`) और एक अनुसूचित बैकअप या स्टार्ट (`scheduler.runTaskWithRetry`) जो सर्वर को किसी अन्य क्रिया के साथ व्यस्त पाते हैं, 30 मिनट तक हर 20 सेकंड / 60 सेकंड में फिर से प्रयास करते हैं, और एक पैक अपडेट या रोलबैक उसी तरह अपने लॉक किए गए चरणों को पुनः प्रयास करता है (`opLock.retryWhileBusy`); एक क्रैश रीस्टार्ट या एक प्रतीक्षा अनुसूचित स्टार्ट तब हार मान लेता है जब किसी ने सर्वर को बंद, मार दिया या शुरू कर दिया हो (`events.lifecycleActionSince`), और क्रैश रीस्टार्ट भी तब जब ऑटो-रीस्टार्ट बंद हो या सर्वर चला गया हो। अनुसूचित रीस्टार्ट, स्टॉप और कमांड को पुनः प्रयास नहीं किया जाता है, और एक शेड्यूल जिसका अंतिम रन अभी भी प्रतीक्षा कर रहा है, वह अपनी अगली फायरिंग को छोड़ देता है।
- **डिस्क कोटा** पैनल द्वारा लागू किए जाते हैं क्योंकि Docker बाइंड-माउंट उपयोग को कैप नहीं कर सकता है: इंडेक्सर प्रति-निर्देशिका आकार को कैश करता है और डिस्क-बढ़ने वाले संचालन उन पर गेट किए जाते हैं।
- **सीक्रेट्स** (RCON पासवर्ड, API कुंजियाँ, TOTP सीक्रेट्स, Discord वेबहुक URL) AES-256-GCM का उपयोग करके `$DATA_DIR/.secret-key` पर एक समर्पित यादृच्छिक कुंजी के साथ आराम पर एन्क्रिप्ट किए जाते हैं (मोड `0600`, ऑटो-जेनरेटेड)। यह `SESSION_SECRET` से स्वतंत्र है; एक `SESSION_SECRET`-व्युत्पन्न कुंजी समर्पित कुंजी के अस्तित्व से पहले लिखे गए मानों के लिए केवल-डिक्रिप्ट फ़ॉलबैक के रूप में रखी जाती है, और
  `src/services/secretsMigration.js` बूट पर एक बार उन लोगों को समर्पित कुंजी के तहत पुनः एन्क्रिप्ट करता है।
  एक `.secret-key` जो मौजूद है लेकिन पार्स नहीं होता है, एक हार्ड बूट त्रुटि है (यह कभी भी चुपचाप फिर से उत्पन्न नहीं होता है)। ब्लूप्रिंट निर्यात पर सभी सीक्रेट्स को स्ट्रिप करते हैं।
- **`server.properties` पैनल के स्वामित्व में है लेकिन env-छायांकित है।** itzg इमेज हर env-समर्थित प्रॉपर्टी को हर स्टार्ट पर फिर से लागू करती है (`OVERRIDE_SERVER_PROPERTIES` डिफ़ॉल्ट रूप से सत्य है), इसलिए पैनल द्वारा सीधे संपादित एक मान - वर्ल्ड कंट्रोल्स PvP/कठिनाई, व्हिटेलिस्ट टॉगल, फ़ाइलें संपादक - अगले स्टार्ट पर चुपचाप वापस कर दिए जाएंगे जब तक कि मिलान करने वाला env चर हटा नहीं दिया जाता है और कंटेनर को फिर से नहीं बनाया जाता है। हर प्रत्यक्ष प्रॉपर्टी राइट `writeServerProperties()` (पूरी फ़ाइल) या `setServerProperty()` (एक कुंजी) `src/services/servers.js` में से होकर गुजरता है, जो परमाणु रूप से फ़ाइल को फिर से लिखते हैं, प्रत्येक परिवर्तित कुंजी के पीछे env चर को अनसेट करते हैं (कैटलॉग फ़ील्ड पर `prop:` विशेषता के माध्यम से, इमेज की अपनी प्रॉपर्टी परिभाषाओं के विरुद्ध परीक्षणों में जांचा जाता है), और `pending_recreate` को फ़्लैग करते हैं। कठिनाई को फ़ाइल में लिखा जाता है और RCON पर भेजा जाता है, क्योंकि एक समर्पित सर्वर हर बूट पर `difficulty` प्रॉपर्टी को फिर से लागू करता है। Minecraft स्वयं बूट-टाइम मानों से server.properties को `whitelist on/off` पर फिर से सहेजता है, जो सर्वर चलने के दौरान किए गए संपादनों को पूर्ववत कर देगा, इसलिए चल रहा व्हिटेलिस्ट टॉगल पहले फ़ाइल को स्नैपशॉट करता है और इसे केवल `white-list` को बदलकर वापस लिखता है। env
  वेरिएबल निर्माण के समय पूरी तरह से कॉन्फ़िगर करने योग्य रहते हैं (विज़ार्ड उन्हें रेंडर करता है और वे एक बार लागू होते हैं); वे केवल पहली बार पैनल अंतर्निहित प्रॉपर्टी को संपादित करने पर अनपिन होते हैं। MOTD वही अनुबंध है: एक प्रत्यक्ष `motd` फ़ाइल संपादन इसे अनसेट करता है, इसलिए अंतिम राइट जीतता है।

## डेटा और वायर प्रारूप

- **`data/panel.db`** - SQLite डेटाबेस। दैनिक रूप से `VACUUM INTO` के माध्यम से `data/backups/_panel/` पर स्नैपशॉट किया जाता है (नवीनतम 14 रखे जाते हैं); बूट पर `PRAGMA integrity_check` चलता है।
- **`data/.session-secret`** - ऑटो-जेनरेटेड कुकी-साइनिंग सीक्रेट, पहले रन पर बनाया जाता है यदि `SESSION_SECRET` अनसेट है। इसे हटाने से सीक्रेट घूम जाता है (जो सत्रों को अमान्य कर देता है)।
- **`data/.secret-key`** - समर्पित 32-बाइट एट-रेस्ट एन्क्रिप्शन कुंजी (मोड `0600`), पहले रन पर ऑटो-क्रिएटेड। `SESSION_SECRET` से स्वतंत्र; इसे हटाने से हर संग्रहीत क्रेडेंशियल अपठनीय हो जाता है, इसलिए यह आपके बैकअप के साथ रहता है।
- **ब्लूप्रिंट (`.mcserver.zip`)** - एक ज़िप जिसमें कॉन्फ़िगरेशन, संसाधन, पिन किया गया पैक संदर्भ, ओवरले मैनिफ़ेस्ट (स्रोत यूआरएल + sha256), चुने गए कॉन्फ़िगरेशन फ़ाइलें, और वैकल्पिक रूप से एक विश्व का वर्णन करने वाला `manifest.json` होता है। आयात प्रत्येक मोड को फिर से डाउनलोड और हैश-सत्यापित करता है और ताज़ा पोर्ट असाइन करता है।
- **Docker कंटेनर** पैनल द्वारा बनाए गए नाम और लेबल वाले होते हैं ताकि वॉचर उन्हें ढूंढ सके; पैनल उनके पूर्ण जीवनचक्र का मालिक है।

## बूट अनुक्रम

1. `require('./instrument')` (Sentry सीम) सबसे पहले, फिर `require('./preflight')` एक असमर्थित Node संस्करण पर स्पष्ट रूप से विफल होने के लिए।
2. कॉन्फ़िगरेशन लोड करें; `.session-secret` **और** `.secret-key` सुनिश्चित/उत्पन्न करें।
3. `ensureDataRoot()` - `./data` लेआउट बनाएं, `tmp/` को पोंछें।
4. डीबी माइग्रेशन चलाएं, फिर `PRAGMA integrity_check` (जोर से लॉग करता है, विफलता पर `data/backups/_panel` की ओर इशारा करता है)।
5. किसी भी लेगेसी `SESSION_SECRET`-कीड सीक्रेट्स को `.secret-key` के तहत पुनः एन्क्रिप्ट करें (`secretsMigration`)।
6. पर्यावरण से एपीआई कुंजियों को एक बार आयात करें (`apiKeys.importFromEnvOnce()`), किसी भी सर्वर को पिन करें जो अभी भी एक अनपिंड मोडपैक चयनकर्ता ले जा रहा है (`packPins.pinUnpinnedServers()`), पिछले प्रक्रिया द्वारा छोड़े गए संस्करण संगतता स्कैन को बाधित के रूप में चिह्नित करें
   (`compat.reconcileScans()`), फिर स्टार्टर ब्लूप्रिंट को सीड करें (गेटेड)।
7. HTTP + WS सर्वर शुरू करें। एक उजागर बाइंड पर, पहले रन का `/setup` PIN प्रिंट करें।
8. पोस्ट-बूट रनटाइम गार्ड स्थापित करें (अनकैच किए गए दोषों को पकड़ता है; `MSM_EXIT_ON_FATAL=1` पर्यवेक्षित परिनियोजन के लिए हार्ड-एग्जिट बनाता है)।
9. पृष्ठभूमि सेवाएं शुरू करें: WS ब्रोकर, स्टोरेज इंडेक्सर, क्रैश + इन्वेंट्री वॉचर्स, शेड्यूलर,
   Discord इवेंट ब्रिज, चैटबॉट आउटरीच वॉचर, और **दैनिक रखरखाव टाइमर** (पुराने एनालिटिक्स पंक्तियों, चैटबॉट ट्रांसक्रिप्ट, इवेंट इतिहास (365 दिन) और एपीआई कैश पंक्तियों को प्रून करें, फिर `panel.db` का स्नैपशॉट लें)।
10. **पृष्ठभूमि में** Docker प्रारंभ करें। डेमन के डाउन होने पर UI पूरी तरह से प्रयोग करने योग्य है; Docker सुविधाएँ तब प्रकाशमान होती हैं जब यह पहुंच योग्य हो जाता है। एक बार कनेक्ट होने के बाद, `refreshStatuses({ boot })` कैश किए गए स्टेटस को सामंजस्य स्थापित करता है, एक सर्वर के लिए एक बार का `offline-after-restart` इवेंट उत्सर्जित करता है जो पैनल के पुनरारंभ होने से पहले चालू था और वापस नहीं लाया जाएगा, और बूट लूप पैनल पुनरारंभ के दौरान क्रैश पाए गए `auto_start` सर्वर और रिकवर `auto_restart` सर्वर शुरू करता है (क्रैश-लूप बैकऑफ़ का सम्मान करते हुए)।

> इंस्ट्रूमेंट-बिफोर-प्रीफ्लाइट ऑर्डर एक जानबूझकर किया गया समझौता है: यह भविष्य के Sentry वायरिंग को रनटाइम को पहले पैच करने देता है, एक वास्तव में प्राचीन Node पर थोड़े कम अनुकूल संदेश की कीमत पर।

## बिल्ड पाइपलाइन

`pnpm run build` = `build:css` (Tailwind → `public/css/app.css`) + `build:js` (esbuild →
`public/dist/js/`, कोड-स्प्लिटिंग के साथ ESM)। `postinstall` **केवल CSS** चलाता है। `public/css/app.css`
और `public/dist/` गिटइग्नोर किए गए बिल्ड आर्टिफैक्ट हैं; Dockerfile बिल्ड स्टेज पूर्ण `pnpm run build` चलाता है और `public/` को रनटाइम इमेज में कॉपी करता है। स्थिर संपत्तियाँ फिंगरप्रिंट की गई फ़ाइलों के लिए
`immutable`/लॉन्ग-कैश, CSS/JS के लिए शॉर्ट-कैश, और HTML और `/api` के लिए `no-cache` के रूप में सर्व की जाती हैं।
