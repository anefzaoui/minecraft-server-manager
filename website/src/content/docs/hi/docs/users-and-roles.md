यह पैनल मल्टी-यूज़र है। **Settings → Users** के अंतर्गत खातों को प्रबंधित करें।

![Users](/docs/images/settings-users.png)

## तीन भूमिकाएँ (Roles)

| भूमिका       | हर सर्वर पर डिफ़ॉल्ट                                                                                                                       |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **admin**    | सब कुछ: यूज़र, API कीज़, ग्लोबल फ़ाइलें, एडवांस्ड Docker ओवरराइड्स और हर सर्वर एक्शन को प्रबंधित करना।                                     |
| **operator** | सर्वर चलाना और कॉन्फ़िगर करना (स्टार्ट/स्टॉप, कंसोल, बैकअप, वर्ल्ड्स, मॉड्स, अधिकांश सेटिंग्स), लेकिन केवल एडमिन वाले क्षेत्रों को छोड़कर। |
| **viewer**   | केवल पढ़ने के लिए। सर्वर और उनकी स्थिति देखें, लेकिन कोई बदलाव न करें।                                                                     |

हर यूज़र, जिसमें व्यूअर भी शामिल है, अपना [टू-फ़ैक्टर ऑथेंटिकेशन](/docs/two-factor-authentication/) प्रबंधित कर सकता है, क्योंकि अपने लॉगिन की सुरक्षा करना सर्वर-प्रबंधन का कार्य नहीं है।

एक भूमिका हर सर्वर के लिए **डिफ़ॉल्ट** होती है। किसी को एक सर्वर पर अलग अधिकार देने के लिए, नीचे दिए गए प्रति-सर्वर अनुमतियों (per-server permissions) का उपयोग करें।

## प्रति-सर्वर अनुमतियाँ

**Permissions** पेज (साइडबार में, या **Settings → Users** के अंतर्गत **Server Permissions**) एक ग्रिड दिखाता है: साइड में हर ऑपरेटर और व्यूअर, और ऊपर हर सर्वर। यह तय करने के लिए कि वह यूज़र उस एक सर्वर पर क्या कर सकता है, किसी सेल पर क्लिक करें। एडमिन्स को सूचीबद्ध नहीं किया गया है क्योंकि उनके पास हमेशा सब कुछ होता है।

![Permissions](/docs/images/settings-permissions.png)

प्रत्येक सेल अनुमतियों का एक सेट है:

| अनुमति       | उस सर्वर पर क्या अनुमति देता है                                                                                   |
| ------------ | ----------------------------------------------------------------------------------------------------------------- |
| **View**     | सर्वर, उसकी स्थिति, कंसोल आउटपुट, खिलाड़ी, इतिहास और आँकड़े देखें।                                                |
| **Power**    | सर्वर को स्टार्ट, स्टॉप, रीस्टार्ट, किल और रीबिल्ड करें।                                                          |
| **Console**  | कंसोल कमांड और वर्ल्ड क्विक एक्शन चलाएँ, चैट भेजें और चैट कमांड प्रबंधित करें।                                    |
| **Players**  | किक, बैन, व्हाइटलिस्ट, ऑप (op) करें और खिलाड़ी नोट्स संपादित करें।                                                |
| **Content**  | मॉड्स, प्लगइन्स, पैक्स, वर्ल्ड्स, डेटापैक्स इंस्टॉल और रिमूव करें, और इन्वेंट्री संपादित करें।                    |
| **Backups**  | बैकअप बनाएँ, रिस्टोर करें, डाउनलोड करें और डिलीट करें।                                                            |
| **Files**    | सर्वर फ़ाइलें, आर्काइव किए गए लॉग और लॉग बंडल ब्राउज़, संपादित, अपलोड और डाउनलोड करें; ब्लूप्रिंट एक्सपोर्ट करें। |
| **Settings** | सर्वर सेटिंग्स, प्रॉपर्टीज़, इंटीग्रेशन, आइकन बदलें और वर्शन अपग्रेड करें।                                        |
| **Delete**   | सर्वर डिलीट करें।                                                                                                 |

![Permission editor](/docs/images/permissions-editor.png)

ग्रिड के नीचे, **What Each Permission Covers** प्रत्येक अनुमति को खोलता है कि कोई व्यक्ति क्या कर सकता है, क्या शामिल नहीं है, और यह किन सटीक पैनल रास्तों (routes) को अनलॉक करता है। उस अंतिम सूची की जाँच टेस्ट सूट द्वारा रनिंग कोड के आधार पर की जाती है।

![Permission reference](/docs/images/permissions-reference.png)

फ़ोन पर, ग्रिड प्रति यूज़र एक कार्ड में स्टैक हो जाती है, जिसमें प्रति सर्वर एक पंक्ति होती है।

</p>

चीजें एक साथ कैसे काम करती हैं:

- **भूमिका डिफ़ॉल्ट है।** एक ऑपरेटर हर सर्वर पर हर अनुमति के साथ शुरू होता है; एक व्यूअर केवल View के साथ शुरू होता है। हल्के टेक्स्ट वाली सेल (जिसका टूलटिप "Role default" कहता है) को कभी बदला नहीं गया है।
- **एक सेल केवल उस सर्वर के लिए भूमिका को ओवरराइड करती है।** एक व्यूअर को एक सर्वर पर Power और Console दें और वे इसे चला सकते हैं, जबकि अन्य सभी सर्वर उनके लिए केवल पढ़ने के लिए (read-only) रहते हैं। अपने मुख्य सर्वर पर एक ऑपरेटर से Delete हटा दें और वे वहाँ बाकी सब कुछ बनाए रखेंगे।
- **हर अनुमति में View शामिल है।** आप उस सर्वर पर कार्य नहीं कर सकते जिसे आप देख नहीं सकते।
- **सर्वर छिपाने के लिए सब कुछ बंद कर दें।** यह उस यूज़र के साइडबार, डैशबोर्ड, बैकअप, शेड्यूल, गतिविधि, अपडेट, मॉडपैक्स, लाइव स्थिति, चल रहे कार्यों और ब्लूप्रिंट से गायब हो जाता है, और वर्ल्ड्स लाइब्रेरी इसे नाम देना बंद कर देती है। एक सीधा लिंक, API कॉल, या कंसोल सॉकेट "not found" का उत्तर देता है, ठीक वैसे ही जैसे कोई सर्वर जो मौजूद नहीं है।
- **पैनल-व्यापी क्रियाएँ अभी भी भूमिका का पालन करती हैं।** सर्वर बनाना (एक को क्लोन करना शामिल है), स्टोरेज, यूज़र, API कीज़, ग्लोबल सेटिंग्स और पैनल-व्यापी शेड्यूल प्रति-सर्वर नहीं हैं, इसलिए कुछ सर्वरों पर अनुमतियों वाला व्यूअर अभी भी इनमें से कुछ नहीं कर सकता है। ऑपरेटर सर्वर निर्माण और पैनल-व्यापी शेड्यूल बनाए रखते हैं; स्टोरेज, यूज़र, API कीज़ और ग्लोबल सेटिंग्स केवल एडमिन के लिए हैं।
- **शेड्यूल सर्वर का पालन करते हैं।** सर्वर पर एक निर्धारित रीस्टार्ट, बैकअप या कमांड के लिए वहाँ संबंधित अनुमति (Power, Backups, या Console) की आवश्यकता होती है, चाहे भूमिका कुछ भी हो।
- **ब्लूप्रिंट भी सर्वर का पालन करते हैं।** एक सर्वर को ब्लूप्रिंट के रूप में एक्सपोर्ट करने के लिए वहाँ Files की आवश्यकता होती है, क्योंकि आर्काइव में उसकी फ़ाइलें होती हैं। किसी ऐसे सर्वर से एक्सपोर्ट किया गया ब्लूप्रिंट जिसे कोई देख नहीं सकता, वह उनके लिए भी छिपा रहता है।
- **एडमिन-ओनली क्षेत्र हर सर्वर पर एडमिन-ओनली रहते हैं:** चैटबॉट, बैकअप रिटेंशन और एडवांस्ड Docker ओवरराइड्स।

हर बदलाव गतिविधि लॉग में लिखा जाता है कि किसने क्या बदला; वे प्रविष्टियाँ केवल एडमिन्स को दिखाई जाती हैं। यूज़र को डिलीट करने से उनकी पंक्तियाँ हट जाती हैं। सर्वर को हटाने से वे बनी रहती हैं, इसलिए किसी से छिपाया गया सर्वर उसके इतिहास और रखे गए बैकअप में छिपा रहता है।

मौजूदा इंस्टॉलेशन बिना बदले काम करते रहते हैं: जब तक कोई एडमिन किसी सेल को संपादित नहीं करता, हर यूज़र के पास वही होता है जो उनकी भूमिका ने उन्हें पहले दिया था।

## केवल एडमिन के लिए, और क्यों

कुछ चीजें जानबूझकर एडमिन्स तक सीमित हैं:

- **यूज़र प्रबंधन, स्टोरेज, ग्लोबल सेटिंग्स, API कीज़ और ग्लोबल फ़ाइलें।**
- **[पब्लिक API](/docs/public-api/)**: `/api/v1` को सक्षम करना और इसके रीड-ओनली Bearer टोकन बनाना, स्कोप करना या रद्द करना।
- **एडवांस्ड Docker ओवरराइड्स**: कस्टम कंटेनर नाम, अतिरिक्त पोर्ट पब्लिश और बाइंड माउंट्स। एक बाइंड माउंट किसी भी होस्ट पाथ को कंटेनर में मैप कर सकता है, और पैनल के Docker एक्सेस के साथ मिलकर यह होस्ट पर प्रभावी रूप से रूट एक्सेस है। ये फ़ील्ड केवल एडमिन्स के लिए दिखाई देते हैं।

कस्टम कंटेनर नाम पैनल के अपने `msm-` नेमस्पेस में भी नहीं रह सकते हैं, इसलिए हाथ से नामित कंटेनर कभी भी दूसरे सर्वर के कंटेनर को शैडो नहीं कर सकता और गलत इंस्टेंस पर स्टॉप या कमांड को निर्देशित नहीं कर सकता।

## खातों का प्रबंधन

![प्रोफ़ाइल चित्र](/docs/images/profile-picture.png)

एडमिन्स यूज़र टेबल से यूज़र बना सकते हैं, भूमिकाएँ बदल सकते हैं, पासवर्ड रीसेट कर सकते हैं और खाते डिलीट कर सकते हैं। **2FA** कॉलम दिखाता है कि क्या प्रत्येक यूज़र के पास टू-फ़ैक्टर सक्षम है; एक एडमिन उस यूज़र के एक्शन मेनू में **Reset 2FA** के साथ किसी अन्य यूज़र का 2FA रीसेट कर सकता है (खोए हुए फ़ोन और बैकअप कोड के मामले के लिए), लेकिन कभी भी अपने पासवर्ड के बिना अपना खुद का अक्षम नहीं कर सकता, जिसे सेल्फ-सर्विस फ़्लो संभालता है।

विफल लॉगिन प्रति खाता दर-सीमित (प्रति-IP और खाता-ग्लोबल काउंटर दोनों) हैं ताकि ब्रूट-फ़ोर्स प्रयासों को धीमा किया जा सके, और वही सीमा 2FA कोड चरण को कवर करती है ताकि एक सही पासवर्ड कोड-अनुमान लगाने से पहले काउंटर को रीसेट न कर सके। इसके सामने लॉगिन / 2FA / सेटअप एंडपॉइंट्स पर एक मोटा प्रति-क्लाइंट-IP अनुरोध सीमक है, जिसे `RATE_LIMIT_AUTH_PER_15MIN` के माध्यम से ट्यून किया जा सकता है (डिफ़ॉल्ट 100; रिवर्स प्रॉक्सी के पीछे, `TRUST_PROXY` सेट करें ताकि यह वास्तविक क्लाइंट IP पर आधारित हो)।
