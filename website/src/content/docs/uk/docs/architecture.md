Minecraft Server Manager — це однопроцесна, серверно-відрендерена Node.js програма. Вона керує
серверами Minecraft, які працюють як Docker-контейнери, використовуючи образ
[itzg/docker-minecraft-server](https://github.com/itzg/docker-minecraft-server), взаємодіючи з
Docker daemon через його API (ніколи не викликаючи `docker` CLI через оболонку).

## Форма виконання

- **Express + Handlebars** рендерять сторінки на стороні сервера. SPA відсутнє; JavaScript браузера в `public/js/`
  є написаним вручну для поступового покращення. Крок esbuild (`pnpm run build:js`) пакує та
  мініфікує його в `public/dist/js/`; програма обслуговує цей бандл, коли він присутній, а сирцевий
  код — в іншому випадку, тому розробка без збірки все одно працює.
- **`node:sqlite`** (вбудований в Node; панелі потрібен Node ≥ 24) — це база даних: синхронна,
  без нативних модулів, в режимі WAL. Невеликий міграційний механізм з версіями застосовує `src/db/migrations/*` при
  завантаженні. Підготовлені запити кешуються в `src/db/index.js` за ключем SQL тексту.
- **`ws`** забезпечує потоки консолі та статистики в реальному часі. Обидва є **посередницькими**: один вихідний потік
  `docker logs --follow` (або `docker stats`) на сервер, демультиплексований один раз і розповсюджений на кожну
  підключену вкладку, замість одного вихідного потоку на кожного глядача. Посередник консолі зберігає невеликий буфер відтворення
  для вкладок, що приєднуються пізніше, і відключає підписника, чий сокет надто відстає, замість того, щоб уповільнювати спільний потік.
- **dockerode** — єдиний спосіб взаємодії програми з Docker. Кінцева точка автоматично визначається для кожної платформи
  (іменований канал Windows проти Unix-сокету).
- **Весь постійний стан зберігається в одній директорії** (`$DATA_DIR`, за замовчуванням `./data`). Копіювання цієї
  директорії мігрує всю панель.

## Шарування

Залежності течуть в одному напрямку:

```
                 ┌─────────────────────────────┐
   HTTP  ───────▶│  web/routes/*  (+ middleware)│   розбір та валідація вводу, формування відповідей
                 └──────────────┬──────────────┘
                                │
                 ┌──────────────▼──────────────┐
                 │         services/*          │   доменна логіка (реальні функції)
                 └───┬─────────┬─────────┬─────┘
                     │         │         │
        ┌────────────▼──┐ ┌────▼────┐ ┌──▼──────────┐
        │   docker/*    │ │  db/*   │ │  storage/*  │   інфраструктура
        └───────────────┘ └─────────┘ └─────────────┘
```

- **`web/routes/`** — один маршрутизатор на домен (`servers`, `players`, `worlds`, `crashes`, `blueprints`,
  `files`, …), підключений в `web/app.js`. Маршрутизатори валідують за допомогою zod, викликають сервіс і повертають JSON
  або рендерять представлення. Бізнес-логіка тут не належить. Два маршрутизатори підключені в **публічній зоні**,
  перед `requireAuth`: `routes/status.js` (HTML-сторінки статусу для кожного сервера за бажанням) та
  `routes/apiV1.js` (`/api/v1`, JSON API тільки для читання, автентифікований токеном Bearer, виданим адміністратором, з
  `services/apiTokens.js`, вимкнений, якщо не активовано в Налаштуваннях; див. `docs/public-api.md`).
- **`services/`** — серце програми. Кожен сервіс володіє одним доменом і може залежати від
  інфраструктури та інших сервісів.
- **`docker/`** — обгортки dockerode: `connect` (визначення кінцевої точки + стан daemon), `containers`
  (створення/запуск/зупинка/перестворення з прив'язаними томами, обмеженнями пам'яті/CPU та мітками), `logs`, `stats`,
  `images` та `watcher`, який перетворює події Docker на історію + виявлення збоїв.
- **`db/`** — обгортка SQLite та механізм запуску міграцій.
- **`storage/`** — початкове завантаження `./data`, **захист шляхів** (`safeJoin`, основа безпеки файлів) та фоновий індексатор розмірів + контроль квот.

Перехресні аспекти:

- **`config/`** — конфігурація середовища плюс **каталог полів**: єдине джерело правди для
  налаштувань сервера. Кожна змінна середовища itzg каталогізована (мітка, довідка, тип, одиниця вимірювання, значення за замовчуванням,
  валідація, розділ, прапори небезпеки). Майстер, форми налаштувань та валідація zod походять від нього, тому виведення нового налаштування — це зміна даних, а не нова обв'язка UI.
- **`events/`** — `recordEvent()` — єдина точка входу для журналу історії; події життєвого циклу також захоплюють уривки логів контейнерів до `data/logs/<id>/events/`.
- **`ws/`** — автентифіковані WebSockets консолі + статистики (cookie сесії перевіряється при оновленні, `Origin` перевіряється для блокування міжсайтового викрадення), посередницькі для кожного сервера (див. "Форма виконання").
- **`logger.js` + `instrument.js`** — `require('./logger')(label)` повертає модуль [Pino](https://getpino.io) логер для кожного модуля; рівень з `LOG_LEVEL`, `makeFailureThrottle()` підтримує цикл фонової роботи, що постійно збоїть, до одного рядка логу плюс рядок "відновлено".
  `src/utils/logSanitize.js` видаляє ключі, схожі на облікові дані, та токени вебхуків зі структурованих метаданих; `src/config/logLevel.js` — це спільний список дозволених рівнів (зберігається окремо, щоб уникнути циклу `require` з `config`). `src/instrument.js` — це неактивний шов Sentry, завантажений першим у
  `src/server.js`. `src/web/middleware/requestLog.js` записує один рядок доступу для кожного запиту (пропускаючи `/healthz` та статичні файли). ESLint забезпечує `no-console` в `src/**`, з винятками для `preflight.js`, `instrument.js` та `config/index.js` (вони запускаються до існування логера).
- **Обмеження швидкості** — `src/web/middleware/rateLimit.js` розміщує `express-rate-limit` перед `/api`
  (`RATE_LIMIT_API_PER_MIN`, за замовчуванням 1200) та POST-запити входу / 2FA / налаштування
  (`RATE_LIMIT_AUTH_PER_15MIN`, за замовчуванням 100); `0` вимикає обмежувач. Він використовує `req.ip` як ключ, тому
  `TRUST_PROXY` має значення за проксі. `/api/v1` має власний обмежувач на токен
  (`RATE_LIMIT_PUBLIC_API_PER_MIN`, за замовчуванням 120), ключований хешем токена Bearer з резервним варіантом IP. Окремий лічильник для кожного облікового запису в
  `src/web/middleware/auth.js` обробляє блокування входу (за IP та глобально для облікового запису, з затуханням).

## Ключова поведінка домену

- **Модпаки завжди закріплюються.** Образ автоматично оновлює незакріплені паки при кожному перезапуску, тому панель розпізнає "latest" до конкретного ідентифікатора версії під час встановлення та закріплює його. Оновлення — це явний оркестрований потік (`updates/`): попередній перегляд → резервне копіювання перед оновленням → граційна зупинка → перезакріплення →
  перестворення → монітор стану → відкат одним кліком.
- **Надбудова користувацьких модів** керується панеллю: додані користувачем моди потрапляють до дедуплікованої бібліотеки та жорстко посилаються на сервер, тому вони переживають оновлення паків. Вимкнення залежить від класу.
- **Порти** виділяються зі схеми бази (гра від `PORT_GAME_START` і вище, RCON = гра +
  `PORT_RCON_OFFSET`, Bedrock від `PORT_BEDROCK_START`), перевіряються на доступність та резервуються в
  базі даних.
- **Дискові квоти** контролюються панеллю, оскільки Docker не може обмежувати використання прив'язаних томів: індексатор
  кешує розміри директорій, а операції розширення диска обмежуються ними.
- **Секрети** (паролі RCON, ключі API, секрети TOTP, URL вебхука Discord) шифруються при зберіганні за допомогою AES-256-GCM з використанням виділеного випадкового ключа в `$DATA_DIR/.secret-key` (режим `0600`,
  автоматично згенерований). Він незалежний від `SESSION_SECRET`; ключ, похідний від `SESSION_SECRET`, зберігається як резервний варіант тільки для розшифровки для значень, записаних до появи виділеного ключа, а
  `src/services/secretsMigration.js` перешифровує їх під виділеним ключем один раз при завантаженні.
  Існуючий `.secret-key`, який не може бути розпарсений, є критичною помилкою завантаження (він ніколи не генерується повторно мовчки поверх старого). Блюпринти видаляють усі секрети при експорті.

## Формати даних та передачі

- **`data/panel.db`** — база даних SQLite. Щоденно знімкується через `VACUUM INTO` до
  `data/backups/_panel/` (зберігається 14 найновіших); `PRAGMA integrity_check` запускається при завантаженні.
- **`data/.session-secret`** — автоматично згенерований секрет підпису cookie, створений при першому запуску, якщо
  `SESSION_SECRET` не встановлено. Видалення його обертає секрет (що анулює сесії).
- **`data/.secret-key`** — виділений 32-байтовий ключ шифрування при зберіганні (режим `0600`), автоматично створений
  при першому запуску. Незалежний від `SESSION_SECRET`; його видалення робить усі збережені облікові дані
  нерозшифровуваними, тому він належить до ваших резервних копій.
- **Блюпринти (`.mcserver.zip`)** — zip-архів з `manifest.json`, що описує конфігурацію, ресурси, закріплене посилання на пак, маніфест надбудови (URL-адреси джерел + sha256), вибрані конфігураційні файли та, опціонально, світ. Імпорт повторно завантажує та перевіряє хеш кожного мода та призначає нові порти.
- **Docker-контейнери**, створені панеллю, іменовані та позначені мітками, щоб спостерігач міг їх знайти;
  панель володіє їх повним життєвим циклом.

## Послідовність завантаження

1. `require('./instrument')` (шов Sentry) перед усім іншим, потім `require('./preflight')`
   для чіткого збою при непідтримуваній версії Node.
2. Завантаження конфігурації; забезпечення/генерація `.session-secret` **та** `.secret-key`.
3. `ensureDataRoot()` — створення структури `./data`, очищення `tmp/`.
4. Запуск міграцій бази даних, потім `PRAGMA integrity_check` (гучно логує, вказує на `data/backups/_panel`
   при збої).
5. Перешифрування будь-яких застарілих секретів, зашифрованих `SESSION_SECRET`, під `.secret-key` (`secretsMigration`).
6. Посів початкових блюпринтів (захищено).
7. Запуск HTTP + WS сервера. При відкритому підключенні виведення PIN-коду першого запуску `/setup`.
8. Встановлення захисту виконання після завантаження (перехоплює незловлені збої; `MSM_EXIT_ON_FATAL=1` змушує жорстко вийти для керованих розгортань).
9. Запуск фонових сервісів: посередник WS, індексатор сховища, спостерігачі збоїв + інвентарю, планувальник,
   міст подій Discord та **щоденний таймер обслуговування** (очищення старих рядків аналітики + знімок
   `panel.db`).
10. Ініціалізація Docker **у фоновому режимі**. UI повністю функціональний, поки daemon недоступний;
    функції Docker активуються, коли він стає доступним. Після підключення `refreshStatuses({ boot })`
    узгоджує кешовані статуси, генерує одноразову подію `offline-after-restart` для сервера, який був увімкнений до перезапуску панелі і не буде відновлений, а цикл завантаження запускає
    сервери `auto_start` плюс відновлює сервери `auto_restart`, знайдені збитими під час збою
    (з урахуванням затримки циклу збоїв).

> Порядок `instrument`-перед-`preflight` є свідомим компромісом: він дозволяє майбутньому підключенню Sentry першим оновити виконання, за рахунок трохи менш дружнього повідомлення при справді старому Node.

## Конвеєр збірки

`pnpm run build` = `build:css` (Tailwind → `public/css/app.css`) + `build:js` (esbuild →
`public/dist/js/`, ESM з розбиттям коду). `postinstall` запускає **тільки CSS**. `public/css/app.css`
та `public/dist/` є артефактами збірки, які ігноруються git; етап збірки Dockerfile запускає повний
`pnpm run build` та копіює `public/` в образ виконання. Статичні файли обслуговуються з
`immutable`/довгим кешем для файлів з відбитками, коротким кешем для CSS/JS та `no-cache` для HTML та
`/api`.
