Коротка відповідь для сервера, на якому реально гратимуть:

| Що ви запускаєте                             | Java heap | Надайте машині |
| -------------------------------------------- | --------- | -------------- |
| Vanilla або Paper, до 10 гравців             | 2 ГБ      | 4 ГБ           |
| Paper з плагінами, 10-30 гравців             | 4 ГБ      | 6 ГБ           |
| Легкий модпак, 40-80 модів                   | 4 ГБ      | 6 ГБ           |
| Великий модпак "все в одному", 150-300 модів | 6-8 ГБ    | 10 ГБ          |
| GregTech New Horizons та подібні монстри     | 8-12 ГБ   | 16 ГБ          |

Два числа, а не одне. Саме це найчастіше пропускають у посібниках, і саме тому люди купують сервер на 4 ГБ, виділяють Java 4 ГБ, а потім спостерігають, як він вмирає.

## Heap та машина — це різні числа

Java heap (`-Xmx`) — це обсяг пам'яті, який сама гра може використовувати для світу, сутностей та даних модів. Машина, або контейнер, повинна вмістити цей heap **плюс** усе інше, що потрібно Java: метадані класів, стеки потоків, облік збирача сміття, мережеві буфери та саму JVM. Цей накладний витрат становить приблизно 0,5-1,5 ГБ для сервера з модами.

Якщо heap дорівнює пам'яті машини, ядро ​​видалить сервер у той момент, коли Java спробує використати ці накладні витрати. У Docker це відображається як код виходу 137, а в логах — ніяк: процес просто зникає посеред речення. Зазвичай звинувачують мод.

Безпечне правило: **heap плюс 25 відсотків, і щонайменше один гігабайт запасу.** 8 ГБ heap потребують машини на 10 ГБ.

## Більше RAM — не більше продуктивності

Minecraft у більшості операцій прив'язаний до одного потоку. Надання модпаку на 40 модів 16 ГБ не прискорить генерацію чанків; це лише подовжить кожну паузу збирання сміття, оскільки є більше об'єктів для обробки. Сервер, який заїкається кожні тридцять секунд, часто має занадто великий heap, а не занадто малий.

Збільшуйте heap, коли бачите це, і не інакше:

- `java.lang.OutOfMemoryError: Java heap space` у логах.
- Повторювані повідомлення "Can't keep up! Is the server overloaded?" з паузами збирання сміття в таймінгах.
- Використання пам'яті, яке досягає максимуму і залишається там годинами.

## Чому ваш сервер показує 12 ГБ використаної пам'яті, коли нікого немає онлайн

Тому що ви так наказали. Два налаштування за замовчуванням діють разом:

1. Поширений образ Docker встановлює початковий heap рівним максимальному, тому `-Xms` і `-Xmx` — це одне й те саме число. Java резервує його одразу, а не поступово збільшує.
2. Популярний набір прапорів Aikar включає `-XX:+AlwaysPreTouch`, який обробляє кожну сторінку цього heap під час запуску, щоб сторінки були дійсно виділені. Це навмисно: це компроміс між повільнішим запуском та великим показником у стані спокою заради меншої кількості пауз пізніше.

Виміряно на Paper 1.21.1 з heap 2 ГБ у контейнері 4 ГБ, вибірка за три хвилини після завершення завантаження світу:

| Конфігурація                           | Резидентна пам'ять |
| -------------------------------------- | ------------------ |
| Без прапорів                           | 2.60 GiB           |
| Прапори Aikar                          | 2.59 GiB           |
| Прапори Aikar без `AlwaysPreTouch`     | 1.95 GiB           |
| Прапори Aikar з початковим heap 512 МБ | 1.38 GiB           |
| Без прапорів з початковим heap 512 МБ  | 1.25 GiB           |

Отже, сервер, який "використовує" 12 ГБ у стані спокою, зазвичай має heap 12 ГБ, який був попередньо оброблений, а не витік пам'яті. Ваш моніторинг показує це правильно; число просто не означає те, на що виглядає.

Якщо ви хочете чесний показник у стані спокою, встановіть початковий heap нижче за максимальний. Ви платите за це кількома додатковими зборами сміття на початку. Якщо ви віддаєте перевагу стабільним часовим рамкам кадрів, залиште все як є і припиніть стежити за графіком.

## Гравці мають менше значення, ніж ви думаєте

Подвоєння кількості гравців з 10 до 20 коштує набагато менше, ніж додавання п'ятдесяти модів. Гравці переважно додають сутності та завантажені чанки, які масштабуються плавно. Моди додають дані класів, реєстри, функції генерації світу та власні кеші, які не масштабуються. Спочатку враховуйте розмір модпаку, а потім додавайте приблизно 100-200 МБ на кожного звичайного гравця на сервері з модами.

Відстань перегляду — це інший важливий важіль. Зменшення з 12 до 8 чанків може заощадити гігабайт на завантаженому сервері і майже непомітно для гри.

## У Minecraft Server Manager

Кожен сервер має два окремі поля: **Java heap** та **ліміт пам'яті контейнера**, саме тому, що це різні питання. Майстер створення встановлює ліміт контейнера на 50 відсотків вище за heap для вас, і панель відмовляється зберігати сервер, ліміт контейнера якого не перевищує його heap, оскільки така комбінація призводить до коду виходу 137, а не до повідомлення про помилку.

Лічильник пам'яті на сервері показує, що насправді використовує контейнер, з приміткою, коли heap був затребуваний одразу, тому попередньо оброблений heap не відображається як неконтрольований. Сервер, який ядро ​​вимкнуло через брак пам'яті, записується саме так в історії, а не як таємниче аварійне завершення.
